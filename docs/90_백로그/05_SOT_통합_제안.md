# SOT 통합 제안

이 문서는 AI-first 기준문서 운영 중 "같은 개념이 여러 파일에 중복·분산 정의"되어 발생하는 drift 위험을 목록화하고, 각 중복에 대한 통합안을 제안한다.

팀 리뷰 후 실제 병합 작업의 근거로 사용한다. 여기 기술된 파일 경로·줄 번호·인용문은 2026-04-20 기준 실제 파일에서 확인된 내용이다.

### 문제: 어떻게 drift될 수 있는가

1. **`accepted` 설명 표현 차이**: `05/01`은 "프로젝트 내부 합의 후 현재 구현 기준으로 사용하는 문서"로 합의 절차를 강조하고, `README`와 `05/08`은 "현재 구현 기준. 충돌 시 우선 준수"로 사용 규칙을 강조한다. AI가 합의 조건 없이 개별 문서를 accepted로 승격 가능한지 판단할 때 해석이 갈릴 수 있다.
2. **`accepted_candidate` 조건 표현 차이**: `05/01`은 "`08_문서_상태_인덱스.md` 또는 작업 브리핑에 명시된 binding 범위 안에서"라는 조건을 명시하나, README는 "임시 구현 기준. 작업 브리핑에 가정과 중단 조건을 적고 사용"으로 더 짧게 표현한다. `08`이 인덱스 자신임을 모르는 AI는 두 조건을 다르게 읽을 수 있다.
3. **`deprecated`/`archived` 재분류 지침**: `05/01` 21줄에만 존재. README와 `05/08`에는 없어, AI가 과거 문서의 `deprecated` 표현을 만났을 때 재분류 기준을 못 찾으면 할루시네이션 가능성이 있다.
4. **향후 상태값 추가 시 3곳 동시 수정 필요**: 현재 A·B·C가 모두 독립 표이므로 한 곳만 수정되면 나머지가 stale된다.

### 통합안

- **SOT 지정**: `05_문서관리_규칙/01_문서_상태와_변경_규칙.md`를 상태 정의의 단일 SOT로 지정한다.

- **README 처리**: 현재 91–109줄의 상태 표를 `[문서 상태 정의 SOT](05_문서관리_규칙/01_문서_상태와_변경_규칙.md#상태-정의)` 한 줄 링크로 대체한다. README는 읽는 순서와 SOT 위치를 안내하는 역할에 집중한다.
- **`05/08` 처리**: 9–17줄의 "상태 읽기" 표를 `[상태 정의는 01_문서_상태와_변경_규칙.md 참조](01_문서_상태와_변경_규칙.md#상태-정의)` 한 줄로 축소한다. `05/08`의 역할은 "문서별 binding 범위 인덱스"이므로 상태 정의 반복은 불필요하다.

```
## BLOCKED 처리 기준

아래에 해당하면 작업자는 임의로 진행하지 말고 `BLOCKED`로 보고한다.

- `accepted` 게임 규칙과 구현 요청이 충돌한다.
```

```
## BLOCKED 기준
```

### 문제: 어떻게 상충/drift될 수 있는가

| 항목 | `05/01` (구현 BLOCKED) | `09` (공유 BLOCKED) | `60/01` (AI 중단) |
|---|---|---|---|
| 목적 | 구현 작업 중단 기준 | 팀 공유본 배포 중단 기준 | AI 세션 중단 기준 |
| 트리거 | 기준문서와 구현 요청 충돌 | 문서 내 보안/충돌 항목 발견 | 요구사항이 기준문서와 충돌 |
| 대상 주체 | 구현자(AI 포함) | 문서 검토자 | AI 작업자 |
| `ChoicePending` 잠금 | 직접 언급 없음 | 빠지면 BLOCKED | 직접 언급 없음 |
| 수치 확정 | 전투 철학 변경만 BLOCKED | 기준문서에 수치 확정값 기록이면 BLOCKED | 직접 언급 없음 |

**구체 drift 시나리오**: AI가 `60/01`만 읽고 작업 중단 기준을 판단하면, "기준문서와 요청 충돌" 조건만 보게 된다. `05/01`의 3D 물리 금지선이나 `09`의 `ChoicePending` 잠금 누락 같은 구체 기준을 모른 채 구현을 계속할 수 있다.

반대로, AI가 `09`의 BLOCKED를 구현 중단 기준으로 오인하면 "카드 지급 조건 설명이 문서마다 다르다"는 이유로 모든 카드 관련 구현을 중단할 수 있다.

### 통합안

세 곳의 BLOCKED는 **목적이 달라 통합이 아닌 명시적 분리**가 올바른 처리다.

- **`05/01`**: "구현 작업 BLOCKED" — 현재 내용 유지. 이것이 구현자의 중단 기준 SOT다.
- **`09`**: "공유본 검토 BLOCKED" — 현재 내용 유지. 검토 verdict이며 구현 BLOCKED와 다른 개념임을 헤더 또는 주석으로 명시한다. 예: "이 BLOCKED는 팀 공유본 배포 중단을 의미하며, 구현 작업 BLOCKED 기준은 `05/01`을 따른다."
- **`60/01`**: "AI 세션 중단 조건" — 현재 내용 유지하되, "상세 기준은 `05_문서관리_규칙/01_문서_상태와_변경_규칙.md`의 BLOCKED 처리 기준 참조"를 한 줄 추가한다.

### 문제: 어떻게 상충/drift될 수 있는가

현재 5곳이 같은 내용을 유지하고 있으나, 향후 변경이 발생할 때 문제가 생긴다.

**구체 drift 시나리오 1**: 플레이테스트 후 "전장을 완전히 끊는 별도 화면이 낫다"는 결정이 나와 `D33`과 `Q20`을 업데이트하지만, `40/30/01`과 `45/02`의 오버레이 기술을 누락하면, AI가 `40/30/01`을 읽고 여전히 오버레이 방식으로 구현한다.

**구체 drift 시나리오 2**: `10/03`의 입력 충돌 방지 표("반투명 카드 오버레이 입력만 받는다")가 오버레이 방식을 전제로 코드화되어 있다. "별도 화면"으로 바뀌면 `10/03`의 입력 잠금 범위가 달라져야 하는데 연결이 없으면 구현자가 놓친다.

**구체 drift 시나리오 3**: Q20이 `closed`로 표시되어 있어 AI가 임시 가정 내용을 "확정된 결정"으로 오해할 수 있다. 실제 결정 SOT는 D33이지만 Q20에서 먼저 발견하면 Q20 임시 가정을 근거로 사용할 수 있다.

### 통합안

  - `10/03`: "반투명 카드 오버레이 입력만 받는다" 표현을 `[카드 선택 UI 정책 SOT](../40_카드_무기_설계/30_구현가이드/01_카드_선택_네트워크_핸드셰이크.md)를 따른다`로 대체한다. 입력 잠금 원칙만 유지하고 UI 방식 설명은 링크로 대체.
