# 팀원 docs 반영 검토

이 문서는 팀원이 제공한 docs 문서를 우리 내부 기준문서 구조에 어떻게 반영할지 검토한 기록이다.

게임 규칙, 카드 보상, 전장/구간 구조, TTK 철학은 기존 기획 세션 기준을 우선한다. 팀원 문서의 게임 규칙과 수치값은 지금 단계에서 그대로 병합하지 않는다.

## 결론

| 영역 | 판단 |
|---|---|
| 게임 규칙/GDD | 보류. 우리 쪽 전장/구간/카드 철학과 충돌 가능 |
| 기술 구조 | 팀원 기준으로 확정. 2D Fusion 네이티브를 따른다 |
| Corgi/Fusion 분석 | 기술 기준에 반영. Corgi는 부분 활용으로 고정 |
| 프로젝트 구조 | 부분 반영. 서드파티 분리, Git LFS, Odin 분기 유용 |
| 팀 운영 | 부분 반영. DRI, 결정 등급, 게이트 운영은 유용 |
| 마일스톤/리스크 | 부분 반영. 일정 수치는 고정하지 말고 게이트 구조만 사용 |
| 템플릿 | 반영 추천. Feature Spec, Playtest, Sprint Review 유용 |

## 완성도 평가 결과

충돌 여부와 별개로, 반영 문서 자체의 완성도는 아래 기준으로 다시 평가했다.

평가 기준:
- 실사용성: 팀원이 바로 작성하거나 판정할 수 있는가.
- 모호성: 언제 쓰는지, 무엇을 완료로 보는지 애매하지 않은가.
- 책임소재: 오너, DRI, 리스크 오너처럼 관리 주체를 남길 수 있는가.
- 산출물 연결: 기능 스펙, 작업 브리핑, 플레이테스트, 스프린트 리뷰, 프리셋과 연결되는가.
- 과잉관리: 게임개발 초보 팀에게 불필요하게 무겁지 않은가.

| 반영 문서 | 평가 | 보정 내용 |
|---|---|---|
| 02_의사결정_등급.md | 조건부 충분 | 기록 위치와 완료 판정 추가 |
| 03_리스크_로그_운영.md | 조건부 충분 | 검증 방법, 갱신 규칙, 완료 판정 추가 |
| 03_기능_스펙_양식.md | 조건부 충분 | 작성 단위, 산출물 연결, 작업 전달 체크 추가 |
| 02_플레이테스트_리포트_양식.md | 조건부 충분 | 빌드 식별자, 액션 유형, 첨부 근거 추가 |
| 03_스프린트_리뷰_양식.md | 조건부 충분 | 리뷰 판정과 다음 산출물 연결 추가 |
| 04_마일스톤_게이트.md | 조건부 충분 | 판정 방식, 진입 조건, 완료 판정 추가 |

평가 결론:
- 현재 6개 문서는 팀 내부에서 시험 사용 가능한 수준이다.
- 아직 `accepted`로 승격하기에는 실제 팀 사용 이력이 부족하다.
- 첫 사용 이후 양식이 너무 무겁거나 비어 있는 칸이 반복되면 항목을 줄인다.

## 확정 반영된 내용

### 1. 기술스택 확정: 2D Fusion 네이티브

팀원 문서는 `Rigidbody2D + NetworkRigidbody2D + Razor Madness` 쪽으로 강하게 기울어져 있다.

기술스택은 팀원이 확정했으므로, 우리 기준문서도 `2D Fusion 네이티브`를 따른다.

| 항목 | 확정 기준 |
|---|---|
| 물리 | Rigidbody2D + Collider2D |
| 네트워크 물리 | NetworkRigidbody2D |
| 캐릭터 구조 | Razor Madness 참고 + Fusion 네이티브 자체 구현 |
| 폐기 | 2.5D 3D 물리, 액티브 래그돌, Configurable Joint 전제 |

반영 방식:
- `50_기술_구조_기준/01_Unity_프로젝트_구조.md`에 반영 완료.
- 이후 작업 브리핑에는 2D Fusion 네이티브를 기본값으로 전달한다.

### 2. Corgi Engine 활용 범위

팀원 문서의 핵심 주장은 Corgi를 캐릭터/무기/어빌리티에는 쓰지 않고, MMFeedbacks/레벨 도구/참고 코드로만 쓰자는 것이다.

이 내용은 기술스택 확정안으로 수용한다.

반영 방식:
- Corgi 캐릭터/무기/어빌리티 시스템은 직접 사용하지 않는다.
- Corgi는 타격감, 카메라/레벨 도구, 참고 코드 중심으로 활용한다.
- 자세한 기술 분석 문서는 필요하면 별도 요약본으로 추가한다.

## 신중하게 다뤄야 하는 내용

### 1. 마일스톤 일정

팀원 문서는 고정 데드라인 기준으로 M1~M4를 제시한다.

일정 구조는 유용하지만, 각 작업의 날짜와 SP는 팀 합의 전에는 고정하면 안 된다.

반영 방식:
- 날짜와 SP는 제거하거나 예시로 둔다.
- 게이트 중심으로 변환한다.

```text
M1: 코어 전투가 한 판으로 성립하는가
M2: 카드와 타격감이 재미를 만드는가
M3: 온라인/네트워크가 데모 가능한가
M4: 안정 빌드와 발표 품질이 확보됐는가
```

추천 문서:
- `70_검증_체크리스트/04_마일스톤_게이트.md`

반영 상태:
- 날짜/SP/개인 태스크를 제거하고 `70_검증_체크리스트/04_마일스톤_게이트.md`로 반영 완료.

## 지금 반영하지 않을 내용

| 항목 | 보류 이유 |
|---|---|
| GDD의 매치 규칙 | 우리 전장/구간/돌파/카드 보상 설계와 충돌 가능 |
| 카드 10종 목록 | 세부 카드 전체 목록은 협업 기준 이후 백로그 |
| 수치값 | 기준문서에는 수치 고정 금지. 프리셋으로 분리 필요 |
| 개인별 R&R | 최종 5인 역할 고정은 보류. 회의 전 임시 작업 소유권은 별도 후보 문서로 관리 |
| Discord/Jira 세부 | 실제 팀 운영 도구 확정 후 반영 |
| 개인 노트 흐름 | 팀 공통 도구가 아니므로 내부용으로만 참고 |

## 후속 작업 후보

1. Corgi/Fusion 분석은 필요하면 기술 리스크 요약 문서로 추가한다.
2. 팀 공유 후 리뷰 결과를 기준문서, 세부설계, 백로그 중 어디에 반영했는지 기록한다.
3. 팀 운영 도구가 바뀌면 이슈/브랜치/리뷰 규칙을 별도 갱신한다.

## 다음 결정 필요

기술스택 충돌은 팀원 기준으로 정리됐고, 운영/검증 양식은 충돌 없는 범위에서 반영됐다.

다음 결정은 문서 운영 쪽이다.

- 기술 리스크 요약 문서를 추가할지.
- 실제 플레이테스트가 시작되면 어떤 지표를 첫 프리셋 목표로 둘지.
