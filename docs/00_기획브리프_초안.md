# 쿡싸피 기획 브리프 초안

## 현재 작업명
- 가칭: `쿡싸피`

## 한 줄 정의
- 주문 타임라인과 레시피 DAG가 주어진 주방에서, 학생이 작성한 `decide(state)` 코드가 직원의 다음 작업을 자동 결정하고 그 결과를 시뮬레이션으로 검증하는 `알고리즘 학습형 주방 시뮬레이션 게임`

## 왜 이 프로젝트인가
- 배틀싸피가 BFS, 다익스트라를 `이동과 경로 탐색`으로 체감시키는 구조였다면, 이번 프로젝트는 `레시피 선행관계와 작업 스케줄링`을 주방 운영으로 체감시키는 구조를 목표로 한다.
- 음식 제작은 `손질 -> 조리 -> 조합 -> 플레이팅`처럼 선행조건이 자연스럽고, 주문은 `도착 시각`과 `마감 시각`을 가지므로 `위상정렬 + 우선순위 판단`을 설득력 있게 녹일 수 있다.
- 사용자는 직접 한 턴씩 조작하지 않고, 자신의 로직이 영업 시간 전체를 어떻게 운영하는지 `리플레이와 결과 분석`으로 확인한다.

## 문제정의
- 플레이어가 손으로 매 순간 입력하는 게임이 아니라, 학생이 사전에 작성한 코드가 매 틱 주방 상태를 읽고 다음 작업을 결정하는 구조여야 한다.
- 각 주문은 레시피 DAG를 가지며, 현재 가능한 작업은 선행조건이 모두 충족된 노드로 제한된다.
- 단일 직원 또는 소수 직원이 여러 주문 사이에서 어떤 작업을 먼저 시작할지 결정해야 하며, 이 결정은 주문 성공률과 평균 대기 시간에 직접 영향을 준다.
- 따라서 이 게임의 본질은 `요리 조작`이 아니라 `상태를 읽고 정책을 설계하는 것`이다.

## 핵심 학습 목표
- 1차 학습 목표: `위상정렬`
  - 레시피 DAG에서 지금 수행 가능한 작업을 판별
  - 선행조건을 만족하는 유효한 작업 순서를 구성
- 2차 학습 목표: `시간 제약 하 작업 우선순위 판단`
  - 주문 도착 시각, 마감 시각, 작업 시간을 함께 고려
  - 유효한 작업 중 어떤 것을 먼저 처리할지 결정
- 확장 학습 목표:
  - 공유 선행작업의 전략적 가치
  - 복수 직원 환경에서의 assignment / routing

## 핵심 사용자 경험
- 코드 작성 단계:
  - 학생이 `decide(state)` 하나를 개선하면서 자신의 정책을 설계한다.
- 실행 단계:
  - 시뮬레이터가 영업 시간을 틱 단위로 진행하며 학생 코드의 결정을 적용한다.
- 회고 단계:
  - 리플레이, 턴 로그, 주문 실패 원인, 성능 지표를 통해 로직의 약점을 이해한다.

## 현재 방향의 결론
- 장르는 `턴제 퍼즐`이 아니라 `코드 설계형 시뮬레이션 게임`이다.
- 핵심 인터랙션은 `사전 코드 작성`이지 `실시간 또는 턴별 수동 조작`이 아니다.
- MVP는 `직원 1명 + decide(state)` 구조로 출발한다.
- 위상정렬은 핵심 기반 개념이고, 스케줄링은 그 위에 얹히는 선택 문제로 설명한다.
- 리플레이와 디버깅 가능한 결과 화면이 필수다.

## 필수 입력 및 의존성
- 필수 입력
  - 메뉴별 레시피 DAG 정의
  - 주문 스폰 타임라인과 마감 규칙
  - 작업 타입별 소요 시간표
  - 챕터별 직원 구성과 통과 기준
- 외부 의존성
  - 학생 코드 실행을 위한 샌드박스 또는 안전한 실행 환경
  - 틱 기반 시뮬레이터
  - 리플레이 및 결과 시각화 UI
- 구현 전제
  - 같은 시드에서 항상 같은 결과가 나오는 결정론 구조
  - 잘못된 Assignment를 무시하고 로그로 남기는 검증기

## 현재 성공 조건
- 이 게임이 `직접 조작형 요리 게임`이 아니라 `코드 기반 시뮬레이션 게임`임이 1분 안에 설명된다.
- `왜 위상정렬이 필요한가`와 `왜 스케줄링 판단이 추가되는가`가 모두 드러난다.
- 학생 API, 상태 모델, 평가 방식, 챕터 구조가 한 방향으로 맞물린다.
- MVP 범위가 과도하게 넓지 않고 실제 구현 가능한 단위로 잘려 있다.

## 현재 리스크
- 스케줄링 요소가 너무 커지면 위상정렬 학습 게임이라는 정체성이 약해질 수 있다.
- 복수 직원을 너무 빨리 도입하면 프로젝트 초점이 assignment 문제로 이동할 수 있다.
- 리플레이 화면이 약하면 코드 작성형 게임의 재미와 설득력이 떨어질 수 있다.
