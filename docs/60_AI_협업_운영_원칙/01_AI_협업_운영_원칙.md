# AI 협업 운영 원칙

> 상태: accepted_candidate. 이 문서는 AI 작업 전 기준문서 확인, 담당 범위, 중단 조건, 결과 보고 원칙에 한해 임시 구현 기준으로 사용한다. 문서 상태와 binding 범위는 `05_문서관리_규칙/08_문서_상태_인덱스.md`를 우선한다.

이 문서는 팀원이 AI 도구를 활용해 게임 개발 작업을 진행할 때 지켜야 하는 공통 운영 원칙을 정의한다.

대상 도구는 특정하지 않는다. 각자 사용하는 AI 도구가 무엇이든 이 문서의 기준을 따른다.

## 핵심 원칙

AI는 담당자의 대체자가 아니라, 담당자가 가진 소유 범위 안에서 기준문서를 읽고 작업을 보조하는 실행 도구다.

| 원칙 | 의미 |
|---|---|
| 담당자가 책임진다 | AI가 만든 결과도 담당자의 작업물이다 |
| 기준문서를 먼저 읽는다 | 구현 전에 게임 규칙, 기술 기준, 소유권, 미결정을 확인한다 |
| 담당 범위를 넘지 않는다 | 다른 담당자의 시스템을 바꾸려면 먼저 확인한다 |
| 의존성을 먼저 본다 | 내 변경이 전투, 카드, 맵, UI, 네트워크에 미치는 영향을 확인한다 |
| 충돌은 멈춘다 | 기준문서, 담당 범위, 공용 프리팹, secret과 충돌하면 임의 진행하지 않는다 |
| 결과는 재현 가능해야 한다 | 다음 세션이나 다른 팀원이 같은 맥락으로 이어받을 수 있어야 한다 |

## 왜 필요한가

게임 개발은 일반 서비스 개발보다 시스템 의존성이 강하다.

입력 하나를 바꾸면 이동, 총격, 카드 선택, UI, 네트워크 동기화, 리스폰, 밸런스가 함께 흔들릴 수 있다. 각 담당자가 AI를 적극적으로 사용하면 작업 속도는 빨라지지만, 운영 기준이 없으면 AI마다 서로 다른 전제를 세우고 전체 게임의 정합성이 깨진다.

이 문서의 목적은 AI 사용을 제한하는 것이 아니라, 여러 AI 세션이 같은 기준문서를 읽고 같은 방식으로 작업하게 만드는 것이다.

## 작업 시작 순서

AI에게 작업을 맡기기 전 담당자는 아래 순서를 확인한다.

| 순서 | 확인 항목 | 목적 |
|---|---|---|
| 1 | 작업 목적 | 무엇을 만들거나 고칠지 한 문장으로 고정 |
| 2 | 담당 범위 | 본인 소유 시스템인지, 다른 담당자와 겹치는지 확인 |
| 3 | 기준문서 | 관련 게임 규칙, 기술 기준, 검증 기준 확인 |
| 4 | 미결정 질문 | open/blocked 질문이 있는지 확인 |
| 5 | 수정 가능 파일 | 공용 씬, 프리팹, 네트워크 설정, 기준문서 수정 여부 확인 |
| 6 | 검증 방법 | 실행, 테스트, 수동 확인, 문서 검토 중 무엇으로 완료 판단할지 결정 |

작업이 위 항목을 통과하지 못하면 바로 구현하지 않고 작업 브리핑 또는 질문으로 정리한다.

## 작업 브리핑 하드스톱

Jira 이슈 또는 작업 브리핑 없이 코드, 에셋, 공용 프리팹, 네트워크 설정을 수정하지 않는다.

예외는 오탈자 수정, 개인 로컬 메모 정리, 명백한 깨진 링크 수정처럼 게임 규칙과 구현 산출물에 영향을 주지 않는 초소형 문서 작업뿐이다.

브리핑이 없는데 구현이 필요해 보이면, AI의 첫 작업은 구현이 아니라 작업 브리핑 초안 작성이다. 브리핑 초안에는 담당 범위, 기준문서, 수정 가능 파일, 금지 파일, 검증 기준, 중단 조건을 적는다.

## AI에게 전달해야 하는 정보

AI 작업 요청에는 최소한 아래 정보가 포함되어야 한다.

| 항목 | 설명 |
|---|---|
| 목표 | 이번 작업의 완료 상태 |
| 배경 | 왜 이 작업이 필요한지 |
| 담당 범위 | 수정 가능한 시스템과 수정하면 안 되는 시스템 |
| 기준문서 | 반드시 읽어야 하는 문서 |
| 허용 파일 | 수정 가능한 파일 또는 디렉토리 |
| 금지 파일 | 건드리면 안 되는 씬, 프리팹, 설정, secret |
| 완료 기준 | 테스트, 플레이 확인, 문서 반영, 리뷰 기준 |
| 중단 조건 | 충돌, 미결정, 담당 외 영역 발견 시 멈출 기준 |

구체 양식은 `02_작업_브리핑_양식.md`를 따른다.

## 의존성 탑 확인

작업자는 기능을 단독 파일 수정으로만 보지 않는다. 아래 의존성 탑에서 어디를 건드리는지 먼저 확인한다.

| 계층 | 예시 | 충돌 위험 |
|---|---|---|
| 게임 규칙 | 승패, 구간 돌파, 카드 지급, 리스폰 | 매우 높음 |
| 네트워크 truth | StateAuthority, 입력, 동기화 상태 | 매우 높음 |
| 전투 판정 | 피격, 탄환, 넉백, 사망 | 높음 |
| 전장/구조물 | 구간, 카메라, 낙사, 추 | 높음 |
| 카드/밸런스 | 카드 후보, 티어 제한, 프리셋 | 중간 |
| UI/피드백 | HUD, 카드 선택 UI, VFX/SFX | 중간 |
| Presentation | 이모트, 혹, 화면 연출 | 낮음. 단, gameplay truth로 승격하면 높음 |

상위 계층을 바꾸는 작업일수록 AI가 임의로 결정하면 안 된다.

## 작업 분리 원칙

한 작업 안에 아래 성격을 무리하게 섞지 않는다.

| 섞으면 위험한 조합 | 이유 |
|---|---|
| 게임 규칙 변경 + 코드 구현 | 합의되지 않은 규칙이 구현으로 굳을 수 있음 |
| 네트워크 truth 변경 + UI 연출 | presentation이 authoritative 상태를 오염시킬 수 있음 |
| 카드 효과 추가 + 밸런스 수치 확정 | 효과 검증 전 수치가 확정값처럼 굳을 수 있음 |
| 맵 구조 변경 + 리스폰 변경 | 카메라, 구간 돌파, 카드 지급이 함께 흔들림 |
| 공용 프리팹 수정 + 여러 담당자 병렬 작업 | Unity merge 충돌과 책임 불명확성이 커짐 |

필요하면 기능 스펙, 작업 브리핑, 구현 작업, 검증 작업을 분리한다.

## 중단 조건

AI 또는 담당자는 아래 상황에서 임의로 계속 진행하지 않는다.

| 조건 | 처리 |
|---|---|
| 기준문서와 요구사항이 충돌 | BLOCKED로 보고하고 충돌 문서를 명시 |
| 담당 외 시스템 수정 필요 | 해당 담당자에게 확인 요청 |
| 공용 씬/프리팹 동시 수정 가능성 | 파일 소유권 확인 |
| secret/App ID/계정 정보 노출 가능성 | 문서와 코드에 직접 기록하지 않음 |
| P0 open/blocked 질문 발견 | 관련 구현 중단 |
| 수치 확정 요구가 기준문서로 들어옴 | GameplayProfile 또는 프리셋 후보로 분리 |
| local-only artifact가 공유 문서로 섞임 | 레포 밖 또는 local artifact 위치로 이동 |

> AI 세션 중단 트리거 시의 BLOCKED 태그 분류는 [05/01#blocked-태그-분류-정본](../05_문서관리_규칙/01_문서_상태와_변경_규칙.md#blocked-태그-분류-정본) 참조. 본 문서는 AI 세션 중단 트리거의 맥락만 다룬다.

단순 구현 디테일은 담당자가 가정을 명시하고 진행할 수 있다. 단, 그 가정은 결과 보고에 남긴다.

## 결과 보고 원칙

AI 작업 결과는 다음 사람이 바로 이어받을 수 있어야 한다.

| 항목 | 필수 내용 |
|---|---|
| 변경 요약 | 무엇이 바뀌었는지 |
| 변경 파일 | 주요 파일 또는 문서 |
| 기준문서 영향 | 어떤 규칙과 연결되는지 |
| 검증 결과 | 실행한 테스트, 수동 확인, 실패/미실행 이유 |
| 남은 리스크 | 아직 불확실한 점 |
| 다음 작업 | 이어서 해야 할 일 |
| 중단/가정 | 임의로 둔 가정과 확인 필요 항목 |

결과 보고는 장황한 작업 일지가 아니라, 다음 담당자와 다음 AI 세션이 복구할 수 있는 요약이어야 한다.

## 세션 리셋 복구 규칙

AI 세션이 리셋되면 새 세션은 아래 순서로 맥락을 복구한다.

| 순서 | 문서 | 목적 |
|---|---|---|
| 1 | `README.md` | 기준문서 구조와 우선순위 확인 |
| 2 | 담당 영역 기준문서 | 전투, 전장, 카드, 기술, UI 중 작업 범위 확인 |
| 3 | `90_백로그/04_미결정_질문_레지스터.md` | 닫힌 결정과 남은 질문 확인 |
| 4 | `05_문서관리_규칙/06_의사결정_로그.md` | 왜 그렇게 결정했는지 확인 |
| 5 | 작업 브리핑 또는 기능 스펙 | 이번 작업의 실제 범위 확인 |

세션 복구 중 기준문서와 작업 요청이 충돌하면 작업 요청보다 기준문서 상태값을 우선한다.

## 역할별 사용 방식

| 담당 유형 | AI 사용 기준 |
|---|---|
| 기획/전투 설계 | 규칙, 후보, 금지선, 미결정을 문서화한다 |
| 전투 구현 | 입력, 이동, 발사, 피격을 기준문서와 테스트로 검증한다 |
| 카드 구현 | 카드 지급, 후보 생성, 선택 확정을 기준문서와 분리하지 않는다 |
| 맵/아트/UI | gameplay truth와 presentation을 구분한다 |
| 네트워크/인프라 | StateAuthority, secret, 환경값, 배포 경계를 임의로 바꾸지 않는다 |

## 금지

- AI에게 “알아서 적당히 구현”하라고 맡기는 것.
- 기준문서에 없는 게임 규칙을 코드로 먼저 확정하는 것.
- 담당 외 공용 씬, 프리팹, 네트워크 설정을 확인 없이 수정하는 것.
- 수치값을 기준문서에 확정값처럼 기록하는 것.
- presentation-only 연출을 gameplay truth로 승격하는 것.
- AI 결과를 검증 없이 바로 팀 기준으로 공유하는 것.

## 팀 공유본 작성 기준

- 팀 공유본에서는 특정 AI 도구 사용을 강제하지 않는다.
- 공유본의 핵심은 도구명이 아니라 담당 범위, 기준문서 확인, 수정 가능 범위, 중단 조건, 검증 보고 형식이다.
- 각 담당자별 작업 브리핑 예시는 필요해지면 별도 문서로 만든다.
