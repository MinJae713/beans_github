# 기능 스펙 양식

이 문서는 기능 의도를 정리한 뒤 작업자에게 넘기기 위한 기능 단위 스펙 양식이다.

작업 브리핑이 실제 작업 조건을 정리하는 문서라면, 기능 스펙은 그 전에 기능의 목적, 플레이어 경험, 비범위를 잠그는 문서다.

기능 스펙은 모든 작업마다 작성하지 않는다. 게임 규칙, 전투 양상, 카드/무기 구조, 구간/구조물, UI 흐름, 네트워크 truth처럼 여러 담당자에게 영향을 주는 기능을 만들거나 바꿀 때 작성한다. 작은 버그 수정, 단순 문서 수정, 수치 프리셋 조정은 작업 브리핑만으로 진행할 수 있다.

## 사용 시점

- 새 전투 기능, 카드 기능, 무기 기능, UI 흐름을 만들기 전.
- 여러 사람이 같은 기능을 나눠 구현해야 할 때.
- 사람 또는 AI에게 구현을 맡기기 전에 게임 의도와 비범위를 고정해야 할 때.

## 작성 단위

기능 스펙은 "한 작업자가 독립적으로 구현하고 검증 가능한 기능"을 기준으로 쪼갠다.

너무 큰 기능은 스펙을 나눈다. 예를 들어 `카드 시스템 전체`보다 `패배자 카드 선택 UI`, `카드 효과 적용`, `카드 프리셋 저장`처럼 나누는 편이 좋다.

## 양식

```markdown
# 기능 스펙: <기능명>

## 메타
- DRI:
- 우선순위: Must / Should / Could
- 관련 기준문서:
- 관련 관찰지표:
- 관련 구간 패턴:
- 관련 카드 효과 분류:
- 관련 이슈:
- 예상 작업량:

## 목적
- 이 기능이 플레이어 경험에 필요한 이유:
- 이 기능이 해결하는 문제:

## 플레이어 경험
1. <단계>
2. <단계>
3. <단계>

## 수용 기준
- [ ] <기준>
- [ ] <기준>
- [ ] <기준>

## 구현 범위
- 포함:
- 제외:

## 기준문서 충돌 확인
- 게임 규칙 충돌:
- 기술 구조 충돌:
- 밸런스 철학 충돌:
- 관찰지표 충돌:
- 구간 패턴 충돌:
- 카드/무기 분류 충돌:
- 아트/UX 기준 충돌:

## 기술스택 준수 확인
- 목표 기술스택:
- 허용 API:
- 금지 API:
- 기존 구현과의 충돌 가능성:
- 충돌 시 처리 기준:

## 검증 방식
- EditMode:
- PlayMode:
- Manual Smoke:
- 빌드 확인:
- 테스트 결과 XML 또는 대체 증빙:
- 패키지/import warning 처리:

## 산출물 연결
- 생성/수정될 작업 브리핑:
- 관련 리스크 ID:
- 관련 플레이테스트 리포트:
- 관련 프리셋:
- 관련 미결정 질문 ID:

## Open Questions
- [ ] <질문>
```

## 작성 규칙

- 기능 스펙에는 플레이어가 체감해야 하는 결과를 먼저 쓴다.
- 체력, 피해량, 쿨타임 같은 수치는 확정값이 아니라 프리셋 또는 실험값으로 표기한다.
- 전투 결과를 판단하는 기능은 `관찰지표 정의`의 원인 분류와 연결한다.
- 구간 또는 구조물 기능은 `구간 패턴 카탈로그`의 패턴 목적과 금지선을 확인한다.
- 카드 또는 무기 기능은 `카드 효과 분류체계`의 효과 분류와 누적 방식을 확인한다.
- 수용 기준은 구현자가 통과/실패를 판단할 수 있는 문장으로 쓴다.
- "연결 가능한 상태", "자연스럽게 동작" 같은 표현은 체크 가능한 하위 기준으로 쪼갠다.
- 비범위를 반드시 적어 스코프 크리프를 막는다.

## 작업 전달 전 체크리스트

- [ ] 플레이어 경험이 구현 설명보다 먼저 적혀 있다.
- [ ] 포함 범위와 제외 범위가 분리되어 있다.
- [ ] 수용 기준이 통과/실패로 판정 가능하다.
- [ ] 관련 기준문서 충돌 여부를 확인했다.
- [ ] 관찰지표, 구간 패턴, 카드 효과 분류 중 해당되는 연결 항목을 적었다.
- [ ] accepted 기술스택과 충돌하는 API 사용 여부를 확인했다.
- [ ] 수치값은 프리셋 또는 실험값으로 분리했다.
- [ ] 작업자에게 넘길 작업 브리핑과 연결했다.
