# Jira Git 컨벤션

이 문서는 Colloseum 팀의 Jira/Git 컨벤션을 게임개발 기준문서 안에서 어떻게 적용할지 정리한다.

원문 컨벤션 전체를 복사하는 문서가 아니라, 게임개발 기준문서와 작업 브리핑에서 바로 참조해야 하는 운영 규칙만 요약한다.

## 원문 상태

| 원문 | 적용 상태 |
|---|---|
| Jira 컨벤션 | Colloseum 적용 가이드 v2.2 |
| Git 컨벤션 | v2.0 DRAFT, 팀 합의 전 |
| GitLab 원격 | `https://lab.ssafy.com/s14-final/S14P31A303` |
| 2026-04-20 로컬 관찰 | `origin/master`, `origin/develop` 존재. 현재 GitLab UI의 default/protected 설정 확인 전까지 후보 정보로만 사용 |
| 기준 Jira 프로젝트 | S14P31A303 |
| 이슈 키 | A303-{번호} |
| 스프린트 용량 | 5인 기준 35점 산정 |

Git 컨벤션은 원문 상태가 `DRAFT`이므로, 팀 합의 전까지 이 문서도 `candidate`로 둔다. 단, 작업 브리핑과 MR 설명을 정리할 때는 현재 임시 기준으로 사용할 수 있다. 실제 GitLab protected branch, default branch, MR approval 설정이 이 문서와 다르면 GitLab 설정과 담당자 지시를 우선한다.

담당자가 GitLab 설정을 확인하기 전에는 새 브랜치 생성, MR 대상 브랜치 확정, protected branch 직접 push를 하지 않는다. 브랜치/MR 정책은 문서보다 실제 GitLab 설정과 담당자 안내가 우선한다.

## 적용 범위

- Jira 이슈 제목, Component, Priority, DoD.
- Git 브랜치, 커밋 메시지, MR 제목과 리뷰 규칙.
- Unity 씬/프리팹/meta/LFS/NetworkObject 운영 금지선.
- Gate 플레이테스트와 빌드 태그 운영.
- 작업 브리핑에 넣어야 하는 Jira/Git 연결 정보.

이 문서는 게임 규칙, 밸런스 수치, 네트워크 truth 구조를 바꾸지 않는다.

## Jira 도메인 구분자

웹 프로젝트식 `[FE]`, `[BE]`, `[AI]` 구분자는 사용하지 않는다. Unity 게임 도메인 기준으로 아래 구분자를 쓴다.

| 구분자 | 역할 | Jira Component |
|---|---|---|
| [GAMEPLAY] | 게임 로직, 카드, 승리조건, 전투, 밸런스 | Gameplay |
| [NETWORK] | Photon Fusion, 동기화, 세션, 서버 권위 | Network |
| [PHYSICS] | 캐릭터 이동, 충돌, 점프, 물리 | Physics |
| [UI] | HUD, 메뉴, 카드 선택, 로비, 인게임 UI | UI |
| [ART] | 스프라이트, 애니메이션, VFX, 맵 비주얼 | Art |
| [AUDIO] | FMOD, SFX, BGM, 사운드 이벤트 | Audio |
| [INFRA] | CI/CD, 빌드, 프로젝트 설정, Git | Infra |
| [PLAN] | 기획, 설계, 문서, 플레이테스트, 발표 | 미지정 |

Epic은 구분자, Label, Component 없이 기능명만 사용한다.

## Jira Priority 기준

| 등급 | 기준 |
|---|---|
| High | 이번 스프린트에 반드시 완료해야 하거나, 없으면 다음 작업이 막힘 |
| Medium | 이번 스프린트에 완료하면 좋지만 데모 가능성은 유지됨 |
| Low | 다음 스프린트로 미뤄도 되며 여유가 있을 때 처리 |

우선순위 판단은 아래 순서로 한다.

1. 이게 없으면 다음 작업을 못 하는가?
2. 사용자 또는 플레이어에게 얼마나 중요한가?

의존성이 있으면 사용자 중요도와 관계없이 `High`로 본다.

## Git 브랜치 규칙

팀 Git Flow 후보는 아래 구조를 따른다. 현재 로컬 관찰 기준으로 기본 브랜치는 `master`, 통합 후보 브랜치는 `develop`이다. 단, GitLab UI에서 다른 default/protected 설정이 확인되면 그 설정을 우선한다.

```text
master
  - develop
    - feat/A303-45-card-system
    - fix/A303-78-respawn-bug
    - hotfix/A303-90-crash-fix
```

브랜치 네이밍:

```text
{타입}/A303-{이슈번호}-{간단한-설명}
```

예시:

```text
feat/A303-45-card-system
fix/A303-78-respawn-bug
hotfix/A303-90-crash-on-disconnect
art/A303-30-character-palette
```

Unity 단일 프로젝트이므로 `fe/`, `be/`, `ai/` 같은 파트 접두사는 쓰지 않는다.

## 기준문서 브랜치 전략

기준문서는 코드와 마찬가지로 기본 브랜치 또는 통합 브랜치에 직접 수정하지 않는다. 문서 변경은 별도 `docs/` 브랜치에서 작업하고 MR로 검토한다.

기본 브랜치 선택:

| 상황 | 기준 브랜치 |
|---|---|
| 구현 레포가 `develop`을 통합 브랜치로 쓰는 경우 | `develop` |
| 문서 전용 레포 또는 문서 전용 보호 브랜치가 있는 경우 | 팀이 정한 `docs` 또는 문서 기준 브랜치 |
| 팀 GitLab 설정이 아직 불명확한 경우 | 담당자 확인 전 기본 브랜치와 통합 브랜치 직접 수정 금지 |

문서 브랜치 네이밍:

```text
docs/A303-{이슈번호}-{도메인}-{기능}
docs/{도메인}-{기능}
```

예시:

```text
docs/A303-112-card-reward-rule
docs/A303-118-level-segment-guide
docs/card-weapon-catalog
docs/git-doc-branch-policy
```

Jira 이슈가 있으면 반드시 `A303-{번호}`를 포함한다. Jira 이슈 없이 빠른 문서 정리를 해야 하는 경우에만 `docs/{도메인}-{기능}` 형식을 임시로 허용한다.

사용자가 제안한 `doc/<도메인>/<기능>` 구조와 비교하면 방향은 같다. 다만 현재 팀 Git 규칙은 Jira 이슈 연결을 요구하므로 최종 권장형은 `docs/A303-{번호}-{도메인}-{기능}`이다. 슬래시를 여러 번 쓰는 `doc/card/reward` 형태는 GitLab UI에서 브랜치 그룹이 과하게 깊어질 수 있어 기본값으로 쓰지 않는다.

## 기준문서 MR 규칙

기준문서 MR은 “문장 수정”이 아니라 팀의 구현 기준 변경으로 취급한다.

| 변경 유형 | MR 필요 여부 | 리뷰 기준 |
|---|---|---|
| 오탈자, 깨진 링크, 표현 정리 | 필요 | 문서 소유자 또는 1명 리뷰 |
| 후보 카탈로그 추가 | 필요 | 해당 도메인 DRI 리뷰 |
| 게임 규칙 변경 | 필요 | 영향 영역 DRI 1명 이상 + 의사결정 로그 |
| 기술 구조 변경 | 필요 | 네트워크/인프라 DRI 리뷰 + 구현 영향 명시 |
| 수치 프리셋 변경 | 필요 | 플레이테스트 근거 또는 변경로그 |
| secret/개인 경로 제거 | 필요 | 즉시 수정 가능하나 MR에 제거 사실 명시 |

기준문서 MR 본문에는 아래 항목을 적는다.

```text
source_branch:
target_branch:
문서 변경 요약:
영향 도메인:
확정/임시/보류 상태:
관련 Jira:
관련 기준문서:
검토 요청자:
AI 검토 사용 여부:
남은 미결정:
```

다른 사람의 AI가 검토하는 구조는 허용한다. 단, AI 검토는 최종 승인자가 아니라 리뷰 보조 자료다. MR 병합 책임은 사람 담당자 또는 팀이 정한 통합 담당자가 가진다.

## 커밋 메시지 규칙

형식:

```text
[A303-{이슈번호}] {타입}: {제목}
```

타입:

| 타입 | 의미 |
|---|---|
| feat | 새로운 기능 |
| fix | 버그 수정 |
| refactor | 기능 변경 없는 구조 개선 |
| style | 포매팅, 네이밍 같은 스타일 정리 |
| docs | 문서 수정 |
| test | 테스트 추가/수정 |
| chore | 빌드, 설정, 에셋 관리 |
| art | 아트 에셋 추가/변경 |
| audio | 사운드/FMOD 관련 |
| hotfix | 긴급 수정 |

한 커밋은 하나의 논리적 변경만 담는다. 제목은 짧게 쓰고, 본문은 필요한 경우 “왜 바꿨는가”를 중심으로 적는다.

## MR 규칙

MR 제목:

```text
[A303-{이슈번호}] {타입}: {간단한 설명}
```

MR 방향과 승인:

| 방향 | 승인 | 기준 |
|---|---|---|
| feat/fix -> develop | 1명 이상 | 기능 통합. 팀 GitLab 설정 확인 후 사용 |
| develop -> master | 2명 이상 | 빌드 가능 상태 확인 필수. 팀 GitLab 설정 확인 후 사용 |

merge 방식은 `Merge commit`을 기본으로 한다. Unity 에셋 이력 추적을 위해 squash merge를 기본값으로 두지 않는다.

셀프 머지는 금지한다. 단, 긴급 hotfix는 예외가 가능하지만 사후 리뷰가 필요하다.

## MR 체크리스트

| 항목 | 기준 |
|---|---|
| 관련 이슈 | A303 이슈 번호가 제목, 브랜치, 커밋, MR에 연결됨 |
| 테스트 방법 | Unity Editor Play, 관련 씬 확인, 자동 테스트 여부 명시 |
| 씬/프리팹 충돌 | 동시 수정 금지 대상 변경 여부를 명시 |
| Debug.Log | 불필요한 로그 제거 또는 의도 명시 |
| meta 파일 | 누락/꼬임이 없는지 확인 |
| NetworkObject | 추가/삭제/설정 변경 시 MR 설명에 명시 |
| 리뷰 응답 | 리뷰 코멘트에 빠르게 응답 |

## DoD

개발 작업은 아래 조건을 만족해야 완료로 본다.

- 코드 또는 에셋이 정상 동작한다.
- MR을 올리고 최소 1명의 리뷰를 받았다.
- 리뷰 코멘트를 반영하고 MR이 머지되었다.
- 빌드가 깨지지 않는다.
- Story라면 인수 조건이 모두 충족되었다.
- 아트 에셋이라면 AD 승인을 받았다.

기획/설계 작업은 산출물이 Notion 또는 GitLab `docs/`에 작성되고, 팀원 공유와 피드백 반영이 완료되어야 완료로 본다.

## Gate 플레이테스트와 태그

- 마일스톤 Gate 통과 시 전원 플레이테스트를 기본으로 한다.
- Gate 플레이테스트는 Jira에 `[PLAN] Gate N 플레이테스트` Task로 등록한다.
- 플레이테스트 리포트는 기준문서의 플레이테스트 리포트 양식 또는 팀 `docs/templates` 양식을 따른다.
- 빌드 태그는 Gate 통과와 최종 빌드 시점에만 사용한다.

| 시점 | 태그 |
|---|---|
| Gate 1 통과 | gate-1 |
| Gate 2 통과 | gate-2 |
| Gate 3 통과 | gate-3 |
| 최종 빌드 | v1.0-demo |

## 게임개발 기준문서와의 연결

- 작업 브리핑에는 Jira 이슈, 도메인 구분자, Component, 브랜치 이름을 적는다.
- 기능 스펙은 Jira 이슈와 연결하되, 기준문서의 게임 규칙을 대체하지 않는다.
- `accepted` 기술 구조 기준과 Git 컨벤션이 충돌하면 기술 구조 기준을 우선한다.
- Git 컨벤션이 팀 합의 전이면 MR/브랜치 운영은 담당자 안내를 우선한다.
- Photon App ID, secret, 계정 정보는 기준문서, MR 본문, tracked 설정 파일에 실제 값으로 직접 적지 않는다.
