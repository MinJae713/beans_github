# 스모크테스트

이 문서는 기준문서 관점의 smoke gate다. 기존 구현 문서나 프로토타입 smoke 항목은 reference로만 사용하며, MVP 기준과 충돌하면 이 문서의 기준을 우선한다.

## 목적

기본 브랜치, 통합 브랜치, 또는 공유 빌드는 항상 한 판 플레이 가능해야 한다.

컴파일 성공만으로 완료로 보지 않는다. 플레이어 이동, 공격, 피격, 카드 선택, 리스폰, 구간 진행이 최소한 끊기지 않아야 한다.

## 검증 종류

| 종류 | 용도 |
|---|---|
| EditMode tests | 카드/수치/순수 규칙 검증 |
| PlayMode tests | Unity 런타임 상호작용 검증 |
| Manual smoke | 사람이 직접 한 판 흐름을 확인 |
| Standalone build smoke | 빌드 결과물이 에디터와 동일하게 동작하는지 확인 |

## 작업 유형별 최소 검증

| 작업 유형 | 최소 검증 |
|---|---|
| 전투/이동/피격 | PlayMode 또는 manual smoke + 이동/공격/사망 확인 |
| 카드/밸런스 | EditMode 또는 PlayMode + 스탯 적용과 수치 변경 요약 + 카드 효과 태그/계약 데이터 확인 |
| UI/VFX | manual smoke + 스크린샷/영상 + 입력 방해 여부 확인 + 판정 결과와 표현 결과 분리 확인 |
| 레벨/맵 | manual smoke + 리스폰/카메라/구간 돌파/낙사 확인 |
| 기술 구조 | 컴파일 + 관련 EditMode/PlayMode 또는 build smoke |
| Room Registry / Infra | Spring Boot 기동, Redis 연결, Worker Agent 연동, Room API CRUD smoke |
| 문서/기획 | 관련 기준문서 충돌 여부와 미결정 사항 표시 |

## Manual Smoke 최소 항목

아래 항목은 MVP 기준 최소 smoke다. legacy 구현 체크리스트가 별도로 있더라도, 대시/더블점프처럼 MVP 보류 항목을 필수 smoke로 끌어올리지 않는다. 현재 입력 행동 기준에는 MVP 기믹 행동으로 딱밤이 남아 있으나, SMK-04/05의 blocker 범위에 딱밤을 반드시 포함할지는 후속 결정이 필요하다. 결정 전까지는 기본 발사 검증을 우선하고, 딱밤은 별도 관찰 메모로 분리한다.

| ID | 확인 |
|---|---|
| SMK-01 | 런타임 부팅, 두 플레이어 표시 |
| SMK-02 | P1 이동/점프/기본 발판 이동 |
| SMK-03 | P2 이동/점프/기본 발판 이동 |
| SMK-04 | P1 발사 행동. 딱밤 기믹 행동은 후속 결정 전까지 별도 관찰 메모 |
| SMK-05 | P2 발사 행동. 딱밤 기믹 행동은 후속 결정 전까지 별도 관찰 메모 |
| SMK-06 | 피격/사망/리스폰 |
| SMK-07 | 카드 선택 UI 클릭과 적용 |
| SMK-08 | 구간(Segment) 전환 |
| SMK-09 | 승리 조건 |
| SMK-10 | HUD와 스크린샷 |
| SMK-11 | 리스폰 직후 1초 무적 프레임 확인: 리스폰 완료 후 1초 이내 피격 시 피해 무효 처리되는지 확인. 1초 경과 후 정상 피격되는지 확인. (D48) |

## Contracts/Presentation 확인

카드, 전투 판정, UI/VFX가 함께 바뀐 작업은 Manual Smoke 결과에 아래 내용을 함께 남긴다.

| 확인 항목 | 기준 |
|---|---|
| 사건 데이터 | 발사, 피격, 반사, 사망, 리스폰, 구간 돌파 중 변경 대상 사건의 payload가 식별자/위치/방향/결과/태그를 충분히 남기는가 |
| 카드 효과 태그 | 카드 효과가 presentation에서 식별 가능한 tag 또는 snapshot으로 노출되는가 |
| 표현 소비 | VFX/SFX/HUD/카메라 피드백이 판정 결과를 읽어 표현하며, 체력/탄약/승패를 직접 바꾸지 않는가 |
| 원인 분리 | 실패가 판정 로직 문제인지, 계약 데이터 부족인지, presentation 매핑 문제인지 분류되는가 |
| 증빙 | 영상/스크린샷만 남기지 않고 로그, 이벤트명, 관련 프리셋 또는 에셋명을 함께 적는가 |

## Room Registry / Localbuild / Remotebuild 확인

Spring Boot Room Registry, `infra/localbuild/`, 또는 `infra/remotebuild/` 구성이 바뀐 작업은 아래 항목을 함께 남긴다.

| 확인 항목 | 기준 |
|---|---|
| JAR 실행 또는 Docker Compose 기동 | `server` 단독 실행 또는 `infra/localbuild/docker-compose.yml`로 Redis + Spring Boot가 정상 기동하는가 |
| 원격 API 기동 | `infra/remotebuild/APIServer/` 자산으로 Spring Boot API 컨테이너가 정상 기동하고 Room API가 응답하는가 |
| 원격 Worker 기동 | `infra/remotebuild/WorkerServer/` 자산으로 Worker Agent 컨테이너가 정상 기동하고 Linux Dedicated build를 spawn할 수 있는가 |
| 원격 Onboarding 기동 | `infra/remotebuild/OnboardingPage/` 자산으로 Nginx 정적 페이지가 기동하고 `/downloads/Client.zip` 다운로드가 가능한가 |
| Redis 연결 | Spring Boot가 `REDIS_HOST`, `REDIS_PORT` 환경값 또는 기본값(`localhost`, `6379`)으로 Redis에 연결되는가 |
| 방 생성 | Worker Agent spawn 후 `POST /api/v1/rooms`가 성공하는가 |
| 방 목록 조회 | Find Room 진입 또는 Refresh 버튼으로 `GET /api/v1/rooms` 결과가 로비에 표시되는가 |
| 상태 변경 | `##STATUS`, `##PLAYERS` 마커가 `PATCH /api/v1/rooms`로 반영되는가 |
| 방 삭제 | GameServer 프로세스 종료 후 `DELETE /api/v1/rooms/{sessionName}`가 호출되어 목록에서 제거되는가 |
| 원격 주소 정렬 | Lobby의 `COLOSSEUM_WORKER_BASE_URL`, `COLOSSEUM_ROOM_API_BASE_URL` 값이 Worker/API EC2 실제 주소와 일치하는가 |

`infra/localbuild/` 또는 `infra/remotebuild/` 기반 smoke는 "컨테이너가 뜬다"만으로 통과로 보지 않는다. 최소한 Redis 연결 성공, Room API CRUD 1회, Worker spawn 1회, 원격 배포 작업이면 Onboarding 다운로드 1회를 확인해야 한다.

## QA R/A 증빙

Smoke 결과에는 QA 실행과 최종 승인을 분리해 남긴다.

| 항목 | 기준 |
|---|---|
| QA 실행자(R) | 김범승. smoke 실행, 실패 원인 분류, gate 통과 판정 초안을 남긴다 |
| QA 최종 승인자(A) | 유민재. 빌드/실행 환경과 최종 승인 여부를 확인한다 |
| 필수 증빙 | 실행 빌드 또는 커밋, 실행자, 승인자, 승인 여부, 실패 시 후속 이슈 또는 BLOCKED 사유 |

## 산출물 위치

raw 결과물은 레포에 직접 넣지 않는다.

```text
<local-artifacts-root>/<YYYYMMDD-HHMM>-<short-task>/
- logs/
- screenshots/
- traces/
- temp/
- notes.md
```

공유가 필요한 경우에만 `docs/`에 짧은 요약을 남긴다.

## 자동 테스트 증빙 규칙

Unity 배치 테스트는 프로세스 종료코드만으로 충분하지 않다. 가능한 경우 테스트 결과 XML과 로그를 함께 남긴다.

| 상황 | 처리 |
|---|---|
| XML 생성 성공 | XML 경로, 로그 경로, 프로세스 종료코드를 함께 기록 |
| XML 미생성 | 로그 경로, 종료코드, XML 미생성 사유를 기록 |
| 종료코드 0 + 경고 | 경고가 플레이/빌드 차단인지 판단해 계속/중단 기록 |
| 종료코드 비정상 | 실패로 기록하고 기본/통합 브랜치 병합 또는 accepted 승격 금지 |

`DirectoryNotFoundException`, package import warning, URP import warning처럼 환경 또는 패키지 문제로 보이는 로그가 있으면 아래 중 하나로 분류한다.

- `continue`: 테스트 대상 기능과 직접 관련 없고 플레이/빌드를 막지 않는 경고.
- `isolate`: 원인 분리는 필요하지만 이번 기능 검증은 독립적으로 가능한 경고.
- `blocked`: 패키지, 렌더 파이프라인, 입력, 물리 초기화 문제로 기능 검증 신뢰성이 깨지는 경고.

## 실패 처리

- smoke 실패 시 기본/통합 브랜치 병합 또는 accepted 승격을 하지 않는다.
- 실패 결과는 숨기지 않고 Handoff Summary의 `남은 리스크`에 기록한다.
- 실패가 게임 규칙, 아키텍처, 공유 에셋, 네트워크 구조 충돌 때문이면 `BLOCKED`로 보고한다.
- 단순 구현 디테일이면 가정을 명시하고 수정 또는 후속 작업으로 넘긴다.
