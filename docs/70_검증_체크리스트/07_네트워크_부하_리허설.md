# 네트워크 부하 리허설

이 문서는 여러 방, 여러 2인 매치, 관전/랭킹 확장 가능성을 검증하기 위한 네트워크 부하 리허설 기준이다.

CCU, 방 개수, tick rate, 패킷 크기, 메모리 사용량, 프레임 목표 같은 구체 수치는 이 문서에 고정하지 않는다. 실제 목표값은 Photon 플랜, 테스트 환경, 빌드 프리셋, 별도 부하 테스트 기록에서 관리한다.

## 목적

가장 큰 리스크는 “로컬에서는 재미있지만 다중 사용자 환경에서 감당되지 않는 구조”가 되는 것이다. 이 문서는 서버 운영 세부 구현서가 아니라, 그런 위험을 조기에 관찰하기 위한 리허설 기준이다.

| 목적 | 의미 |
|---|---|
| 부하 위험 조기 발견 | 여러 매치가 동시에 돌 때 병목을 확인 |
| truth 범위 검증 | Networked 상태와 local-only 연출 분리가 유지되는지 확인 |
| 관전 확장 대비 | 관전자 기능을 넣기 전 상태 전파 비용을 가늠 |
| 비용 예측 | Photon 플랜과 사용량 리스크를 실험으로 전환 |
| 구현 범위 조절 | 기능 추가 전 줄여야 할 네트워크 상태를 찾음 |

## 전제

- 첫 playable slice가 로컬 2인 또는 Fusion Host Mode 기준으로 통과된 뒤 실행한다.
- 입력/이동의 Fusion 전환 범위가 먼저 안정되어야 한다.
- 발사, 피격, 사망, 카드 선택이 모두 network truth로 완성되지 않았더라도, 현재 구현 범위 안에서 관찰 가능한 부하를 기록한다.
- Photon App ID, secret, 계정 정보는 문서에 적지 않는다.

## 리허설 범위

| 범위 | 확인 내용 |
|---|---|
| 단일 방 반복 | 한 매치가 오래 진행될 때 상태 누수나 로그 폭증이 있는가 |
| 다중 방 동시 실행 | 여러 2인 매치가 서로 영향을 주지 않는가 |
| 빠른 방 생성/종료 | 방 생성, 입장, 종료, 재입장 흐름이 안정적인가 |
| 관전 후보 | 관전자에게 보내야 할 상태와 숨겨야 할 상태가 분리되는가 |
| 로그/측정 | raw 로그와 요약 결과가 분리되어 저장되는가 |

## 관찰 지표

| 지표 | 관찰 질문 |
|---|---|
| 상태 동기화 | 위치, 입력, 발사, 사망 상태가 일관되게 보이는가 |
| 지연 체감 | 입력 지연이나 피격 지연이 전투 판단을 망치는가 |
| 대역폭 후보 | Networked 상태가 과도하게 늘어나고 있지 않은가 |
| CPU/프레임 후보 | 동시 매치 수 증가 시 전투 가독성이 무너지는가 |
| 로그 품질 | 문제 발생 시 어느 방/플레이어/상태인지 추적 가능한가 |
| 카드 선택 padding 충분성 | `serverAcceptPadding=0.3s`가 Photon KR 리전 p95 RTT 대비 충분한지 관찰. padding 내 도착률과 타임아웃 랜덤 확정 발생 빈도를 기록한다. (D46) |
| 끝자락 클릭 무효율 | `visibleDeadline` 직전(마지막 0.5s 이내) 클릭이 `hardDeadlineTick` 이내에 Host에 도착하는 비율을 측정한다. 무효율이 높으면 `serverAcceptPadding` 증가 또는 `visibleChoiceDuration` 조정을 검토한다. (D46) |
| Host-only clamp RTT 체감 | 이동 주도권 보유자의 "후진 금지" Host-only clamp 상태에서 원격 RTT 환경 시 rubber-banding 체감이 전투 판단을 흔드는가. 체감이 유의미하면 Q39 A2(양측 예측 clamp) 조건부 승격을 검토한다. (D43/Q39) |
| 카드 seed 일관성 | 양 클라이언트가 동일 `choice_seed`로 동일 후보 3장을 생성하는가. 재접속/늦은 join 시에도 `[Networked]` seed를 수신해 후보가 재구성되는가. (D46) |
| 동일 tick race 재현 | 플레이어 선택 tick과 타임아웃 tick이 동일하거나 인접할 때 `player_choice_wins` 규칙이 일관되게 재현되는가. 타임아웃 이벤트가 폐기되는지 확인한다. (D46) |
| 선택 이펙트 롤백 | Host reject 시 로컬 선택 이펙트(버튼 강조·사운드)가 롤백되고 재선택 UI가 복원되는가. (D46) |

이 문서는 목표 수치를 확정하지 않는다. 각 리허설은 당시 환경과 결과를 별도 리포트에 남긴다.

## 단계

| no | 단계 | 통과 기준 |
|---|---|---|
| 1 | 단일 방 안정성 | 한 매치의 입력/이동/종료 흐름이 반복 가능 |
| 2 | 다중 방 격리 | 방 사이 상태가 섞이지 않음 |
| 3 | 빠른 생성/종료 | 생성, 입장, 종료, 재입장 흐름이 깨지지 않음 |
| 4 | 관전 후보 점검 | 관전자에게 필요한 상태 범위를 설명 가능 |
| 5 | 병목 기록 | 병목 후보를 코드/프리셋/네트워크 상태로 분류 |
| 6 | WebGL 후보 리허설 | 2차 릴리스 전 WebSocket/WebGL 제약 확인 |

## WebGL 후보 리허설

WebGL은 1차 시연 목표가 아니라 2차 릴리스 후보로 검증한다.

| 항목 | 통과 기준 |
|---|---|
| WebSocket 접속 | WebGL 빌드가 Photon Cloud에 접속 가능 |
| 크로스플레이 | Standalone과 WebGL 클라이언트가 같은 매치를 볼 수 있음 |
| 탭 비활성화 | 브라우저 탭 비활성화 후 재접속/이탈 처리가 설명 가능 |
| Host 금지 | WebGL이 Host 역할을 맡지 않는 구조가 명확함 |
| Server Mode 선결 | WebGL 공식 지원 전에 Server Mode 안정화가 선행됨 |

## 부하 리허설에서 금지

- 부하 테스트 전에 네트워크 구조를 임의 최적화하는 것.
- presentation-only 연출을 network truth로 승격해 상태를 불필요하게 늘리는 것.
- raw 로그, 스크린샷, 영상 파일을 기준문서 디렉토리에 저장하는 것.
- Photon credential 또는 App ID를 문서에 적는 것.
- 통과 수치를 기준문서에 박고 모든 환경에 동일하게 적용하는 것.

## 산출물

리허설 후에는 아래 요약만 문서 또는 handoff로 남긴다.

| 항목 | 내용 |
|---|---|
| 테스트 환경 | Unity 버전, 빌드 방식, Photon 모드, 실행 장비 분류 |
| 실행 범위 | 단일 방, 다중 방, 생성/종료, 관전 후보 중 무엇을 했는가 |
| 관찰 결과 | 지연, 동기화 불일치, 로그, 병목 후보 |
| 판정 | Pass, Narrow, Blocked, Retest 중 하나 |
| 다음 조치 | 줄일 Networked 상태, 분리할 연출, 추가할 측정 |

raw 로그와 영상은 레포 밖 보관 위치 또는 팀이 합의한 테스트 산출물 정책을 따른다.
