# 문제정의 및 핵심 컨셉

## 1. 프로젝트 목표
- 학생이 `레시피 선행관계`와 `주문 마감 압박`을 코드로 처리하는 경험을 통해 위상정렬 기반 사고를 체감하게 만든다.
- 사람이 화면에서 직접 플레이하는 게임이 아니라, `내가 짠 로직이 주방을 어떻게 운영하는가`를 시뮬레이션으로 보는 경험을 만든다.

## 2. 장르 정의
- 실시간 조작형 요리 게임 아님
- 손재주 중심 게임 아님
- 정확한 정의:
  - `코드 설계형 시뮬레이션 게임`
  - `주방 운영 알고리즘 게임`
  - `위상정렬 기반 스케줄링 학습 게임`

## 3. 플레이어가 실제로 하는 일
- 학생은 매 틱 호출되는 `decide(state)` 함수를 작성한다.
- 함수는 현재 주방 상태를 보고 `지금 어떤 직원이 어떤 작업을 시작해야 하는가`를 반환한다.
- 시뮬레이터는 이 결정을 영업 시간 동안 반복 적용한다.
- 학생은 실행 후 리플레이와 로그를 보면서 로직을 개선한다.

## 4. 왜 음식 테마가 맞는가
- 음식은 선행조건을 자연스럽게 설명한다.
  - 채소 손질이 끝나야 샌드위치 조합 가능
  - 육수가 끓어야 우동 조리 가능
  - 패티와 빵이 준비돼야 버거 조합 가능
- 따라서 레시피를 DAG로 표현하는 데 무리가 없다.
- 또한 주문 도착과 손님 인내심은 시간 제약을 게임적으로 보여주기 좋다.

## 5. 위상정렬이 왜 핵심 기반인가
- 주문 하나의 레시피는 DAG다.
- 어떤 작업이 지금 가능한지는 선행 작업 완료 여부로 결정된다.
- 즉 학생 코드는 매 틱 `현재 진입 가능한 노드 집합`을 읽는 문제를 항상 마주한다.
- 후반에 공유 선행작업이 들어와도 여전히 그래프는 DAG이며, 위상정렬 기반 사고는 유지된다.

## 6. 스케줄링이 왜 같이 붙는가
- 실제 주방 운영에서는 가능한 작업이 하나만 열리지 않는다.
- 여러 주문이 동시에 존재하고, 작업 시간도 다르고, 손님의 마감시간도 다르다.
- 따라서 학생은 유효한 작업 중 `어떤 것을 먼저 처리할지` 판단해야 한다.
- 이 판단은 위상정렬을 깨지 않는 범위 안에서의 스케줄링이다.

## 7. 이 프로젝트의 핵심 문장
- `가능한 작업을 읽는 능력은 위상정렬이고, 그중 무엇을 먼저 처리할지 정하는 능력은 스케줄링이다.`

## 8. 사용자 경험 목표
- 학생이 한 판이 끝난 뒤 아래를 느껴야 한다.
  - `내 코드가 가능한 작업을 잘 읽었는가`
  - `급한 주문보다 더 중요한 공유 준비작업을 먼저 해야 했는가`
  - `이 정책은 특정 상황에서 왜 병목을 만들었는가`
  - `자료구조나 우선순위 로직을 바꾸면 더 좋아질 수 있겠구나`

## 9. 발표 시 설명 포인트
- 배틀싸피가 `이동과 탐색`이라면, 쿡싸피는 `순서와 시간`이다.
- 학생은 셰프를 직접 움직이지 않는다.
- 대신 `주방 정책 코드`를 짜고, 시뮬레이터가 이를 실행한다.
- 결과는 주문 성공률, 평균 지연, 리플레이 로그로 확인한다.

## 10. 현재 기획 결론
- 이 게임의 본질은 `조리 액션`이 아니라 `주방 정책 설계`다.
- 음식은 도메인이고, 핵심은 `DAG 기반 작업 선택 로직`이다.
