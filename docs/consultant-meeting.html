CookSSAFY

학생이 "주방 운영 전략"을 코드로 작성하면,
시뮬레이터가 그 전략대로 주방을 돌려보고 결과를 보여주는 알고리즘 학습 게임입니다.

배틀싸피가 "길 찾기"를 가르쳤다면, 쿡싸피는 "작업 순서 정하기"를 가르칩니다.

왜 이 프로젝트인가

배틀싸피

BFS/다익스트라 → 길 찾기 알고리즘을 게임으로 배움

쿡싸피

"어떤 요리 작업을 먼저 할까?"
작업 순서 결정 알고리즘을 게임으로 배움

"지금 할 수 있는 작업을 파악하는 능력, 그리고 그중 무엇을 먼저 처리할지 판단하는 능력을 기르는 게임입니다."
  • 요리에는 순서가 있습니다 (예: 채소 손질 → 조합 → 플레이팅). 이 순서를 지키면서 여러 주문을 효율적으로 처리하는 게 핵심입니다
  • 주문마다 마감 시간이 있어서, "어떤 주문을 먼저 처리할지" 판단이 중요합니다

학생이 하는 일

학생은 decide()라는 함수 하나만 작성합니다. 이 함수가 "지금 직원이 어떤 작업을 해야 하는지"를 결정하고, 시뮬레이터가 영업 시간 내내 이 함수를 반복 호출합니다.

지원 언어

Python을 기본으로 지원하고, Python 버전이 안정화되면 Java도 추가합니다.

# Python (기본) def decide(state): # 현재 주방 상태를 보고, # 직원이 할 다음 작업을 반환 ...
// Java (추후 지원) public static Assignment decide(state) { // 동일한 로직을 Java로 ... }

학생 경험 시나리오 — "민수의 여정"

SSAFY 교육생 민수가 처음 접속해서 챌린지 모드까지 도달하는 과정입니다.

Ch1. 첫 접속 가장 단순한 코드로 주문 1개 완료. "아, 코드가 주방을 돌리는 거구나""생각보다 간단하네?"
Ch2. 전략의 발견 주문 3개가 동시에 들어옴. 순서대로 하니까 느림 → 짧은 주문부터 하니까 확 빨라짐"전략을 바꿨더니 결과가 달라졌다!"
Ch3. 함정에 빠짐 "짧은 작업부터"가 오히려 느려지는 상황 발생. 주문 전체를 보는 전략이 더 나음"눈앞의 최선이 전체 최선은 아니구나"
Ch4. 마감의 압박 빨리 끝나는 주문만 했더니 급한 주문을 놓침. 마감 기준을 추가하니 전부 성공"마감을 고려해야 하는구나"
Ch5. 전체를 보는 눈 육수 한 번 끓이니 4개 주문이 동시에 진행 가능해짐. 내 주문만 보면 안 됨"한 작업이 전체 흐름을 바꿀 수 있구나"
챌린지. 종합 시험 Ch5 전략으로 제출했더니 Ch3에서 점수가 낮음 → 여러 기준을 합친 복합 전략으로 개선"하나의 코드로 모든 상황에 대응해야 하는구나"
리더보드 경쟁 1위와의 차이를 분석하고 전략을 미세 조정. Java로도 같은 전략을 옮겨봄

  • ☐ 5개 예시 전략의 결과가 검증 시뮬레이터와 정확히 일치한다
  • ☐ 잘못된 코드(무한루프, 금지된 기능 사용)를 자동으로 감지하고 안내한다

  • ☐ 통과/실패 여부가 점수와 메시지로 명확히 표시된다
  • ☐ 공유 작업이 여러 주문에 영향을 주는 장면이 시각적으로 강조된다
  • ☐ 학생용 가이드 문서 3종 완성 (시작 가이드, API 설명, 코드 템플릿)
  • ☐ Java 버전 코드 템플릿과 데이터 모델 제공

왜 브라우저에서 실행하는가?

학생이 아무것도 설치할 필요 없고, 위험한 코드도 자동 차단됩니다. 9개 후보 중 비교 후 선정. 서버 부하를 학생 브라우저로 분산하여 동시 접속에도 안정적입니다.

안전 장치 (샌드박스)

무한루프는 10초 후 자동 종료. 메모리 256MB 제한. 파일 접근이나 네트워크 사용은 원천 차단. Web Worker에서 격리 실행하여 UI 멈춤 방지.

Rate Limiting

유저당 제출 간격 10초. Redis 기반 Sliding Window. 무차별 제출 방지 + 서버 보호.

채점 큐

제출 즉시 응답(접수 확인) → Redis Queue에 적재 → Worker가 순차 채점 → 결과 비동기 반환. 피크 시에도 요청 유실 없음.

캐싱 전략

리더보드: Redis 캐시 10초 TTL. 챕터 데이터: 서버 시작 시 메모리 로드. Pyodide: 브라우저 Service Worker 캐싱 (첫 1회만 다운로드).
