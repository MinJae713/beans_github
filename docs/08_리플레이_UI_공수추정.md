## 1. 프로토타입 vs 프로덕션 — 구현 범위 비교

| 항목 | 프로토타입 (현재) | 프로덕션 (미구현) |
|------|-----------------|------------------|
| 트레이스 데이터 | JS 객체로 하드코딩 (30틱, 3주문) | 서버 WebSocket / REST JSON 스트리밍 |
| DAG 렌더링 | 수동 레이아웃 (메뉴별 x%,y% 고정) | 자동 Layered-DAG 레이아웃 (Sugiyama 알고리즘) |
| 주문 수 | 3개 고정 | N개 동적 (챕터에 따라 1~10개+) |
| 직원 수 | 1명 고정 | N명 동적 (Ch.7부터 복수 직원) |
| 반응형 | 미지원 (1280px 기준) | 태블릿(1024px) / 데스크탑(1440px) 대응 필요 |
| 접근성 | 없음 | ARIA 레이블, 키보드 완전 지원, 색각 이상 대응 |
| 실제 Python 트레이스 연동 | 없음 | 시뮬레이터 JSON 출력 → UI 파싱 |
| 에러 핸들링 | 없음 | 잘못된 트레이스 포맷, 네트워크 실패 처리 |
| 테스트 | 없음 | 컴포넌트 단위 테스트 + 플레이백 통합 테스트 |
| 다국어 / 국제화 | 한국어 하드코딩 | 불필요 (SSAFY 내부 툴, 한국어 고정) |
| 성능 최적화 | 없음 (30틱 수준) | 200틱 × N주문 × M직원 대응 (렌더링 최적화) |
| 저장 / 공유 | 없음 | 리플레이 URL 파라미터 또는 파일 다운로드 |

## 2. 컴포넌트별 복잡도 추정

| 컴포넌트 | 복잡도 | 근거 |
|---------|--------|------|
| **KPI 스트립** | 낮음 | 단순 숫자 바인딩. 상태 계산은 시뮬레이터 측에서 제공하면 표시만. |
| **주문 티켓 스트립** | 낮음 | 리스트 렌더링 + 인내심 바. 주문 수가 동적이면 overflow 스크롤 처리 추가. |
| **플레이백 컨트롤** | 낮음 | 버튼 + 인터벌 타이머 조합. 속도 전환 시 인터벌 재시작 처리만 주의. |
| **틱 로그** | 낮음 | 로그 라인 리스트 + 색상 분류. 200틱 이상이면 가상 스크롤 고려. |
| **직원 현황 패널** | 중간 | 복수 직원 시 카드 레이아웃 재계산. 작업 진행 바 애니메이션은 틱 기반 보간 필요. |
| **실패 원인 태그** | 중간 | 태그 분류 로직은 시뮬레이터가 제공해야 신뢰성 있음. UI는 단순하나 판정 기준 설계가 핵심. |
| **레시피 DAG (SVG)** | 높음 | 수동 레이아웃은 메뉴가 늘수록 유지 불가. Sugiyama/Dagre 자동 레이아웃 도입 필요. 노드 수, 에지 수, 공유 노드 표현, 애니메이션 모두 비선형적으로 복잡해짐. |
| **트레이스 로더** | 중간 | 시뮬레이터 JSON 스키마 확정 후 파서 구현. WebSocket 스트리밍이면 부분 업데이트 처리 추가. |
| **전체 상태 관리** | 중간 | 현재 틱, 선택 주문, 재생 상태를 동기화. 규모가 커지면 Zustand/Jotai 수준의 상태 관리 도입 가치 있음. |

## 3. 기술 스택 권장안 — 2인 SSAFY 팀 기준

### 권장: **React (Vite) + D3-dag 또는 Dagre + Zustand**

```
React 18 (Vite)
  ├── 컴포넌트: 함수형 + hooks (기존 팀 숙련도 활용)
  ├── 스타일링: CSS Modules 또는 Tailwind (빠른 스타일 반복)
  ├── DAG 렌더링: dagre-d3 또는 @dagrejs/dagre + 직접 SVG 렌더
  ├── 상태 관리: Zustand (경량, 보일러플레이트 없음)
  └── 빌드: Vite (HMR 속도, SSAFY 환경 호환)
```

**선택 근거:**

- SSAFY 교육과정 기준으로 팀원 대다수가 React에 익숙함. 학습 비용 최소화.
- Dagre는 계층형 DAG 자동 레이아웃을 제공하며 npm 패키지로 즉시 사용 가능. D3 풀셋보다 진입 장벽이 낮음.
- Zustand는 Redux 없이 전역 틱 상태 / 선택 주문을 깔끔하게 관리할 수 있음.
- 순수 Vanilla JS는 DAG 레이아웃 알고리즘, 컴포넌트 재사용, 상태 동기화를 직접 구현해야 해서 2인 팀에게 유지 비용이 큼.
- SolidJS / Svelte도 성능은 우수하지만 팀 전환 비용이 SSAFY 일정에 비해 크다.

### 차선: **순수 Vanilla JS + Dagre (npm 없이 CDN)**

데모/PoC 수준에서 계속 가져가야 한다면 Dagre CDN + SVG 직접 렌더로 프로토타입을 확장하는 것도 가능. 단, 컴포넌트 분리와 상태 관리가 수동으로 복잡해지므로 코드 2인 유지 기준 추천하지 않음.

## 4. FE 개발 상위 3대 리스크

### 리스크 1. DAG 레이아웃 자동화 — 예상 공수 폭발 가능
- **내용**: 메뉴 수가 늘면 수동 x%/y% 레이아웃은 유지 불가. Dagre 자동 레이아웃 도입 시 노드 크기, 에지 라우팅, 공유 노드 시각화(같은 노드가 두 주문 DAG에 동시 표시) 처리가 예상보다 복잡해질 수 있음.
- **완화책**: 초기부터 Dagre 기반으로 구현하고, 공유 노드는 "동일 노드 ID = 단일 SVG 노드" 규칙으로 설계. 메뉴 DAG 정의는 시뮬레이터와 동일 스키마 공유(JSON).

### 리스크 2. 시뮬레이터 트레이스 스키마 미확정으로 인한 FE-BE 재작업
- **내용**: 현재 프로토타입은 트레이스를 직접 모델링했음. 실제 Python 시뮬레이터 출력 포맷이 확정되지 않으면 FE 파서를 두 번 짜야 할 수 있음.
- **완화책**: 시뮬레이터 구현 전에 트레이스 JSON 스키마를 먼저 합의 (node_status, active_tasks, log_lines 필드). FE는 mock JSON으로 개발 후 실 연결.

### 리스크 3. 플레이백 타이밍과 UI 동기화 — 틱이 빠르면 렌더 누락
- **내용**: 5× 속도(200ms/틱)에서 React 재렌더가 밀리면 KPI / DAG / 로그가 틱을 건너뛸 수 있음. requestAnimationFrame과 setInterval 충돌.
- **완화책**: 플레이백 루프를 별도 tick-engine으로 분리하고, UI는 tick-engine이 emit하는 이벤트에 구독하는 구조로 설계. 고속 재생 시 중간 틱은 log만 누적하고 렌더는 마지막 틱만 수행하는 "batch-render" 옵션 제공.

## 5. 개발 공수 요약 (2인, React 기준)

| 구간 | 내용 | 예상 일수 |
|------|------|-----------|
| 환경 셋업 + 스키마 합의 | Vite 초기화, 트레이스 JSON 스키마 확정 | 1일 |
| 기본 레이아웃 + KPI + 티켓 | 상단 UI 구현 | 1일 |
| DAG 컴포넌트 (Dagre) | 자동 레이아웃 + 노드 상태 렌더 | 2~3일 |
| 플레이백 엔진 | 틱 루프 + 컨트롤 UI | 1일 |
| 트레이스 로더 (JSON 파싱) | 시뮬레이터 연결 | 1~2일 |
| 직원 + 실패 태그 패널 | 동적 직원 수 대응 포함 | 1일 |
| 반응형 + 접근성 기본 | 1024~1440px, ARIA | 1~2일 |
| 버그 수정 + 통합 테스트 | | 2일 |
| **합계** | | **10~13일** |

> 2인이 병렬로 진행 시(DAG 담당 / 나머지 UI 담당) 실질 캘린더 일수는 7~9일 수준.
