# 작업 속도와 검토 리듬

이 문서는 Colosseum 개발에서 문서, 구현, 검토를 어떤 속도로 돌릴지 정한다.

목적은 모든 기준을 한 번에 완성하려는 병목을 줄이고, 게임 개발에 맞게 빠른 프로토타입과 반복 검증을 우선하는 것이다.

## 기본 판단

지금 단계에서는 `하나씩 완성한 뒤 다음 단계로 이동`보다 `빠른 전체 골격 작성 후 반복 검토`가 더 적합하다.

게임 개발은 일반 서비스 개발보다 초기에 불확실성이 크다. 특히 조작감, 타격감, 카드 재미, 전장 압박은 문서만으로 검증되지 않는다. 따라서 기준문서는 구현을 막지 않을 정도의 금지선과 판단축을 먼저 제공하고, 재미와 수치는 프로토타입과 플레이테스트로 확인한다.

## 일반적인 게임 개발 리듬

게임 개발팀은 보통 아래 흐름으로 움직인다.

1. 핵심 재미 가설을 짧게 정의한다.
2. 가장 작은 playable slice를 빠르게 만든다.
3. 직접 플레이하면서 재미, 혼란, 불공정, 기술 리스크를 찾는다.
4. 살아남은 아이디어만 문서와 구현 기준으로 승격한다.
5. 재미가 약하거나 구현비가 큰 아이디어는 과감히 보류한다.

즉, 초반에는 완벽한 설계서보다 `검증 가능한 플레이 상태`가 더 중요하다. 다만 네트워크 권위, 상태머신, 씬/프리팹 소유권처럼 나중에 되돌리기 어려운 구조는 초반부터 엄격하게 관리한다.

## 빠르게 진행할 영역

아래 영역은 초안을 빠르게 만들고, 실제 플레이 결과를 보고 고친다.

| 영역 | 이유 | 허용되는 방식 |
|---|---|---|
| 카드 후보 | 재미와 상성은 플레이 전까지 확정하기 어렵다 | candidate 카탈로그로 넓게 작성 |
| 무기 감각 | 수치보다 손맛 검증이 먼저다 | 임시 프리셋으로 실험 |
| 전장 구간 패턴 | 실제 카메라/이동감에 따라 달라진다 | 테스트 구간을 여러 개 만든 뒤 선별 |
| 구조물 기믹 | 읽힘, 대응 가능성, 억울함을 플레이로 확인해야 한다 | 낙사/추처럼 단순한 후보부터 실험 |
| VFX/UI 톤 | 설명 가능성과 체감 품질을 보며 다듬는다 | 빠른 목업 후 교체 |
| 밸런스 수치 | 초반 수치는 거의 반드시 바뀐다 | GameplayProfile/프리셋으로 분리 |

이 영역의 문서는 `accepted`를 서두르지 않는다. 구현자가 참조할 수 있는 후보와 검증 질문을 제공하는 것이 우선이다.

## 천천히 잠글 영역

아래 영역은 잘못 정하면 구현 충돌이나 대규모 재작업이 생기므로 느리더라도 엄격하게 잠근다.

| 영역 | 엄격해야 하는 이유 | 기준 |
|---|---|---|
| Unity/Fusion 기술스택 | 물리/네트워크 전제가 바뀌면 전체 구현이 흔들린다 | accepted 문서 우선 |
| 라운드 상태머신 | 사망, 돌파, 카드, 리스폰이 모두 연결된다 | 상태 전이는 단일 기준 필요 |
| 네트워크 truth | 클라/호스트 판단이 섞이면 디싱크가 난다 | StateAuthority 기준 명시 |
| 카드 선택 핸드셰이크 | UI 직접 적용은 온라인에서 깨질 수 있다 | 요청, 검증, 확정 분리 |
| 씬/프리팹 소유권 | Unity 에셋 충돌은 병합 비용이 크다 | 파일 락과 담당자 명시 |
| secret/환경값 | 노출되면 회수 비용이 크다 | 문서/소스 직접 기입 금지 |

이 영역은 느리게 가더라도 기준문서의 품질을 우선한다.

## 권장 작업 비율

현재 단계의 권장 비율은 아래와 같다.

| 작업 종류 | 비율 | 설명 |
|---|---:|---|
| 빠른 후보 작성과 구현 실험 | 60% | playable slice와 후보군을 빠르게 늘린다 |
| 플레이테스트와 관찰 기록 | 20% | 재미와 문제를 직접 확인한다 |
| 기준문서 정리와 승격 | 20% | 실제로 필요한 기준만 accepted 후보로 올린다 |

문서 완성도가 떨어지면 구현이 흔들리지만, 문서 완성만으로는 게임의 재미가 검증되지 않는다. 따라서 `문서 100% 후 구현`이 아니라 `얇은 기준문서 + 빠른 구현 + 반복 검토`로 운영한다.

## 문서 작성 모드

문서는 두 가지 모드로 나눈다.

| 모드 | 목적 | 완료 기준 |
|---|---|---|
| 빠른 후보 모드 | 넓은 범위의 아이디어와 선택지를 놓치지 않는다 | 충돌 금지선, 미결정 질문, 다음 검증 방법이 있다 |
| 경화 모드 | 구현자가 그대로 따라도 되는 기준으로 잠근다 | accepted 승격 조건과 검증 근거가 있다 |

`빠른 후보 모드` 문서는 불완전해도 된다. 대신 확정된 것처럼 쓰면 안 된다.

`경화 모드` 문서는 느려도 된다. 대신 구현자가 읽고 바로 작업할 수 있어야 한다.

## 플레이 가능한 슬라이스 우선순위

문서 작업이 구현을 과하게 늦춘다고 판단되면 아래 순서로 우선순위를 둔다.

1. 두 플레이어가 움직이고 공격한다.
2. 피격, 사망, 돌파, 리스폰이 한 루프로 이어진다.
3. 구간 돌파 패배자/방어자가 카드 선택으로 다음 전투를 바꾼다.
4. 카드 선택이 네트워크에서 요청, 검증, 확정으로 처리된다.
5. 구간 진행과 최종 승리가 설명 가능하게 보인다.
6. 플레이테스트 로그로 문제를 재현할 수 있다.

이 순서와 직접 연결되지 않는 문서는 백로그로 미룰 수 있다.

## 회의와 문서 반영 방식

회의에서 나온 내용은 즉시 모든 기준문서에 완벽히 반영하지 않는다.

| 회의 결과 | 처리 |
|---|---|
| 바로 구현이 필요한 결정 | 관련 기준문서와 의사결정 로그에 반영 |
| 재미 검증이 필요한 아이디어 | candidate 문서 또는 백로그에 추가 |
| 수치 조정 | GameplayProfile/프리셋 또는 플레이테스트 기록으로 이동 |
| 충돌 가능성이 있는 결정 | 미결정 질문 레지스터에 등록 |
| 폐기된 아이디어 | 아카이브 또는 백로그 보류로 이동 |

## 현재 적용 결론

현재 기준문서 작업은 완성도보다 속도를 더 높여도 된다.

다만 아래는 계속 엄격하게 본다.

- Unity/Fusion 2D 기술스택.
- 라운드 상태머신.
- 카드 선택 네트워크 흐름.
- 씬/프리팹 소유권.
- secret/개인 경로 차단.
- 기준문서와 수치 프리셋 분리.

나머지 카드 목록, 무기 후보, 구조물 후보, UI/VFX 후보는 빠르게 작성하고 전체 검토로 정리한다.
