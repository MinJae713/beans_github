# 리스크 로그 운영

이 문서는 Colloseum 개발 중 발견되는 리스크를 어떻게 기록하고 추적할지 정의한다.

리스크 로그는 문제를 과장하기 위한 문서가 아니라, 기획자와 구현자가 같은 우선순위로 위험을 보는 장치다.

## 기록 대상

아래 항목은 리스크 로그에 남긴다.

- 일정 안에 해결되지 않으면 기능 범위를 줄여야 하는 리스크.
- 네트워크, 물리, 공용 씬, 프리팹, 에셋 파이프라인처럼 되돌리기 어려운 리스크.
- 특정 팀원에게 작업이 과도하게 몰리는 리스크.
- 재미 검증, 카드 밸런스, 매치 템포처럼 플레이테스트 전에는 확신할 수 없는 리스크.

아래 항목은 리스크 로그 대신 작업 기록으로 충분하다.

- 단순 버그.
- 하루 안에 해결 가능한 구현 디테일.
- 프리셋 값 조정만으로 해결 가능한 P2 튜닝.

## 기본 양식

| ID | 리스크 | 확률 | 영향 | 오너 | 완화책 | 검증 방법 | 상태 |
|----|--------|------|------|------|--------|-----------|------|
| R-000 | | 낮음/중간/높음 | 낮음/중간/높음 | | | | Open |

`검증 방법`에는 리스크를 닫기 위해 필요한 확인 방법을 적는다. 예를 들어 플레이테스트, 빌드 실행, 네트워크 동기화 확인, 에셋 통합 테스트처럼 관찰 가능한 방법이어야 한다.

## 상태

| 상태 | 의미 |
|---|---|
| Open | 아직 관리 중인 리스크 |
| Mitigating | 완화 작업이 진행 중인 리스크 |
| Resolved | 완화 완료 또는 더 이상 문제가 아닌 리스크 |
| Accepted | 위험을 인지하고 스코프/품질/일정상 감수하기로 한 리스크 |

## 운영 규칙

- P0/P1 결정과 연결되는 리스크는 결정 기록과 함께 남긴다.
- 수치가 필요한 리스크는 기준문서에 수치를 고정하지 않고, 플레이테스트 리포트 또는 밸런스 프리셋과 연결한다.
- 리스크가 실제 구현 블로커가 되면 작업 브리핑의 `남은 리스크`에 같은 ID로 적는다.
- 리스크 해소 여부는 말로만 닫지 않고 검증 방법을 함께 기록한다.

## 갱신 규칙

- 새 기능 스펙을 작성할 때 관련 리스크가 있으면 ID를 붙인다.
- 스프린트 리뷰 때 Open 또는 Mitigating 리스크만 훑고, Resolved 리스크는 다시 열 필요가 있을 때만 본다.
- 같은 리스크가 반복해서 작업을 막으면 단순 리스크가 아니라 P0/P1 결정 안건으로 올린다.
- 오너가 비어 있는 리스크는 관리 중인 리스크로 보지 않는다.

## 완료 판정

리스크 기록은 아래 조건을 만족하면 관리 가능한 상태로 본다.

- 리스크 문장이 구체적인 실패 상황을 설명한다.
- 확률과 영향이 모두 적혀 있다.
- 오너와 완화책이 적혀 있다.
- 닫을 때 필요한 검증 방법이 적혀 있다.
- 관련 기능 스펙, 플레이테스트, 스프린트 리뷰 중 하나 이상과 연결되어 있다.
