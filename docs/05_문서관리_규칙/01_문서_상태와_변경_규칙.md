> **정본 · 요약과 충돌 시 본 문서 우선 (SOT)**

> 이 문서는 문서 상태 정의 + BLOCKED 태그 분류의 정본이다. README·05/08의 상태 표는 요약이며, 충돌 시 본 문서가 우선한다.

# 문서 상태와 변경 규칙

이 문서는 `docs/` 아래 문서들이 어떤 상태로 관리되고, 어떤 절차로 변경되는지 정의한다.

목적은 기획자, 구현자, AI 작업자가 같은 기준을 보고 작업하되, 아직 합의되지 않은 초안을 확정 규칙처럼 오용하지 않게 하는 것이다.

이 문서는 팀 공유 기준문서 기준으로 정제된 문서다. 개인 PC 경로, 세션 운영 맥락, secret, raw artifact 위치는 현재 SOT에 포함하지 않는다.

## 상태 정의

| 상태 | 의미 |
|---|---|
| governance | 문서 루트, 우선순위, 변경 절차, 의사결정 로그처럼 SOT 사용법을 정의 |
| accepted | 프로젝트 내부 합의 후 현재 구현 기준으로 사용하는 문서 |
| accepted_candidate | 최종 확정 전이지만, `08_문서_상태_인덱스.md` 또는 작업 브리핑에 명시된 binding 범위 안에서는 임시 구현 기준으로 사용할 수 있는 문서 |
| candidate | 초안 또는 검토 중인 기준 후보. 작업 참고는 가능하나 확정 아님 |
| reference | 배경, source, handoff. 현재 구현 기준을 대체하지 않음 |
| backlog | 후순위 작업, 미결정 질문, 제안. 구현 지시가 아님 |
| archive | 폐기, 대체, 기록 보존 목적의 문서. 현재 작업 기준으로 사용 금지 |

`deprecated`와 `archived` 같은 과거 표현은 현재 canonical status가 아니다. 과거 문서에서 발견되면 `reference`, `backlog`, `archive` 중 하나로 재분류한다.

## 상태별 적용 범위

| 상태 | 작업자에게 적용되는 취급 |
|---|---|
| governance | 문서를 어떻게 읽고 바꿀지 정의. 구현 규칙 자체보다 우선하여 상태 해석을 제공 |
| accepted | 우선 준수. 게임 규칙/아키텍처 충돌이면 임의 변경 금지 |
| accepted_candidate | 명시된 binding 범위에서 임시 구현 기준으로 사용 가능. 코드/에셋 수정은 별도 작업 브리핑 필요 |
| candidate | 참고 가능. 구현 영향 또는 accepted 충돌 가능성이 있으면 승인 증거 없이는 BLOCKED |
| reference | 배경 근거로만 사용. 현재 구현 판단 근거로 우선하지 않음 |
| backlog | 후순위 검토 또는 미결정 질문. 구현 지시로 사용 금지 |
| archive | 참고만 가능. 새 작업의 기준으로 인용 금지 |

상태 해석과 문서별 현재 상태의 단일 인덱스는 `08_문서_상태_인덱스.md`다. README와 이 문서는 상태 체계를 설명하지만, 문서별 상태 판단은 `08_문서_상태_인덱스.md`를 우선한다.

구현 규칙의 적용 우선순위는 `accepted > 08_문서_상태_인덱스 또는 작업 브리핑에 명시된 accepted_candidate > candidate 참고 후보 > reference > backlog > archive > 회의 원문/개인 메모`다.

SOT 충돌이 있을 때는 아래 표를 따른다.

| 우선순위 | source | 사용 범위 | 충돌 시 처리 |
|---|---|---|---|
| 1 | `accepted` 문서 | 현재 구현 기준 | 다른 source가 다르면 `accepted` 우선. accepted끼리 충돌하면 `BLOCKED` |
| 2 | `08_문서_상태_인덱스.md` | 문서별 상태와 binding 범위 | README, 개별 배너, 의사결정 로그와 상태 메타데이터가 다르면 상태 인덱스 우선. accepted 본문 내용 충돌은 상태 인덱스만으로 해소 불가 |
| 3 | 상태 인덱스 등재형 `accepted_candidate` | 명시된 binding 범위 안의 임시 기준 | accepted와 충돌하거나 범위를 넓히면 `BLOCKED` 또는 작업 브리핑 승인형으로 전환 |
| 4 | 작업 브리핑 승인형 `accepted_candidate` | 이번 작업 범위 안의 임시 기준 | 승인 증거, 중단 조건, 재검토 시점이 없으면 `BLOCKED` |
| 5 | Jira 이슈 또는 작업 브리핑 | 작업 범위, 파일 권한, 검증 기준 | 기준문서보다 우선하지 않음. 기준문서와 충돌하면 `BLOCKED` |
| 6 | `candidate` 문서 | 배경 참고 또는 승인된 예외 구현 근거 | 승인 증거 없이 구현 근거로 사용 금지 |
| 7 | Figma Board | 화면 흐름, 정보 배치, UI 참조 | gameplay truth, network truth, 기술스택을 덮어쓰지 않음 |
| 8 | 의사결정 로그 | 근거와 변경 이력 | accepted 본문 내용과 충돌하면 해당 accepted 기준문서 본문에 반영되기 전까지 실행 기준 아님 |
| 9 | `reference`, `backlog`, `archive`, 회의 원문 | 배경, 후순위, 기록 | 구현 권한을 만들지 않음 |

의사결정 로그는 근거와 변경 이력을 설명하는 governance 문서다. 의사결정 로그와 `accepted` 문서가 충돌하면 `accepted` 문서를 우선하고, 해당 작업은 `BLOCKED`로 보고한다. 최신 결정이 accepted 본문 내용을 바꿔야 한다면 해당 accepted 기준문서 본문이 먼저 갱신되어야 한다. `08_문서_상태_인덱스.md`는 상태와 binding 범위를 맞추는 메타데이터이며, accepted 본문 충돌을 단독으로 해소하지 않는다.

문서 상태 메타데이터가 충돌하면 `08_문서_상태_인덱스.md`를 우선한다. README, 개별 문서 상태 배너, 의사결정 로그가 상태 인덱스와 다르면 구현하지 말고 `BLOCKED`로 보고한다.

## Proceed / BLOCKED 결정표

| 근거 | 진행 조건 | BLOCKED 조건 |
|---|---|---|
| `accepted` 문서 | 작업 브리핑 또는 Jira 이슈가 있고, 작업 내용이 accepted 문서와 충돌하지 않음 | accepted 문서끼리 충돌하거나 구현 목표가 accepted 문서를 바꿔야 함 |
| 상태 인덱스의 `accepted_candidate` | 상태 인덱스에 등재되어 있고, 작업 브리핑에 binding 범위, 가정, 중단 조건, 재검토 시점, SOT 충돌 확인 결과가 있음 | accepted 문서와 충돌하거나 브리핑에 중단 조건 또는 SOT 충돌 확인 결과가 없음 |
| 작업 브리핑 기반 `accepted_candidate` | 승인자/승인 증거/Jira 또는 MR 링크가 있고, 승인 범위가 이번 작업으로 제한되며 SOT 충돌 확인 결과가 있음 | 승인자, 승인 증거, 승인 범위, 재검토 시점, SOT 충돌 확인 결과 중 하나라도 없음 |
| plain `candidate` 예외 | 해당 영역 담당자 또는 팀 회의 결정이 작업 브리핑에 증거로 남음 | 승인 증거가 없거나 후보 문서가 accepted 문서를 바꾸려 함 |
| `reference`, `backlog`, `archive`, legacy/raw notes | 현재 구현 기준으로 사용하지 않음 | 이를 근거로 코드, 에셋, 공용 프리팹, 네트워크 설정을 바꿔야 함 |

`accepted_candidate`는 두 종류로만 인정한다.

| 종류 | 승인 판단 | 작업 브리핑 필수 항목 |
|---|---|---|
| 상태 인덱스 등재형 | `08_문서_상태_인덱스.md` 자체가 승인 근거다. 별도 승인자/증거는 요구하지 않는다 | 참조 문서, 상태 인덱스 항목, binding 범위, 임시 가정, 충돌 시 중단 조건, 재검토 시점, SOT 충돌 확인 결과 |
| 작업 브리핑 승인형 | 상태 인덱스에 없는 임시 binding이다. 명시 승인자와 승인 증거가 필요하다 | 참조 문서, 승인자/승인 출처, 승인 증거 위치, 승인 범위, 임시 가정, 충돌 시 중단 조건, 재검토 시점, SOT 충돌 확인 결과 |

상태 인덱스 등재형 `accepted_candidate`의 binding 범위를 넓히거나 accepted 문서와 충돌할 가능성이 있으면 더 이상 상태 인덱스 등재형으로 처리하지 않는다. 이 경우 작업 브리핑 승인형 절차를 따르거나 `BLOCKED`로 보고한다.

작업 브리핑 기반 `accepted_candidate`를 구현에 사용할 때는 작업 브리핑에 아래 항목을 적는다.

- 참조한 문서 경로.
- 임시 가정 문장.
- 충돌 시 중단 조건.
- 해당 가정을 다시 검토할 시점.
- 승인자 또는 승인 출처.
- 승인 증거 위치. Jira 이슈, MR 본문, 회의 메모, Mattermost 결정 캡처 등.
- SOT 충돌 확인 결과와 확인자.

plain `candidate` 문서만 근거로 구현해야 한다면 문서 소유자 또는 해당 영역 소유자의 한시 승인이 필요하다. 승인자는 작업 브리핑에 실명, 역할, Jira 담당자, MR 리뷰어, 회의 결정 중 하나로 명시해야 한다. 승인자가 불명확하면 구현하지 않고 `BLOCKED`로 보고한다. `candidate`의 내용이 accepted 문서와 충돌하거나 게임 규칙/기술 truth를 바꿀 가능성이 있으면 가정만으로 진행할 수 없고, 승인 증거가 없으면 반드시 `BLOCKED`다.

한시 승인은 작업 브리핑에 기록하고, 작업 종료 후 의사결정 로그 또는 미결정 질문 레지스터에 정리한다. 승인 증거가 없으면 해당 `candidate`는 구현 기준이 아니라 참고 자료로만 취급한다.

승인 권한은 아래 순서로 판정한다.

| 경우 | 승인 권한 | 승인 증거 |
|---|---|---|
| 상태 인덱스에 이미 `accepted_candidate`로 등재된 문서 | `08_문서_상태_인덱스.md` 자체 | 작업 브리핑에 참조 문서, 임시 가정, 중단 조건, 재검토 시점 기록 |
| 작업 브리핑에서 새로 `accepted_candidate` 가정을 적용해야 하는 경우 | 문서 반영 책임자, 해당 영역 담당자, Jira 담당자와 MR 리뷰어, 또는 팀 회의 결정 중 하나 | Jira 이슈, MR 본문, 회의 메모, Mattermost 결정 캡처 중 하나 |
| plain `candidate` 문서를 구현 근거로 쓰는 예외 | 해당 영역 담당자 또는 팀 회의 결정 | 작업 브리핑의 승인자/승인 출처와 승인 증거 위치 |
| 승인자 또는 증거가 불명확한 경우 | 없음 | `BLOCKED`로 보고하고 구현하지 않음 |

승인 권한은 역할명만으로 추측하지 않는다. 작업 브리핑에 승인자, 역할 또는 근거, 승인 증거 위치를 직접 적은 기록이 권한 판정의 기준이다. 역할/소유권 문서는 승인자를 찾기 위한 참고 자료일 수 있지만, 작업 브리핑에 승인자와 증거가 없으면 승인된 것으로 보지 않는다.

작업 브리핑의 작성·보관·종료 책임은 아래와 같다.

| 항목 | 기준 |
|---|---|
| 브리핑 작성자 | Jira 담당자, 작업 요청자, 또는 MR 작성자 |
| 보관 위치 | Jira 이슈, MR 본문, 또는 팀이 합의한 작업 브리핑 문서 |
| 병합 전 확인자 | MR 리뷰어. MR이 없으면 작업 요청자가 확인 |
| merge-stop 조건 | 승인 증거, 충돌 중단 조건, 재검토 시점 중 하나라도 없으면 병합 또는 handoff 중단 |
| 종료 정리 | MR 병합 전 의사결정 로그, 상태 인덱스, 미결정 질문 레지스터 중 하나에 유지/폐기/후속 검토 결과 기록 |

`candidate` 또는 작업 브리핑 기반 `accepted_candidate`를 사용한 MR은 승인 증거 위치를 MR 본문에 남긴다. 승인 증거가 없거나 충돌 중단 조건이 빠져 있으면 병합 전 검토에서 중단한다. MR 없이 작업이 끝나는 경우에도 handoff summary에 같은 증거를 남기고, 다음 작업자가 확인할 수 없으면 `BLOCKED`로 취급한다.

MR 또는 handoff에는 아래 체크리스트가 있어야 한다.

| 체크 항목 | 필수 여부 |
|---|---|
| 승인자/승인 출처 | 필수 |
| 승인 증거 위치 | 필수 |
| 참조한 문서 상태 | 필수 |
| 충돌 중단 조건 | 필수 |
| 재검토 또는 cleanup 시점 | 필수 |
| SOT 충돌 확인 결과 | 필수 |
| SOT 충돌 확인자 | 필수 |
| 확인한 리뷰어 또는 작업 요청자 | 필수 |

문서별 현재 상태와 binding 범위는 `08_문서_상태_인덱스.md`를 단일 인덱스로 본다.

## 문서 업로드 / Push 게이트

팀 공유 기준문서를 GitLab 또는 팀 공유 위치에 반영하기 전에는 아래 게이트를 통과해야 한다.

| 리뷰 verdict | 업로드/Push 허용 | 필수 조치 | 승인/확인 주체 | 증거 위치 |
|---|---|---|---|---|
| PASS | 허용 | 변경 파일과 검증 결과를 MR 본문 또는 handoff에 기록 | 문서 반영 책임자 또는 MR 리뷰어 | MR 본문, Jira 이슈, 리뷰 리포트 |
| PASS_WITH_CONDITIONS | 조건부 허용 | 조건을 반영했거나 남은 조건을 명시적으로 deferred로 기록 | 문서 반영 책임자와 영향 영역 담당자 중 1명 이상 | MR 본문, Jira 이슈, 리뷰 리포트, 의사결정 로그 |
| NEEDS_FIX | 금지 | 지적 항목을 수정하고 리뷰 또는 자체 점검 재실행 | 문서 반영 책임자 | 수정 커밋, 리뷰 리포트 |
| FAIL | 금지 | 원인 분석 후 별도 수정 브랜치 또는 작업 브리핑으로 재시작 | 문서 반영 책임자와 영향 영역 담당자 | 수정 계획, 리뷰 리포트, Jira 이슈 |

게이트 집행 책임은 아래와 같이 나눈다.

| 상황 | 집행자 | 중단 조건 |
|---|---|---|
| MR이 있는 문서 변경 | MR 리뷰어 또는 GitLab Maintainer | verdict가 `NEEDS_FIX` 또는 `FAIL`인데 merge/push를 시도함 |
| MR 없이 문서만 직접 반영하는 경우 | 반영자 본인과 작업 요청자 | 리뷰 결과, SOT 충돌 확인, 민감정보 점검 중 하나라도 누락됨 |
| 코드/에셋/프리팹/네트워크 설정 변경 포함 | 해당 영역 담당자와 MR 리뷰어 | Jira 이슈 또는 작업 브리핑이 없음 |
| GitLab 설정, protected branch, MR target 변경 | GitLab Maintainer 또는 인프라/네트워크 담당자 | 실제 GitLab 설정 확인 증거가 없음 |

업로드/Push 증거에는 최소한 아래 항목이 있어야 한다.

- 리뷰 verdict와 리뷰 리포트 위치.
- 변경 파일 목록.
- SOT 충돌 확인 결과와 확인자.
- 민감정보 점검 결과.
- 남은 조건이 있으면 deferred 사유와 재검토 시점.

증거 기록 위치는 아래 우선순위를 따른다.

| 우선순위 | 위치 | 사용 조건 |
|---|---|---|
| 1 | MR 본문 | GitLab MR을 생성하는 경우 |
| 2 | Jira 이슈 코멘트 또는 설명 | Jira 이슈가 있는 문서 작업 |
| 3 | 팀이 합의한 작업 브리핑 또는 handoff 문서 | MR 없이 문서만 전달하는 경우 |
| 4 | 리뷰 리포트 파일 경로 | 자동 리뷰 또는 수동 리뷰 결과를 첨부하는 경우 |

증거 기록에는 아래 필드를 빠뜨리지 않는다.

| 필드 | 필수 여부 |
|---|---|
| 검토 일시 | 필수 |
| 검토 대상 파일 | 필수 |
| 리뷰 verdict | 필수 |
| 리뷰어 또는 확인자 | 필수 |
| upload/push 가능 여부 | 필수 |
| 남은 조건과 deferred 사유 | 조건부 필수 |
| SOT 충돌 확인 결과와 확인자 | 필수 |
| 민감정보 점검 결과 | 필수 |
| 재검토 필요 시점 | 조건부 필수 |

`NEEDS_FIX`가 나오면 문서 반영 책임자가 수정 위치를 정하고, 수정 커밋 또는 변경 묶음에 리뷰 리포트와 조치 결과를 연결한 뒤 재검토를 요청한다. `FAIL`이 나오면 같은 변경 묶음으로 밀어붙이지 않고, 수정 브랜치 또는 새 작업 브리핑으로 재시작한다. 재검토 요청자는 문서 반영 책임자이며, 재검토 승인자는 MR 리뷰어 또는 작업 요청자다.

`PASS_WITH_CONDITIONS`의 조건은 낮은 위험의 문구 정리, 링크 보강, 운영 로그 갱신처럼 현재 구현 기준을 바꾸지 않는 항목에 한정한다. 게임 규칙, 기술 SOT, 카드 지급/승패 규칙, 네트워크 truth, 공용 프리팹/씬 소유권에 관한 조건이 남아 있으면 `PASS_WITH_CONDITIONS`가 아니라 `NEEDS_FIX`로 취급한다.

낮은 위험 조건은 아래 모두를 만족해야 한다.

- accepted 문서와 상태 인덱스를 바꾸지 않는다.
- gameplay truth, network truth, 기술스택, 승패/카드 지급 규칙을 바꾸지 않는다.
- secret, App ID, 개인 경로, raw artifact 노출과 관련이 없다.
- 링크, 표기, 오탈자, 설명 보강, 운영 로그 갱신 수준이다.
- 문서 반영 책임자와 MR 리뷰어 또는 작업 요청자가 deferred로 남기는 데 동의한다.

## accepted 승격 조건

문서를 `accepted`로 승격하려면 아래 조건을 만족해야 한다.

- 개인 PC 절대 경로와 특정 장치에서만 통하는 경로가 없어야 한다.
- 구현 레포 기준으로 재현 가능한 상대 경로 또는 역할 기반 표현을 우선 사용해야 한다.
- 기준문서에는 체력, 피해량, 쿨타임, 탄속, 장탄수 같은 튜닝 수치를 고정하지 않아야 한다.
- 튜닝 수치는 `85_밸런스_프리셋/` 문서 또는 Unity 프리셋 구현체로 분리되어야 한다.
- 문서의 소유자, 적용 범위, 관련 문서가 명확해야 한다.
- 기존 `accepted` 문서와 충돌하지 않아야 한다.
- 구현에 영향을 주는 변경이면 검증 기준 또는 smoke 영향이 함께 적혀야 한다.
- 프로젝트 내부 합의 또는 해당 영역 소유자의 검토 결과가 남아야 한다.

`accepted` 승격은 문서 반영 책임자 단독 판단으로 처리하지 않는다. 영향 영역 담당자 또는 팀 회의 결정이 필요하며, 승인 근거는 `06_의사결정_로그.md`, MR 본문, Jira 이슈, 회의 메모 중 하나에 남긴다. 승격 시에는 `08_문서_상태_인덱스.md`도 같은 MR 또는 같은 변경 묶음에서 갱신한다.

|---|---|
| 프로젝트 비전 | 프로젝트 내부 합의 필요. 게임 정체성 변경은 단독 수정 금지 |
| 게임플레이 기준 | 기획 세션 초안 작성 후 구현 영향 검토 필요 |
| 전투/밸런스 철학 | 기획 초안 작성 후 구현 담당자 검토 필요 |

| 기술 구조 기준 | 구현 담당자 제안 후 기획 담당자가 게임 의도와 충돌 검토 |
| AI 협업 운영 원칙 | 실제 작업 중 문제 발견 시 기획 세션이 갱신 가능 |

| 백로그/아카이브 | 기획 세션이 정리 가능 |

## 변경 절차

1. 변경하려는 문서의 현재 `status`와 적용 범위를 확인한다.
2. 변경이 게임 규칙, 아키텍처, 공유 에셋, 네트워크 구조에 영향을 주는지 분류한다.
3. 영향이 큰 변경이면 기존 문서를 바로 덮어쓰지 말고 후보 문서 또는 변경 제안으로 남긴다.
4. 단순 문구 정리, 경로 정리, 오탈자 수정은 같은 문서에서 바로 수정할 수 있다.
5. `accepted` 문서를 바꾸는 경우 변경 이유와 검증 영향을 문서 안에 남긴다.
6. 게임 규칙, 기술 구조, 릴리스 범위, 역할 소유권에 영향을 주는 결정은 `06_의사결정_로그.md`에도 남긴다.
7. 폐기된 내용은 삭제보다 `99_아카이브/` 이동을 우선한다.

## 한시 승인과 예외 처리

회의나 정식 승격을 기다리면 구현이 멈추는 경우, 아래 조건을 모두 만족할 때만 한시 승인으로 진행할 수 있다.

| 항목 | 기준 |
|---|---|
| 승인 주체 | 문서 소유자 또는 해당 구현 영역 소유자 |
| 유효 범위 | 해당 작업 브리핑에 적힌 파일/기능 범위로 한정 |
| 유효 기간 | 다음 회의, 다음 MR 리뷰, 또는 지정한 게이트 전까지 |
| 기록 위치 | 작업 브리핑과 의사결정 로그 또는 미결정 질문 레지스터 |
| 재검토 조건 | 구현 결과가 accepted 문서와 충돌하거나 P0 질문을 바꿀 때 |
| 금지 | secret, 라이선스 키, 3D 물리 전환, 새 승패 규칙 무단 도입 |

한시 승인은 `accepted` 승격을 대체하지 않는다. 구현을 잠시 진행할 수 있게 하는 운영 장치일 뿐이며, 이후 반드시 기준문서 상태를 정리한다.

## 기준문서 변경 승인 체크리스트

게임 규칙, 기술 구조, 릴리스 범위, 공용 에셋/프리팹 소유권에 영향을 주는 `.md` 기준문서 변경은 아래 항목을 통과해야 한다.

| 항목 | 기준 |
|---|---|
| 결정 내용 | 무엇을 현재 기준으로 볼지 한 문장으로 적었는가 |
| 책임 주체 | 문서 반영 책임자와 영역 검토자를 적었는가 |
| 근거 | 회의 결정, 구현 피드백, 기술 기준, 리스크 중 근거가 있는가 |
| 영향 문서 | 바뀌는 기준문서와 구현 영역을 적었는가 |
| 미결정 분리 | 확정되지 않은 내용은 질문 레지스터로 보냈는가 |
| 수치 분리 | 체력/피해량/쿨타임 등 수치는 프리셋으로 보냈는가 |
| secret 차단 | Photon App ID, secret, 개인 경로가 들어가지 않았는가 |
| 검증 연결 | smoke, 리허설, 플레이테스트, 리뷰 중 하나와 연결했는가 |
| SOT 충돌 확인 | 기존 accepted 문서와 상태 인덱스를 확인했고 충돌이 없는가 |
| 승인 근거 | 승인자, 승인 출처, 승인 증거 위치를 남겼는가 |

체크리스트를 만족하지 못한 변경은 `accepted` 승격을 멈춘다. 단, `candidate` 문서의 임시 정리는 가능하되 `06_의사결정_로그.md`에 `proposed` 또는 `reflected` 상태와 남은 조건을 남긴다.

긴급 예외는 게임 규칙, 기술 SOT, 네트워크 truth, 공용 프리팹/씬, 카드 지급/승패 규칙에는 적용하지 않는다. 승인자가 부재하거나 증거를 남길 수 없으면 긴급 상황이어도 `BLOCKED`로 보고한다.

비민감 영역의 예외는 오탈자, 깨진 내부 링크, 상태 인덱스와 이미 일치하는 문구 보강처럼 구현 기준을 바꾸지 않는 문서 정리에만 허용한다. 이 경우에도 변경 파일, 변경 이유, 확인자를 MR 본문 또는 handoff에 남긴다. 예외 사용 후에는 다음 회의 또는 다음 MR 리뷰에서 유지/폐기 여부를 정리한다.

## BLOCKED 처리 기준

아래에 해당하면 작업자는 임의로 진행하지 말고 `BLOCKED`로 보고한다.

- `accepted` 게임 규칙과 구현 요청이 충돌한다.
- 확정된 2D Fusion 물리 구조, 네트워크 권위 구조, 공용 씬/프리팹 소유권을 바꿔야 한다.
- 목표 구현이 신규 3D Rigidbody, 3D Collider, ConfigurableJoint, 액티브 래그돌 확장을 요구한다.
- 기준문서에 없는 새 승패 규칙, 카드 보상 규칙, 리스폰 규칙이 필요하다.
- 특정 로컬 환경에서만 통하는 경로 또는 툴 설정을 기준문서에 넣어야 한다.
- 수치 프리셋 변경이 아니라 전투 철학 자체를 바꾸는 요청이다.

## BLOCKED 태그 분류 (정본)

구현·검토·AI 세션에서 "BLOCKED" 판정을 내릴 때 반드시 아래 3태그 중 하나로 분류한다. 해소 경로가 서로 다르기 때문.

### `BLOCKED_TECH`
- **의미**: 구현·기술 난제. 팀 내 기술 조사·실험·스파이크로 해소.
- **예시**: Fusion tick drift, NetworkRigidbody2D 2D 물리 한계, [Networked] 컬렉션 Capacity 초과
- **해소 경로**: 기술 조사 → [50/04](../50_기술_구조_기준/04_Fusion_구현_가드레일.md) 가드레일 갱신 → 구현 재개

### `BLOCKED_DECISION`
- **의미**: 팀 의사결정 대기. 회의·DRI 확정·투표로 해소.
- **예시**: 최종 게임명, DRI 이름 배정, 반사탄 SOT 선택지
- **해소 경로**: 팀 회의 또는 [05/06 의사결정 로그](06_의사결정_로그.md) 기록 → 관련 문서 반영

### `BLOCKED_EXTERNAL`
- **의미**: 외부 의존. 에셋 구매·라이선스·네트워크·권한으로 해소.
- **예시**: Odin seat 추가 구매, 도메인 DNS 전파, Fusion CCU 증설
- **해소 경로**: 외부 발주·정산·계정 변경 → 반영 확인

**주의**: 관련 규칙은 각 맥락 문서([05/09 팀공유본 검토](09_팀공유본_검토_기준.md), [60/01 AI 세션 중단](../60_AI_협업_운영_원칙/01_AI_협업_운영_원칙.md))에 분리 서술되며, 태그 정의는 본 문서가 정본.

아래는 `BLOCKED`가 아니라 가정을 명시하고 진행할 수 있다.

- 함수명, 파일명, 컴포넌트 배치 같은 구현 디테일.
- 기준문서와 충돌하지 않는 임시 수치 실험.
- smoke를 위한 임시 디버그 표시.
- 개인 로컬 artifact 저장 위치 선택.

## 기준문서 작성 금지선

기준문서에는 아래 정보는 넣지 않는다.

- 개인 PC 절대 경로.
- 개인 계정명, 장치명, 다운로드 폴더명.
- 다른 작업자가 재현할 수 없는 로컬 실행 전제.
- 외부에 공유하면 안 되는 토큰, 라이선스 키, 계정 정보.

필요하면 아래처럼 표현한다.

| 나쁜 표현 | 좋은 표현 |
|---|---|
| 개인 절대 경로 | 각 작업자의 로컬 clone 루트 |
| 레포 내부 raw 로그 | 팀이 합의한 레포 밖 또는 ignore된 로컬 artifact 저장소 |
| 개인 메모 위치 | 기준문서 위치 또는 구현 레포 기준 상대 경로 |
| 특정 사용자 폴더 | <repo-root>, <artifact-root> 같은 플레이스홀더 |

## PR/MR 원칙

- 기준문서는 기본 브랜치 또는 통합 브랜치에 직접 반영하지 않는다.
- 문서 변경은 `docs/` 브랜치 또는 팀이 지정한 문서 작업 브랜치에서 진행한다.
- PR/MR 본문에는 변경한 기준, 영향을 받는 구현 영역, 검증 여부, 남은 미결정을 적는다.
- 여러 세션이 동시에 문서를 바꾸는 경우 최종 반영 순서는 통합 담당자가 결정한다.
- 팀 Git 운영은 `80_Jira_Git_운영_원칙/01_Jira_Git_컨벤션.md`를 따른다.
- Jira 이슈가 있는 작업은 브랜치, 커밋, MR 제목에 `A303-{번호}`를 연결한다.
- Git 컨벤션 원문이 팀 합의 전 상태라면 실제 GitLab 설정과 담당자 안내를 우선 확인한다.
- Photon App ID, secret, 계정 정보는 PR/MR 본문, 기준문서, tracked 설정 파일에 실제 값으로 직접 적지 않는다.

## 현재 적용

현재 `docs/`의 문서들은 대부분 `candidate`다. 다만 팀 확정 기술스택 문서(`50_기술_구조_기준/01_Unity_프로젝트_구조.md`), 라운드 상태머신 문서(`10_게임플레이_기준/02_라운드_상태머신.md`), 파일경로별 DRI 매트릭스(`50_기술_구조_기준/05_파일경로별_DRI.md`, 2026-04-21 D49 승격)는 구현 판단 기준으로 `accepted` 상태다. 게임 철학과 핵심 루프 일부는 `08_문서_상태_인덱스.md`에 적힌 범위 안에서만 `accepted_candidate`로 취급한다.

따라서 지금 단계의 목표는 모든 문서를 완성하는 것이 아니라, 사람과 AI 작업자가 혼동 없이 작업할 수 있는 최소 기준을 우선 `accepted`로 잠그고, 콘텐츠 후보는 빠르게 `candidate`로 유지하는 것이다.
