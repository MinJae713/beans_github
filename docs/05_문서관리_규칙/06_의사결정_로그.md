# 의사결정 로그

이 문서는 기준문서에 반영된 주요 결정을 한 곳에서 추적하기 위한 내부 로그다.

기준문서 본문은 현재 기준을 설명하고, 이 문서는 왜 그렇게 바뀌었는지와 어느 문서에 영향을 주는지를 남긴다. 세부 수치, 일정표, 개인 로컬 경로, secret, Photon App ID는 기록하지 않는다.

## 현재 결정문

2026-04-30 기준으로 이 문서는 회의 결과, 인프라 기술 결정, M2 협업 구조 조정을 내부 기준문서에 반영한 로그다.

현재 구현자가 binding으로 취급할 수 있는 것은 `accepted` 문서와, `05_문서관리_규칙/08_문서_상태_인덱스.md` 또는 작업 브리핑에 `accepted_candidate`로 명시된 임시 가정이다. plain `candidate`는 참고 후보이며, 소유자 확인 또는 작업 브리핑 한시 승인 없이 구현 기준으로 쓰지 않는다. 단, `90_백로그/04_미결정_질문_레지스터.md`에 `open` 또는 `deferred`로 남은 항목은 확정 규칙이 아니라 작업 전 확인 대상이다.

## 책임과 승인

| 역할 | 책임 |
|---|---|
| 문서 정합 책임 | 박병준. 기준문서 체계, 상태 인덱스, 의사결정 로그, 문서 리뷰 리듬 관리 |
| 카드/전투 정책 검토 | 김범승. 카드, GameplayProfile 수치 의미, 전투 정책, 이벤트 계약, QA 판정 기준 검토 |
| 전투/네트워크 구현 검토 | 최진우. 입력, 이동, 총격, 피격, 사망/리스폰, Fusion 상태 동기화 구현 가능성 검토 |
| 아트/UI/표현 검토 | 우수연. HUD, VFX, SFX, 캐릭터/맵 룩, 피격/사망/발사 표현 검토 |
| 인프라/빌드/서빙 검토 | 유민재. Fusion 실행 환경, Host/Server Mode, Worker Agent, 빌드/서빙 범위 검토 |
| accepted 승격 | 문서 정합 책임자 + 영향 영역 검토자 1명 이상 + 팀 회의 기록 필요 |

현재 문서 반영은 `candidate` 또는 `reflected` 상태다. `accepted` 승격은 영역 담당자 검토와 팀 회의 확인 후 진행한다. 승격 승인 기록은 이 문서의 결정 항목 또는 회의록에 남긴다.

## 결정 근거와 대안

이번 반영의 핵심 판단은 “회의 메모와 인프라 기술 기준을 흩어진 참고자료로 두지 않고, 구현자가 README부터 따라가며 확인할 수 있는 내부 기준문서 후보로 정렬한다”는 것이다.

대안은 세 가지였다.

1. 회의 메모를 그대로 두고 구현자가 각자 해석하게 둔다.
2. 모든 문서를 즉시 `accepted`로 승격한다.
3. 회의/기술 결정을 기준문서 후보에 반영하되, 미확정 항목은 질문 레지스터와 결정 로그로 분리한다.

선택한 방식은 3번이다. 이유는 1번은 구현 담당자마다 해석이 갈리고, 2번은 아직 카드 제한 세부 수치, 대시, UI 방식 같은 미결정을 확정한 것처럼 오용될 위험이 크기 때문이다. 따라서 구현자가 지금 참고할 수 있는 임시 기준은 제공하되, `open`/`deferred` 질문은 구현 전 확인 대상으로 남긴다.

| 결정 | 근거와 대안 |
|---|---|
| 1v1 MVP 고정 | 대안은 2v2 조기 포함. 하지만 상태머신, 카드 지급, 리스폰 판정이 미정의라 MVP 리스크가 큼 |
| 1차 Host Mode | 대안은 즉시 Server Mode/WebGL. 하지만 시연 안정성과 일정 리스크가 커 2차로 분리 |
| 총알 제어 카드 | 대안은 총기 교체 중심. 하지만 ROUNDS 복제처럼 보이고 디자인/구현 범위가 넓어짐 |
| 카드 지급 제한 | 대안은 패배 때마다 무제한 지급. 하지만 고의 패배와 강화 폭주 위험이 큼 |
| 낙사/추 MVP 구조물 | 대안은 압사/밧줄 절단까지 포함. 하지만 판정/사전 신호/네트워크 truth 리스크가 큼 |
| 5구간 구조 | 대안은 3개 또는 9개 구조. 현재는 가운데 3개 전투 구간과 양끝 2개 최종 구간을 MVP 기준으로 둠 |
| 대시 별도 검토 | 대안은 기본 이동기로 즉시 포함. 하지만 이동 성장과 구간 밸런스가 크게 흔들릴 수 있음 |

## 승인 체크리스트

아래 항목이 충족되지 않으면 해당 결정은 `accepted`로 승격하지 않는다.

| no | 항목 | 판정 기준 |
|---|---|---|
| 1 | 결정 내용이 한 문장으로 명확하다 | 필수 |
| 2 | 문서 반영 책임자와 영향 영역 검토자가 적혀 있다 | 필수 |
| 3 | 회의 메모, 구현 피드백, 기술 기준, 리스크 중 하나 이상의 근거가 있다 | 필수 |
| 4 | 영향을 받는 기준문서가 적혀 있다 | 필수 |
| 5 | 미결정 항목은 질문 레지스터로 분리되어 있다 | 필수 |
| 6 | 구체 수치는 프리셋/프로필/플레이테스트 기록으로 분리되어 있다 | 필수 |
| 7 | Photon App ID, secret, 개인 절대경로가 없다 | 필수 |
| 8 | 구현자가 binding으로 볼 수 있는 범위와 확인해야 할 범위가 구분되어 있다 | 필수 |

승격 또는 구현 handoff stop rule:

- 필수 항목 중 하나라도 실패하면 `accepted` 승격을 멈춘다.
- high 등급 리뷰 finding이 남아 있으면 구현 handoff에는 “candidate assumptions only”라고 명시한다.
- P0 `open` 또는 `blocked` 질문과 직접 연결된 구현은 작업 브리핑에서 별도 확인 전까지 진행하지 않는다.

## 상태값

아래 상태값은 `결정 상태`다. `accepted`, `candidate`, `backlog` 같은 문서 상태와 섞어서 읽지 않는다. 문서별 상태는 `08_문서_상태_인덱스.md`를 우선한다.

| 상태 | 의미 |
|---|---|
| proposed | 제안 상태. 아직 기준문서에 반영하지 않음 |
| reflected | 기준문서에 반영됨. 단, 문서 상태는 candidate일 수 있음 |
| accepted | accepted 문서 또는 팀 합의 기준으로 잠김 |
| deferred | 지금 반영하지 않고 백로그나 미결정 질문으로 넘김 |
| superseded | 후속 결정으로 대체됨 |

## D19 — 팀전 2v2 MVP 제외

- 결정: MVP는 1v1로 고정하고, 팀전 2v2는 1v1 MVP 안정화 이후 재검토한다.
- 이유: 현재 비전, 라운드 상태머신, 카드 지급, 리스폰, 구간 돌파가 모두 1v1 전제다.
- 구현 영향: 네트워크 입력, 라운드 판정, 카드 선택 UI는 1v1을 우선 기준으로 만든다.
- 남은 질문: 2v2 도입 시 돌파자/방어자 판정, 동시 사망, 카드 선택권 배분을 새 상태머신으로 정의해야 한다.

## D20 — 서빙 2단계 릴리스

- 결정: 1차 시연은 Windows Standalone + Photon Cloud Host Mode로 진행한다.
- 결정: WebGL, Server Mode, 웹 리더보드, 영속 데이터는 2차 릴리스 후보로 둔다.
- 이유: WebGL은 WebSocket 제약과 Host 안정성 리스크가 있어 시연 주 경로로 쓰기 어렵다.
- 폴백: Photon Cloud 온라인 실패 시 LAN Host Mode, 로컬 2P 순서로 발표 흐름을 유지한다.
- 구현 영향: Host Mode에서만 성립하고 Server Mode 전환을 막는 구조는 금지한다.

## D21 — 카드/무기 핵심 전제

- 결정: MVP는 총을 계속 바꾸는 게임이 아니라 총알을 컨트롤하는 게임으로 설명한다.
- 이유: ROUNDS식 카드 UI 복제처럼 보이는 위험을 줄이고, ddakbomb의 차별점을 탄환 운용과 전장 돌파에 둔다.
- 구현 영향: 카드 데이터에는 탄환 성질, 발사 리듬, 위치 압박, 등급, 배타 태그를 표현할 수 있어야 한다.
- 금지: 레이저 같은 즉발형 무기를 MVP 핵심 후보로 두거나, 총기 외형 교체를 차별점으로 설명하지 않는다.

## D22 — 카드 지급과 보유 제한

- 결정: 구간 돌파를 당한 방어자는 사망과 동일하게 카드 선택권을 받는 방향을 기본으로 한다.
- 결정: 카드는 무제한 누적 보상이 아니라 보유 수와 등급 제한을 전제로 한다.
- 이유: 방 개수와 카드 누적이 늘어나면 무기 강화가 과해지고, 고의 패배 전략이 생길 수 있다.
- 구현 영향: 카드 지급 조건, 보유 상한, 상위 티어 제한, 중복/배타 태그를 카드 시스템에서 추적해야 한다.
- 후속 결정: 일반 사망 전체 지급은 채택하지 않고, 구간 돌파 패배 지급을 MVP 기준으로 삼는다. 상세는 D28을 따른다.

- 결정: 팀원 프로토타입에서 드러난 구현 리스크를 기준문서의 candidate 보강으로 반영한다.
- 반영: 카드 선택 네트워크 핸드셰이크, Fusion 구현 가드레일, 관찰로그 최소 스키마를 추가한다.
- 이유: 동작하는 프로토타입을 그대로 규범화하면 Host 전용 임시동작, UI 직접 적용, 전역 탐색 의존이 기준 구현으로 굳을 위험이 있다.
- 구현 영향: 카드 선택은 요청과 확정을 분리하고, `FindObjectOfType` 의존은 제한하며, `INetworkInput` 확장은 매 tick 입력에만 신중히 사용한다.
- 후속 결정: 카드 후보 제시 정책은 D29, 특수공격 제공 방식은 D30에서 닫았다. 카드 선택 요청 구현 방식은 `Q35`와 카드 선택 핸드셰이크 기본안으로 닫았다.

## D27 — 작업 속도와 검토 리듬

- 결정: 현재 단계에서는 모든 문서를 완성하고 구현하는 방식보다, 빠른 후보 작성과 playable slice 검증을 우선한다.
- 이유: 게임의 조작감, 타격감, 카드 재미, 전장 압박은 문서만으로 검증되지 않고 실제 플레이가 필요하다.
- 엄격 유지: Unity/Fusion 기술스택, 라운드 상태머신, 네트워크 truth, 카드 선택 핸드셰이크, 씬/프리팹 소유권, secret 차단.
- 빠른 후보 허용: 카드 목록, 무기 감각, 구간 패턴, 구조물 후보, UI/VFX 후보, 밸런스 수치.
- 구현 영향: 구현자는 candidate 문서를 확정 규칙으로 오용하지 않고, playable slice와 플레이테스트 결과를 기준문서 경화 근거로 남긴다.

## D28 — 카드 지급 트리거와 티어별 제한

- 결정: MVP는 모든 일반 사망에 카드를 지급하지 않는다.
- 결정: 기본 카드 지급 트리거는 구간 돌파 패배다.
- 결정: 카드 보유 수는 티어별 제한으로 관리한다.
- 이유: 일반 사망마다 카드를 지급하면 카드 선택 시간이 플레이타임을 과도하게 차지하고, 고의 사망 성장 전략이 생길 수 있다.
- 구현 영향: 카드 지급 로직은 사망 이벤트 전체가 아니라 구간 돌파 패배 이벤트를 기본 트리거로 삼아야 한다.
- 남은 질문: 상대가 만든 일반 전투 사망에 제한적으로 카드 지급을 줄지는 후속 검토한다.

## D29 — 카드 3장 제시 정책

- 결정: 카드 선택 UI는 3장 제시를 기본으로 한다.
- 결정: 같은 제시 내 중복 카드, 이미 maxed인 카드, 티어 제한을 초과하는 카드는 제외한다.
- 결정: 일반/희귀/에픽/레전더리는 처음부터 등장 가능하되, 희귀도 가중치와 보유 제한으로 통제한다.
- 이유: 해금 단계가 늘어나면 MVP 카드 시스템의 원인 분리가 어려워진다. 대신 제시 가중치와 티어 제한으로 강한 카드의 빈도와 누적을 통제한다.
- 구현 영향: 카드 후보 생성기는 카드 상태, 티어 제한, maxed 여부, rarity weight를 입력으로 받아야 한다.

## D30 — MVP 기믹 행동 범위

- 결정: MVP 기믹 행동은 딱밤만 포함한다.
- 결정: 슬라이딩 태클은 확장 후보로 보류한다.
- 이유: 딱밤은 승리감과 도발을 만드는 저위험 기믹이고, 슬라이딩 태클은 경직/충돌/네트워크 판정 리스크가 더 크다.
- 구현 영향: 딱밤은 피해를 주는 특수공격이 아니라 presentation 중심의 기믹 행동으로 시작한다. 결과 영향이 생기면 StateAuthority 검증 대상이 된다.

## D31 — 5구간 전장과 최종 승리 구간

- 결정: MVP 전장은 5개 구간으로 설계한다.
- 결정: 가운데 3개 구간은 전투 구간, 양끝 2개 구간은 최종 승리 구간이다.
- 결정: 최종 구간에 진입하면 상대방은 리스폰하지 않고, 승리 예정 캐릭터만 끝 지점까지 이동한다.
- 결정: 매치 최종 승리는 최종 구간 끝 지점 도달 후 조작 불가능한 연출이 시작될 때 확정한다.
- 결정: 이동 주도권 보유자는 후퇴할 수 없고, 상단 HUD에는 예를 들어 `=> GO` 또는 `GO <=` 같은 방향 신호를 표시한다.
- 결정: 전장은 논리적으로 5개 구간을 쓰되, 플레이어에게는 현재 전선이 이어져 밀리고 밀리는 흐름으로 읽히게 한다.
- 결정: 전투 구간과 최종 구간 길이는 기준문서 고정값이 아니라 프리셋 후보로 관리한다.
- 이유: Nidhogg식 전선 이동과 승리 구간의 긴장 완화를 살리면서, 카드 지급/전투 루프와 최종 승리 연출을 분리하기 위함이다.
- 구현 영향: 상태머신에는 전투 구간, 최종 구간 진입, VictoryRun, MatchEnding이 구분되어야 한다. 카메라는 이동 주도권 보유자를 기준으로 전선을 따라가며, 입력 시스템은 주도권 보유자의 후퇴 입력을 결과 상태에 반영하지 않아야 한다.

> **superseded by D66 (2026-04-29 W2). 5구간 → 7구간 변경. 본 D31 결정의 결정 근거(다구간 구조 선택, 가운데 전투 + 양끝 VictoryRun 분리)는 유효하나, 구체 수치(5/3/2)는 D66로 갱신되었다.**

## D32 — MVP 카드 보유 제한 baseline

- 결정: MVP baseline 후보에서 일반 카드는 낮은 하드캡을 두지 않고 카드별 최대치로 관리한다.
- 결정: 희귀 카드는 제한적으로 허용한다.
- 결정: 에픽 카드는 최대 2장까지 허용한다.
- 결정: 레전더리 카드는 최대 1장으로 제한한다.
- 이유: 에픽은 전투 양상 변화와 조합 재미를 만들 수 있어야 하므로 1장 제한은 지나치게 좁다. 반면 레전더리는 한 장만으로 판의 판단을 바꾸는 카드로 남겨야 한다.
- 구현 영향: 카드 후보 생성기는 보유 티어별 상한을 확인하고, 상한에 도달한 티어 또는 maxed 카드를 3장 제시 후보에서 제외해야 한다.
- 주의: 이 값은 `accepted` 수치가 아니라 MVP baseline 프리셋 후보이며, 플레이테스트 결과에 따라 CardPool/GameplayProfile에서 조정한다.

## D35 — MVP 카드 후보 수 운영

- 결정: MVP 카드 후보 수를 3개, 5개처럼 인위적으로 제한하지 않는다.
- 결정: 후보 풀은 열어두고, 구현과 검증은 카드 축, 티어, 배타 태그, 리스크 단위로 나누어 진행한다.
- 이유: 카드 후보 수를 너무 좁게 잠그면 전투 양상 변화와 뽕맛을 보여주기 어렵다. 제한은 후보 개수가 아니라 보유 제한, 티어 제한, maxed 제외, 배타 태그, 테스트 slice로 관리한다.
- 구현 영향: 카드 카탈로그는 확장 가능한 데이터 구조여야 하며, 플레이테스트 리포트는 후보 개수보다 어떤 카드 축이 문제를 만들었는지 추적해야 한다.
- 영향 문서: `40_카드_무기_설계/10_세부설계/01_MVP_무기_후보_정의.md`, `40_카드_무기_설계/02_카드_효과_분류_기준.md`, `40_카드_무기_설계/10_세부설계/02_카운터_상성_매트릭스.md`, `70_검증_체크리스트/06_첫_Playable_Slice_검증_패킷.md`, `40_카드_무기_설계/10_세부설계/03_MVP_카드_후보_카탈로그.md`, `90_백로그/04_미결정_질문_레지스터.md`

## D36 — 승리감 연출과 카드 효과 분리

- 결정: 승리감 연출, 딱밤, 혹, 이모트는 카드 효과 후보로 넣지 않는다.
- 결정: 해당 요소는 기본 기믹 행동 또는 presentation 트랙에서 관리한다.
- 이유: 카드 시스템은 전투 양상과 총알 운용을 바꾸는 장치이고, 승리감 연출은 판정 결과를 설명하거나 감정을 강화하는 장치다. 둘을 섞으면 카드 후보의 역할이 흐려지고 네트워크 truth와 local-only 연출 경계가 흔들린다.
- 구현 영향: 카드 데이터에는 승리감 연출만을 목적으로 하는 효과를 등록하지 않는다. 딱밤은 기본 기믹 행동으로 시작하고, 혹/이모트/최종 승리 연출은 presentation 이벤트로 처리한다.
- 영향 문서: `40_카드_무기_설계/02_카드_효과_분류_기준.md`, `45_피드백_UI_연출/01_타격감_피드백_기준.md`, `70_검증_체크리스트/06_첫_Playable_Slice_검증_패킷.md`, `90_백로그/04_미결정_질문_레지스터.md`
