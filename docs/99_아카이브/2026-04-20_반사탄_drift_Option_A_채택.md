# 반사탄 drift 해소 제안

이 문서는 반사탄이 첫 Playable Slice 검증 항목에 포함되어 있으나, 네트워크 truth 표에 해당 상태 스키마가 정의되지 않아 팀원 AI 간 구현 불일치(desync)가 발생할 수 있는 drift를 분석하고 해소 옵션을 제안한다.

---

## 현재 상태: 양쪽 인용

### 출처 A — `70_검증_체크리스트/06_첫_Playable_Slice_검증_패킷.md` (52줄, 62줄, 77줄, 90줄)

반사탄은 첫 Playable Slice의 **포함 항목**으로 명시되어 있다.

```
(52줄) 반사탄은 같은 구간 안에서 엄폐와 각도 싸움이 보이는지 검증한다.

(62줄) | 탄환 변화형 | 기본탄, 충격/넉백탄, 반사탄, 곡사탄, 저격탄 운용 등 전투 양상 후보 |

(77줄) | 3 | 반사탄이 단순 피해량이 아니라 각도 싸움을 만드는가? |

(90줄) | 반사탄이 억울함 | 반사각 가독성, 사전 신호, 피격 로그를 먼저 확인 |
```

즉, 06 검증 패킷은 반사탄을 **1차 포함 탄환 변화형**으로 보고, "각도 싸움 검증"을 통과 관찰 항목 no.3으로 요구한다.

### 출처 B — `50_기술_구조_기준/02_네트워크_truth_표.md` (82–84줄 — 미결정 섹션)

```
## 미결정

- 투사체를 항상 NetworkObject로 둘지, 일부를 tick 기반 예측 객체로 둘지.
- 반사탄/폭발탄 같은 단발 이벤트의 최소 Networked 상태 범위.
- 관전 모드 도입 시 presentation-only 정보와 replay truth를 어떻게 나눌지.
```

Truth 표 본문(17–34줄)의 `투사체 생성`, `투사체 위치` 행은 "반사탄"을 명시하지 않으며, truth 표 어디에도 반사 횟수(`ReflectCount`), 반사 결과의 authority, 반사 판정 tick phase가 정의되어 있지 않다.

## 문제: desync 발생 시나리오

AI 또는 팀원이 `06` 검증 패킷을 읽으면 "반사탄을 첫 slice에 구현해야 한다"는 지시로 해석한다. 이때 `02` truth 표를 열면 반사탄의 Networked 필드, authority, tick phase가 정의되지 않아 구현자가 직접 판단해야 한다.

**구체 desync 경로**:

1. 팀원 A(전투 구현): `02` truth 표에 반사탄 행이 없으므로 기본 `투사체 위치(StateAuthority, Networked, FixedUpdateNetwork)` 방식을 그대로 사용해 반사 로직을 구현한다. 반사 횟수를 로컬 변수로 관리한다.
2. 팀원 B(카드/효과 루프): `02`에 authority가 없으므로 반사 이벤트를 `피격 결과(Networked state 또는 event)` 패턴으로 처리한다. 반사 횟수를 `Networked byte`로 동기화한다.
3. 팀원 C(UI/피드백): `02`에 presentation fallback이 없으므로 반사 트레일을 local-only로 처리하거나, Networked event를 구독해 표시한다.

A/B/C가 같은 기준문서를 읽었음에도 반사 횟수의 authority 위치와 동기화 방식이 달라져 Host/Client 간 반사각이 다르게 계산되는 desync가 발생한다.

**추가 위험**: `06`의 실패 신호에 "반사탄이 억울함 → 반사각 가독성, 사전 신호, 피격 로그를 먼저 확인"이 있다. truth가 정의되지 않은 상태에서 억울함이 발생하면 원인이 "가독성 문제"인지 "desync 문제"인지 분리가 어렵다.

## 옵션 A — 포함 확정: `02` truth 표에 반사탄 행 추가

### 설명

`50_기술_구조_기준/02_네트워크_truth_표.md`의 Truth 표에 반사탄 전용 행을 추가하고, 미결정 섹션에서 "반사탄/폭발탄 같은 단발 이벤트의 최소 Networked 상태 범위"를 제거한다.

### 제안 스키마 (truth 표 추가 행 후보)

| state/event | source authority | Fusion 표현 | tick phase | presentation fallback |
|---|---|---|---|---|
| 반사 판정 결과 | StateAuthority | Networked event 또는 Networked state | FixedUpdateNetwork | 반사 트레일, 충돌 이펙트 |
| 반사 횟수(ReflectCount) | StateAuthority | `[Networked] byte ReflectCount` | FixedUpdateNetwork | 없음 (게임 결과에 영향) |
| 반사 후 투사체 방향 | StateAuthority | `NetworkObject` 위치/속도 갱신 | FixedUpdateNetwork | trail interpolation |
| 반사 피격 결과 | StateAuthority | Networked state 또는 event | FixedUpdateNetwork | hit VFX/SFX |
| 반사 경로 가독성 신호 | Local | local-only | presentation | 반사 예고선, 트레일 색상 |

**스키마 선택 근거**:
- `ReflectCount`를 `StateAuthority` `Networked byte`로 두는 이유: 반사 횟수가 게임 결과(피격 여부, 카드 효과 누적)에 영향을 줄 수 있으므로 local-only 처리 금지.
- 반사 후 투사체 방향을 `NetworkObject` 위치/속도 갱신으로 두는 이유: 기존 `투사체 위치` 행과 동일한 authority 패턴을 유지해 별도 시스템 없이 처리 가능.
- 반사 경로 가독성 신호는 local-only: "반사탄이 억울함" 실패 신호 대응이 presentation 레이어에서 가능하도록 분리.

## 권장 및 이유

**Option A(포함 확정)를 권장한다.**

이유:

1. **Fusion 네이티브 구현 환경**: 현재 프로젝트는 Razor Madness 기반 Fusion 네이티브 자체 구현을 확정한 상태다. 반사탄의 `NetworkObject` 경로 처리는 이미 `투사체 생성/위치` 행의 StateAuthority 패턴을 그대로 확장하면 되므로, 신규 시스템이 아니라 기존 패턴의 적용 범위 확대다.

2. **카드 차별화의 핵심 후보**: `40_카드_무기_설계/10_세부설계/01_MVP_무기_후보_정의.md`에서 반사탄은 검증 우선순위 3번(우선)으로, 곡사탄과 함께 MVP 핵심 탄환 변화형으로 분류되어 있다. Option B로 제외하면 MVP 카드 차별화 검증이 기본탄/넉백탄 2종으로 좁아진다.

3. **`06` 검증 패킷과의 정합성**: `06`에서 반사탄을 제거(Option B)하면 `30_전장_레벨디자인/10_세부설계/01_구간_패턴_카탈로그.md`의 "반사/각도 구간"도 첫 slice에서 제외해야 하며, 구간 카탈로그·카운터 상성 매트릭스 등 5개 이상 문서에 추가 drift가 발생한다.

4. **미결정 해소 비용**: Option A의 `02` truth 표 수정은 5개 파일이지만, Q5/Q20 등 이미 관련 질문이 열려 있어 수정 방향이 명확하다. Option B는 파일 수는 2개로 적지만 추후 반사탄을 다시 포함할 때 더 많은 문서를 수정해야 한다.
