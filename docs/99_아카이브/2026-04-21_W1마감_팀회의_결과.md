#### Q39 — 이동 주도권 "후진 금지" 어디서 막을 것인가

**상황**
이 게임은 주도권자(돌파 중인 쪽)가 전진만 가능하고, 주도권을 잃은 쪽은 밀려나야 한다. 주도권 판정(전진 허용)은 `RoomManager.LastKiller`가 담당하고, 경계 clamp는 `PlayerController.CheckRoomBoundary`가 담당한다.

**현재 구현 검토 (2026-04-20, 최진우 제보 + `worldclasscitizen/colosseum-private` 코드 조사)**

| 라인 | 코드 | 해석 |
|---|---|---|
| `PlayerController.cs:80` | `if (!Object.HasStateAuthority) return;` | `CheckRoomBoundary` 전체가 **Host에서만 실행** |
| `PlayerController.cs:61` | `_rb.velocity = new Vector2(input.Direction.x * speed, ...)` | velocity 세팅은 Authority 분기 없음 (양쪽 실행) |
| `RoomManager.cs:88` | `if (hasLastKiller && player != LastKiller) return false;` | Host에서 LastKiller 검증 |
| `RoomManager.cs:19` | `[Networked] public PlayerRef LastKiller` | Host 권위 동기화 |

→ **현재 구현은 Option A (authoritative-only)**. 치팅 방어는 완벽 (`LastKiller` 검증 + clamp 모두 Host-only)하지만 **Client-side prediction은 없다**. 로컬 2P 테스트에서는 Host=Client 동시 실행이라 차이가 안 보이나, 원격 2P에서는 RTT 비례 rubber-banding 잠재 리스크.

**용어 정합 (2026-04-20 Mattermost 사전 합의 — 최진우 제안 16:33 + 박병준 확인 16:37)**

"후진 금지"는 **방(Segment) 단위** 제약이다. 방 내 좌우 이동(A/D 키) 자체는 항상 자유.

구체 규칙:
1. `LastKiller == null` → 양쪽 모두 **상대 진영쪽 방**으로 전진 가능
2. `LastKiller == P1` → P1만 상대 진영쪽 방으로 전진 가능
3. `LastKiller == P2` → P2만 상대 진영쪽 방으로 전진 가능
4. **본인 진영쪽 방으로 이동은 언제나 불가** (= "후진 금지"의 실제 의미)
5. 한 방 내부에서의 이동은 항상 허용

"이동 커맨드 자체 차단(A키 입력 억제)" 해석은 기각. **방 경계 전환 시점의 게이팅만 강제**.

→ 회의 T1 Q39는 semantic 설명을 건너뛰고 **구현 경계(A1 유지 vs A2 즉시 승격)만 결정**한다. 부록 A6로 Jun 선행 반영.

**선택지**

| 옵션 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A1 (권장)** | **현재 구현 유지, W3 원격 RTT 측정에서 체감 검증** | 코드 추가 0, 치팅 방어 이미 OK | 원격 rubber-banding 발견 시 W3~W4 재작업 |
| A2 | 즉시 Option C 승격: `PlayerController.cs:80`의 `HasStateAuthority` gate 제거, `TryAdvanceRoom`/`ClampToX` 내부 Host gate만 유지 | 원격 rubber-banding 사전 방어 | 10~20줄 수정, W1 마감 압박 |
| B | InputAuthority local clamp만 | 즉각 피드백 | 치팅 우회 가능 — 현재 구현 대비 퇴행 |
| C | StateAuthority + InputAuthority 이중 | — | 사실상 A2와 동일 |

**Jun 권장: Option A1** (최진우 의견 수용 + 실측 기반 결정).

이유:
- 치팅 방어는 `RoomManager.TryAdvanceRoom`의 `LastKiller` 검증 + Host-only 실행으로 이미 작동.
- MVP 우선순위상 "추측 방어"보다 **W3 RTT 측정(`SCHEDULE.md W3 ④`) 시 실제 체감 확인 후 수정**이 합리적.

**미결정 시**: 없음. Option A1은 현재 코드 유지이므로 W2 착수 가능.

**결정 후 반영**:

#### Q42 — ChoicePending race condition + RTT 도착 지연 + seed 동기화

**상황**
카드 선택 화면에서 세 축의 문제가 겹친다.

1. **동일 tick race**: 타이머(예: 10초) 만료 직전에 플레이어가 클릭했을 때, **플레이어 선택**과 **타임아웃 랜덤 자동 선택**이 동일 tick에 도착할 수 있다. Host/Client가 다른 결과를 확정하면 원격 세션에서 카드가 desync된다.
2. **RTT 도착 지연** (2026-04-20 팀원 제기, Mattermost): 플레이어가 UI 기준 9.99s에 클릭해도 패킷이 RTT 타고 Host에 10.12s에 도착하는 경우가 빈번하다. UI deadline과 Host hard deadline이 같으면 끝자락 클릭이 일괄 무효 처리되어 "내 클릭 왜 무시됨" 체감이 누적된다.
3. **seed 동기화**: 랜덤 자동 선택의 seed를 Host/Client가 독립 생성하면 결과가 갈린다.

**선택지**

| 옵션 | race 처리 | RTT 흡수 | seed 동기화 |
|---|---|---|---|
| A | 플레이어 선택 절대 우선 | 없음 (UI=Host deadline 동일) | 로컬 각각 → Host 최종값 강제 |
| B 원안 | Grace 1 tick (≈16~33ms) | 1 tick만 — Photon KR p95 300ms 대비 부족 | Networked seed 브로드캐스트 |
| **B 개정 (권장)** | **hardDeadline 내부 동일 tick race 시 선택 우선** | **2-deadline 분리 + padding ~300ms** | **Networked seed 브로드캐스트** |
| C | 타임아웃 우선 | (고려 안 함) | (고려 안 함) |

**B 개정 상세 정책**

```yaml
# UI와 Host 권위 분리
visibleChoiceDuration: 10.0s          # 플레이어에게 보이는 카운트다운
serverAcceptPadding:   0.3s           # RTT 흡수 버퍼 (W3 실측 후 튜닝)

# Fusion tick 환산
visibleDeadlineTick = choiceStartTick + visibleDurationTicks
hardDeadlineTick    = visibleDeadlineTick + ceil(padding / tickRate)

# Host 판정
Host 수신 tick <= hardDeadlineTick  → 수락
Host 수신 tick >  hardDeadlineTick  → 타임아웃 랜덤 확정

# hardDeadline 내부 race 해석
선택 + 타임아웃이 동일 tick에 들어온 경우 → 선택 우선 (타임아웃 이벤트 폐기, 큐잉 금지)

# UI 상태
0초 시점 → 버튼 비활성화 + "확정 중" 짧은 잠금 상태
Host 결과 수신 → 다음 단계 전환
```

**Jun 권장: Option B 개정**. 이유:

- 원안 Grace 1 tick(≈30ms)은 Fusion 동일-tick race 해석용으로는 적절하나 **RTT 도착 지연 흡수**에는 부족.
- Photon Cloud KR 리전 p95 300ms RTT (`SCHEDULE W4 ①` 목표) 기준, padding 300ms가 **끝자락 클릭 UX 보호**와 **악의적 늦은 선택 차단**의 균형점.
- 2-deadline 구조는 UI가 먼저 잠기고 Host가 짧게 더 받아주는 형태이므로 **Host authoritative 원칙 유지**.
- `serverAcceptPadding` 값은 W3 RTT 실측 후 튜닝 대상: 너무 짧으면 끝자락 클릭 무효, 너무 길면 상대 플레이어 "결과 확정이 느리다" 체감.
- race 해석 규칙을 함께 박아두지 않으면 hardDeadline 경계 tick의 동시 이벤트 해석이 구현자 재량으로 남아 Q42를 닫은 뒤에도 desync 재발 가능.

**미결정 시**: W3 원격 2P 카드 선택에서 (a) desync 또는 (b) 끝자락 클릭 일괄 무효 체감 누적. 디버깅 며칠 + 밸런스 인상 저하.

# 85/20/01 전투 수치 프리셋 스키마 v0 (수치는 모두 TBD)

reloadTime: float     # 재장전 시간 (초)
bulletSpeed: float    # 탄속 (units/s)
