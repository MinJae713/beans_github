# 매칭/로비 기준 (candidate)

> 상태: candidate. D62에서 확정된 "방 목록 기반 로비 플로우"를 구현 후보 기준으로 풀어 쓴 문서다. Room Registry control plane의 구현 착수와 accepted_candidate 승격은 네트워크/인프라 DRI 확인 후 진행한다.
>
> D62의 binding 범위는 "Option A(Host + Room Code)보다 Option B(Lobby Browser) 방향을 우선한다"는 flow choice다. 이 문서의 Spring Room API, Redis, Worker Agent, Room Registry 세부 구현 기준은 DRI gate 통과 전까지 candidate guidance다.

## 왜 이 문서가 필요한가

로비/매칭은 Unity UI, Worker Agent, Spring Boot Room Registry, Redis, Fusion game server가 함께 얽히는 control plane이다. 담당자마다 다른 방 생성/조회 방식을 구현하면 방 목록 drift, 유령 방, `ROOM_CREATE_FAILED`, 게임 서버 spawn 실패가 반복된다.

이 문서는 MVP 매칭·로비의 공통 후보 기준을 정의한다. 단, 피격/사망/카드/승패 같은 gameplay authoritative 결과는 여전히 Fusion `StateAuthority`가 소유한다.

## 범위와 비범위

### 범위

- 메인 -> PLAY -> 방 목록 -> 방 생성/입장 흐름
- Worker Agent를 통한 GameServer 프로세스 spawn / 종료
- Spring Boot Room Registry API와 Redis 기반 방 목록 관리
- 로비 화면의 최소 기능과 실패 처리

### 비범위

- 스킬 기반 자동 매치메이킹
- 랭크 시스템·리더보드
- 관전 기능 (`90/04 Q21` deferred)
- 친구 초대·Discord Rich Presence
- gameplay 결과 판정 권한

## MVP 로비 옵션 비교

| 옵션 | 방식 | 현재 취급 | 비고 |
|---|---|---|---|
| A. Host Mode + Room Code | 방장이 세션 생성, 코드를 공유해 입장 | reference / 폴백 후보 | D62로 MVP 기본안에서 내려감. 방 코드 입력 UI를 기본 구현하지 않음 |
| B. Lobby Browser | 방 목록에서 선택 입장, 생성 버튼으로 새 방 요청 | MVP 기본 후보 | 현재 구현 방향. 닉네임/방장 표시 기반 UX |
| C. Auto-Match | 대기열 기반 자동 매칭 | 2차 후보 | MVP 범위 초과 |

## MVP 후보 구현 방향 — Option B (Lobby Browser)

### 기본 흐름

1. 플레이어가 메인 화면에서 닉네임을 입력한다.
2. PLAY 진입 시 Find Room 화면에서 방 목록을 조회한다.
3. 방 만들기 버튼은 Unity Lobby -> Worker Agent -> GameServer spawn -> Spring Room API 등록 흐름을 탄다.
4. 참가자는 방 목록에서 방을 선택해 해당 Fusion session/game server에 입장한다.
5. 방 생성/상태 변경/삭제는 Room Registry에 반영되고, UI는 조회 결과 projection을 표시한다.

### Room Registry control plane

| 구성요소 | 책임 |
|---|---|
| Unity Lobby | 클라이언트 로비 메시지 수신, 방 목록 projection 전달, 입장 흐름 연결 |
| Worker Agent | GameServer 프로세스 spawn / 종료 / stdout 상태 수집 / Room API `POST/PATCH/DELETE` 호출 |
| Spring Boot | Room Registry API (`GET/POST/PATCH/DELETE /api/v1/rooms`) |
| Redis | 중앙 방 메타데이터 저장소 |

Room Registry는 Fusion gameplay truth가 아니다. 방 목록은 "어떤 방 프로세스가 보이고 입장 가능한가"를 위한 service/control plane 상태다.

## 로비 상태 후보

| 상태 | Authority / source | 표현 | 전이 조건 |
|---|---|---|---|
| `Lobby.Empty` | Local | 로비 메인 화면 | 초기 진입 / 매치 종료 후 복귀 |
| `Lobby.Browsing` | Lobby -> Spring Room API | 방 목록 화면 | PLAY 또는 Refresh |
| `Lobby.Creating` | Unity Lobby -> Worker Agent | "방 생성 중" 표시 | 방 만들기 클릭 |
| `Lobby.Joining` | Client request -> Fusion session | "입장 중" 표시 | 방 목록에서 방 선택 |
| `Lobby.InRoom` | Fusion/session + Room Registry projection | 방/참가자 상태 표시 | 입장 성공 |
| `Lobby.Starting` | StateAuthority / server flow | 매치 시작 전환 | 게임 서버 준비 완료 |

## 실행 전제

로컬 2클라 또는 exe smoke에서 로비 경로를 검증하려면 아래 서비스가 맞물려야 한다.

| 전제 | 기준 |
|---|---|
| Redis | 기본 `localhost:6379` 또는 작업 브리핑에 명시한 환경값으로 기동 |
| Spring Boot Room API | 기본 `http://127.0.0.1:8081/api/v1` 기준으로 Room Registry CRUD 제공 |
| Worker Agent | 기본 `http://127.0.0.1:8080`에서 lobby spawn 요청 수신 |
| Worker Agent -> Room API | `--room-api-base-url http://127.0.0.1:8081/api/v1` 또는 `COLOSSEUM_ROOM_API_BASE_URL`로 Room API 연결 |
| Unity Lobby/GameServer | `COLOSSEUM_WORKER_BASE_URL=http://127.0.0.1:8080`, `COLOSSEUM_ROOM_API_BASE_URL=http://127.0.0.1:8081/api/v1` 기준을 공유 |
| 원격 EC2 reference | Onboarding / Lobby / Worker / API 4개 역할 분리. Lobby는 Linux Dedicated 프로세스, Worker와 API는 Docker 기반, Onboarding은 Nginx 정적 페이지를 사용 |

구체 명령, 포트 override, 로컬 절대경로는 이 문서에 고정하지 않고 작업 브리핑 또는 운영 표준문서에 적는다.

현재 원격 배포 프로토타입에서는 Lobby가 private VPC 주소의 Worker Agent와 Spring Room API를 호출한다. 대표 형식은 `COLOSSEUM_WORKER_BASE_URL=http://10.x.x.x:8080`, `COLOSSEUM_ROOM_API_BASE_URL=http://10.x.x.x:8081/api/v1` 이며, Onboarding 페이지는 gameplay truth와 무관한 별도 정적 다운로드 경계로 취급한다.

## 승격 / 승인 게이트

이 문서는 아직 `candidate`다. 아래 항목이 확인되기 전에는 `accepted_candidate`로 승격하거나 Room Registry 전제를 push-ready / 시연-ready 기준으로 선언하지 않는다.

Network/Infra DRI의 현재 owner source는 [`05_파일경로별_DRI.md`](05_파일경로별_DRI.md)와 [`../05_문서관리_규칙/05_팀_작업구조와_역할_소유권.md`](../05_문서관리_규칙/05_팀_작업구조와_역할_소유권.md)를 따른다.

| 항목 | 기준 |
|---|---|
| 승인 주체 | Network/Infra DRI 또는 해당 DRI가 위임한 구현 담당 |
| 증빙 위치 | Jira 코멘트, MR 본문/스레드, 또는 검증 리포트. 로컬 알림은 해당 공식 증빙 위치를 가리키는 보조 포인터로만 취급 |
| 실행 증빙 | Redis `6379`, Spring Room API `8081`, Worker Agent `8080`, Unity env 정렬 상태가 같은 리허설에서 확인됨 |
| merge-stop | Room API/Redis/Worker Agent 중 하나라도 미기동 상태에서 로비 경로 성공처럼 보고하면 안 됨 |
| rehearsal-stop | Room Registry 장애 시 폴백이 정해지지 않았으면 방 생성/방 목록 기반 리허설을 통과로 처리하지 않음 |

### 게이트 체크리스트

아래 항목은 MR 본문, Jira 코멘트, 또는 검증 리포트에 evidence link / 로그 요약 / 승인자를 남겨야 한다. 로컬 알림을 병행할 수는 있지만, 알림 자체가 공식 증빙을 대체하지 않는다.

| 체크 | 필요한 증빙 |
|---|---|
| Redis | `localhost:6379` 또는 지정 포트 연결 확인. 기대 결과: Spring Room API가 Redis 연결 실패 없이 기동 |
| Spring Room API | `http://127.0.0.1:8081/api/v1/rooms` 기준 `GET/POST/PATCH/DELETE` Room CRUD smoke. 기대 결과: 각 요청이 2xx/명시된 정상 응답으로 끝남 |
| Worker Agent | `http://127.0.0.1:8080` listen 상태와 GameServer spawn 요청 로그. 기대 결과: spawn 요청 실패가 아니라 GameServer 기동 또는 명확한 하위 실패 로그 |
| Room API 연결 | Worker Agent의 `--room-api-base-url` 또는 `COLOSSEUM_ROOM_API_BASE_URL` 값. 기대 결과: Spring Room API URL과 문자열 기준 일치 |
| Unity env 정렬 | Lobby/GameServer의 `COLOSSEUM_WORKER_BASE_URL`, `COLOSSEUM_ROOM_API_BASE_URL` 값. 기대 결과: Worker Agent / Room API 실제 기동 주소와 일치 |
| DRI 확인 | Network/Infra DRI 또는 위임자가 위 실행 증빙을 확인했다는 기록. 위임 승인인 경우 delegating DRI, delegate, date, evidence location을 함께 남김 |
| 폴백/no-go 결정 | Room Registry 장애 시 LAN Host Mode, 수동 room 재시작, no-go 중 하나를 선택하거나 rehearsal-stop으로 명시. 기본값은 Room Registry 경로 no-go |

이 MR 범위의 문서 보강은 candidate 기준을 명확히 하는 작업이다. 위 체크리스트가 채워지기 전까지는 로비 경로가 시연-ready 또는 구현 완료라는 의미가 아니다.

증빙 verifier는 MR reviewer 또는 Network/Infra DRI다. Worker Agent 로그, Room API CRUD smoke 출력, 실패 로그는 MR/Jira/검증 리포트 중 하나에 요약과 artifact 위치를 남기고, raw 로그는 레포 밖 artifact 위치에 보존한다. 로컬 알림은 해당 MR/Jira/검증 리포트 링크를 전달하는 보조 알림으로만 사용한다.

승인 결과는 PASS 또는 BLOCKED로 남긴다. Redis/API/Worker/env/fallback 증빙 중 하나라도 없거나 health-only 증빙만 있으면 MR reviewer 또는 Network/Infra DRI는 Room Registry 경로 merge 승인, 리허설 통과 보고, 시연-ready 보고를 BLOCKED로 처리한다.

최소 증빙 스키마:

| 필드 | 기준 |
|---|---|
| environment tuple | Redis URL/port, Room API URL, Worker Agent URL, Unity env 값 |
| timestamp | 실행 시각 |
| command/request summary | 실행한 명령 또는 HTTP method/path 요약 |
| expected result | 기대 응답 또는 로그 조건 |
| actual result | 실제 status code, 로그 라인, room id/session name 등 correlation 값 |
| artifact path | raw 로그/출력 파일 위치. 레포 밖 또는 ignore된 artifact 위치 |
| verifier/approver | MR reviewer, Network/Infra DRI, 또는 위임 승인자 |

로컬 loopback 리허설에서도 audit/log 증빙을 남긴다. 필수 로그 범위는 Worker Agent spawn 요청/응답, Room API `GET/POST/PATCH/DELETE`, GameServer stdout status, Lobby/GameServer env 값, 실패 로그다. 보존 책임은 해당 MR 작성자와 Network/Infra DRI가 공유하며, 최소 보존 시점은 MR merge 또는 해당 demo rehearsal 종료까지다.

artifact 취급 규칙:

| 항목 | 기준 |
|---|---|
| secret redaction | Photon/AppID/API secret, token, 개인 계정값은 raw/log summary 어디에도 남기지 않음 |
| env redaction | env dump는 `COLOSSEUM_WORKER_BASE_URL`, `COLOSSEUM_ROOM_API_BASE_URL`, Redis/Room API/Worker host-port처럼 승인된 key/host만 남김 |
| 개인 경로 | 사용자 홈, 개인 이름, 외부 계정이 드러나는 절대경로는 repo-relative 또는 artifact label로 치환 |
| 저장 위치 | raw artifact는 repo-ignored 또는 레포 밖 위치에 두고 owner/access 범위를 기록 |
| 위반 처리 | unredacted secret/개인 경로/민감 env가 발견되면 MR reviewer 또는 Network/Infra DRI가 PASS 대신 BLOCKED 처리 |

### 노출 / 보안 게이트

Tracked 기본값은 동일 PC 로컬 개발 기준이다. Worker Agent와 Spring Room API는 기본적으로 loopback/local-dev control plane으로 취급한다.

| 조건 | 처리 |
|---|---|
| `127.0.0.1` / localhost 범위 | 로컬 리허설 후보. 위 실행 전제와 체크리스트를 적용 |
| `0.0.0.0`, LAN IP, 공유 호스트, 원격 배포 | Network/Infra DRI 승인 전 merge-stop |
| 비로컬 노출 승인 | 아래 노출 승인 체크리스트를 모두 채우거나 DRI가 명시적으로 N/A 처리 |
| 승인 증빙 없음 | 방 생성/방 목록 경로를 성공 또는 시연-ready로 보고하지 않음 |

비로컬 노출 승인 체크리스트:

| 체크 | 필요한 증빙 |
|---|---|
| bind address | 실제 listen 주소와 포트, 노출 범위 |
| 인증/인가 경계 | 누가 spawn/room API를 호출할 수 있는지와 차단 방식 |
| 네트워크 제어 | firewall, TLS, VPN, 사설망 등 적용 또는 N/A 사유 |
| secret 취급 | Photon/AppID/API secret 등 민감값이 docs/tracked 설정에 노출되지 않았다는 확인 |
| audit/log | spawn 요청, Room API CRUD, 실패 로그의 저장 위치와 보존 기준 |
| 승인 기록 | Network/Infra DRI, 승인 날짜, evidence location |

### fallback / no-go 결정

Room Registry 장애 시 candidate/rehearsal gate 기본값은 **Room Registry 경로 no-go**다. LAN Host Mode 또는 수동 room 재시작은 DRI 승인 기록이 있을 때만 별도 fallback 리허설로 취급한다.

| 항목 | 기준 |
|---|---|
| 승인 주체 | Network/Infra DRI. 위임 시 delegating DRI, delegate, date, evidence location 기록 |
| 선택지 | LAN Host Mode, 수동 room 재시작, no-go 중 하나 |
| 발동 조건 | 어떤 장애/로그/health 결과에서 fallback을 적용하는지 |
| 증빙 위치 | Jira, MR 스레드, 또는 검증 리포트 중 하나. 로컬 알림은 보조 알림으로만 사용 |
| 효력 범위 | fallback은 별도 비-Room-Registry 리허설을 unblock할 수 있지만, Room Registry 기반 리허설 통과 증빙을 대체하지 않는다 |
| 결정 시점 | Room Registry 경로를 시연-ready 또는 push-ready로 주장하기 전 |
| 필수 필드 | selected option, approval outcome(PASS/BLOCKED/REJECTED), validity scope/window, approving DRI/delegate, date, trigger condition, evidence location |

fallback/no-go record가 없거나 outcome이 모호하면 no-go로 처리하고, "Room Registry path passed", "Room Registry push-ready", "Lobby Browser demo-ready" 같은 claim은 BLOCKED다.

## 실패 처리

| 실패 | 처리 기준 |
|---|---|
| Room API 미기동 | 방 목록 조회 실패/빈 목록을 사용자에게 표시하고, 로그에 control plane 실패로 분류 |
| Redis 미기동 | Spring Boot health 또는 Room API CRUD smoke 실패로 분류 |
| Worker Agent 미기동 | 방 생성 실패(`ROOM_CREATE_FAILED` 등)로 분류. Fusion gameplay 실패로 오인하지 않음 |
| GameServer spawn 실패 | Worker Agent 로그와 GameServer 로그를 함께 확인 |
| 방 목록 stale | Room API `GET /rooms`, status patch/delete 경로, process exit cleanup 순서 확인 |

## 금지선

- 방 비밀번호·개인 계정 ID·이메일·Discord 핸들을 방 식별자에 포함하지 않는다.
- Photon Cloud AppID, secret, 개인 환경값을 기준문서나 tracked 설정에 실제 값으로 적지 않는다.
- Room Registry 상태를 gameplay 승패, 피해, 카드 결과의 authoritative truth처럼 사용하지 않는다.
- Unity UI가 Spring/Redis를 직접 truth처럼 소유하지 않는다. UI는 NetworkGameplay/control plane bridge 결과를 표시한다.
- Host + Room Code reference를 현재 MVP 기본 로비 흐름으로 되살리지 않는다.

## 검증 기준

- 로컬: Redis + Spring Room API + Worker Agent + Lobby/GameServer가 함께 기동된다.
- 방 생성: Worker Agent spawn 후 Room API `POST /rooms`가 성공하고 방 목록에 표시된다.
- 방 입장: 두 클라이언트가 같은 room/game screen에 진입한다.
- 상태 변경: `##STATUS`, `##PLAYERS` 등 서버 상태가 Room API `PATCH`로 반영된다.
- 방 삭제: GameServer 종료 후 Room API `DELETE` 또는 cleanup 경로로 목록에서 제거된다.
- gameplay 분리: 방 목록 문제가 피격/카드/승패 truth 문제처럼 처리되지 않는다.

## 미결정

- Room Registry API 장애 시 no-go 기본값을 LAN Host Mode 또는 수동 room 재시작으로 override할지. 이 항목은 MR !69 문서 보강 자체의 blocker는 아니며, Room Registry 경로를 시연-ready 또는 push-ready로 주장하기 전 Network/Infra DRI가 결정한다. override가 없으면 Room Registry 기반 리허설은 no-go / rehearsal-stop으로 처리한다.
- 방 목록 자동 refresh 주기와 수동 Refresh 버튼의 최종 UX.
- 현재 원격 프로토타입은 Worker Agent EC2와 Spring Room API EC2를 분리한다. 이 분리 구조를 이후 기준 운영 topology로 고정할지, 비용·운영 편의상 통합 배치 옵션을 둘지는 미결정이다.
