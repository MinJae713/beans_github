# 07. 학생 코드 샌드박스 옵션 검토

작성일: 2026-04-12
작성 목적: 학생이 작성한 `decide(state)` Python 코드를 **안전하게 실행**하기 위한 옵션을 비교하고, 2인 SSAFY 팀 규모·일정에서 실제 채택할 한 가지를 결정한다.
선행 문서: `00_기획브리프_초안.md`, `02_핵심시스템_초안.md`, `05_API_및_상태모델_초안.md`

---

## 1. 요구사항 정리

### 1.1 기능 요구
- 학생이 제출한 `cook.py` 파일의 `decide(state)` 함수를 시뮬레이터가 매 틱 호출한다.
- 한 판(영업 시간 200틱)에서 학생 함수가 최대 ~200회 연속 호출된다. (Ch8 확장 시 assignment list 반환이면 동일)
- 결정론 보장: 같은 시드 + 같은 학생 코드 → 같은 결과. 샌드박스가 부가적인 비결정성(랜덤 프로세스 ID 등)을 주입하면 안 된다.
- 시뮬레이터(Java or Python) ↔ 학생 코드(Python) 간 **`KitchenState` 직렬화**가 가능해야 한다. JSON 수준으로 충분.

### 1.2 보안 요구
- 학생 코드가 파일시스템을 읽거나 쓰지 못해야 한다 (`/etc/passwd`, 다른 학생 제출물, 정답지 등).
- 네트워크를 사용할 수 없어야 한다 (외부 API로 답 구걸, DoS 유발).
- `os.system`, `subprocess.Popen`, `eval("__import__...")` 같은 import 우회를 막아야 한다.
- **CPU/메모리/실행시간 한도**를 강제할 수 있어야 한다. 무한루프 `while True: pass` 에서 자동 종료.
- 한 판의 총 예산: 실벽시계 기준 ≤ 10s (교육 루프 반응성), 메모리 ≤ 256MB.

### 1.3 제약 조건 (SSAFY 운영 관점)
- **운영 환경**: SSAFY 내부 툴. 로컬(학생 PC)에서 자체 검증 + 서버에서 제출 채점이 둘 다 필요할 수 있다. 전국 단위 배포가 아니라 반(班) 단위 교육이므로 대규모 스케일링은 우선순위 낮음.
- **개발 리소스**: 2인 팀, 8주 내외. 샌드박스 자체가 주 결과물이 아님.
- **학생 PC**: Windows 11 + Git Bash + 자율적으로 설치되는 Python. Linux 전용 메커니즘(seccomp, unshare)은 학생 로컬에서 사용 불가.
- **제출 검증 서버**: 단일 인스턴스로도 충분 (동시 접속 최대 ~50명, 한 판 10s).
- **신뢰 수준**: 학생은 의도적으로 뚫으려 하진 않지만, 호기심·실수·잘못된 import로 사고를 치는 케이스는 현실적으로 자주 발생한다 — 즉 **"교육용 악의 없는 학습자"** 가 위협 모델이다. APT 수준 격리 불필요.

## 2. 후보 옵션 개관 (9가지)

## 3. 옵션별 상세 평가

### 옵션 1. `exec()` + AST 화이트리스트 + `resource` 제한

**개요**: 학생 코드를 `ast.parse` 로 파싱해 위험한 노드(`Import`, `Attribute`, 특정 함수 호출)를 거부한 뒤 `exec()` 로 같은 프로세스에서 실행. `resource.setrlimit(RLIMIT_CPU, ...)` 로 CPU 한도.

- 장점
  - 구현 1~2일. 외부 의존성 0.
  - 성능 오버헤드 거의 없음 (함수 호출당 마이크로초).
  - Python 데이터 구조(dataclass)를 그대로 넘길 수 있어 직렬화 비용 0.
- 단점
  - AST 화이트리스트는 **본질적으로 뚫리는 메커니즘**이다. `().__class__.__bases__[0].__subclasses__()` 같은 메타클래스 트릭을 하나씩 막는 싸움이 끝나지 않는다. 교육생이 악의 없이 짠 `numpy` import도 막히면 학습 경험이 떨어진다.
  - `resource.setrlimit` 은 Windows 에 없다. Windows 학생 로컬에서는 CPU 한도가 강제되지 않음.
  - 같은 프로세스라서 학생 코드가 시뮬레이터 전역 상태(`random.seed`, 클래스 변수)를 오염시킬 수 있다 — 결정론 보장 자체가 흔들림.
- 판정: **로컬 데모 용도만.** 제출 채점에는 부적합.

### 옵션 2. RestrictedPython (Zope)

**개요**: Zope 재단이 20년 이상 유지 중인 라이브러리. `compile_restricted()` 로 컴파일하면 위험한 문법(`exec`, `import`, `open`, `__` 이름)을 AST 레벨에서 제거·치환한다. `safe_builtins`, `safe_globals` 등 사전 정의된 builtins만 노출.

- 장점
  - `pip install RestrictedPython` 한 줄. 순수 파이썬, Windows/Linux/macOS 동일하게 동작. **SSAFY 로컬 환경과 궁합 최상.**
  - Zope와 edX `codejail` 등에서 장기 운영 사례 있음.
  - 화이트리스트 관리가 `safe_builtins` 사전으로 명시화되어 있어, 팀에서 "학생이 쓸 수 있는 것" 을 문서로 공유하기 쉬움. `sorted`, `min`, `max`, `heapq`는 허용, `open`, `__import__` 는 차단.
  - 동일 프로세스라 KitchenState dataclass를 그대로 넘길 수 있음.
- 단점
  - CPU/메모리 한도는 따로 제공하지 않음. 무한루프 보호는 별도 계층(타임아웃 래퍼)에서 해결 필요.
  - 같은 프로세스이므로 학생 코드가 시뮬레이터 객체를 mutation하면 결정론이 깨질 수 있음 — 방어: state를 `copy.deepcopy` 후 주입.
  - `numpy` / `heapq` 같은 표준 라이브러리는 `safe_globals` 에 명시적으로 추가해야 함. 허용 목록 관리 비용이 있음.
- 판정: **매우 유력.** SSAFY 2인 팀 기준에서 "격리 강도 vs 운영 비용" 균형이 가장 좋음.

### 옵션 3. subprocess + `resource.setrlimit` / Windows Job Object

**개요**: 학생 `cook.py` 를 별도 Python 프로세스로 띄워 stdin/stdout(JSON) 로 틱마다 state-assignment 를 주고받는다. 자식 프로세스에서 `resource.setrlimit` 또는 Windows 의 `CreateJobObject` 로 CPU/메모리 한도.

- 장점
  - 프로세스 격리로 결정론 보장이 쉬움. 시뮬레이터 메모리 오염 불가.
  - `setrlimit` 로 CPU/메모리 한도가 **커널이 강제**함 — 가장 확실한 한도.
  - Python 표준 라이브러리만으로 구현 가능.
- 단점
  - 매 틱 IPC 왕복 비용이 크다. 200틱 × JSON encode/decode → 한 판에 수십~수백 ms 오버헤드. 200명 제출을 순차 채점하면 분 단위.
  - Windows 의 Job Object API는 ctypes로 직접 불러야 해서 구현 복잡도가 올라감. Windows 학생 로컬에는 **제출 검증이 아니라 개발용** 이므로 한도 미강제라도 무관하다는 타협이 가능.
  - 파일시스템·네트워크 차단은 `setrlimit` 으로 불가 — 별도 `unshare`, seccomp 등이 필요. 즉 이 옵션 혼자로는 보안이 부족하다.
- 판정: **옵션 2의 보강용**으로는 쓸 수 있으나, 단독으로는 보안 커버리지 부족.

### 옵션 4. seccomp-bpf + setrlimit

**개요**: Linux 커널의 seccomp 필터로 학생 프로세스가 부를 수 있는 시스템콜을 직접 화이트리스트한다. `open`, `socket`, `execve` 등을 전부 차단하고 `read/write/brk/mmap` 정도만 허용.

- 장점: 격리 강도 최상. CTF 레벨의 악의 학생도 방어.
- 단점
  - **Linux 전용.** 학생 로컬(Windows)에서 동일한 메커니즘이 없다.
  - syscall 필터 설계가 정교해야 함. Python 런타임 자체가 `openat`, `mmap` 등을 쓰기 때문에 최소 세트를 뽑는 데 공수가 크다.
  - 2인 팀 8주 일정에서 주 결과물을 이 쪽에 빼앗기는 건 과잉 투자.
- 판정: **과잉.** SSAFY 프로젝트의 위협 모델을 넘어섬.

### 옵션 5. nsjail / firejail / bubblewrap

**개요**: Linux namespace + seccomp 를 감싸서 "컨테이너의 얇은 버전" 을 만드는 CLI 툴. `firejail --net=none --private python cook.py` 로 네트워크·파일시스템·PID·UID 를 격리.

- 장점
  - Docker 보다 훨씬 가볍다. 시작 오버헤드 수십 ms.
  - Linux 서버 채점 서버에서는 실용적 선택.
- 단점
  - **Linux 전용**. 학생 로컬에서 동일한 격리 불가 → 로컬 검증/제출 검증 이원화가 필요해짐.
  - 툴 3개 중 어느 것이 장기 유지될지 불확실 (nsjail는 활발, firejail은 커뮤니티 기반, bubblewrap은 flatpak 의존).
- 판정: **Linux 서버 한정이면 합리**. 그러나 학생 로컬에 같은 메커니즘이 없어 "내 컴퓨터에선 되는데 제출하면 안 된다" 가 발생할 수 있음.

### 옵션 6. Docker container per run

**개요**: 각 학생 제출을 `FROM python:3.11-slim` 기반 이미지에서 `--network=none --memory=256m --cpus=1 --read-only --tmpfs /tmp` 로 실행. tick-by-tick이 아니라 한 판 전체를 한 번에 실행 (시뮬레이터도 컨테이너에 포함).

- 장점
  - **Windows/macOS/Linux 전부 동일하게 동작** (Docker Desktop 또는 WSL2 백엔드).
  - 익숙한 기술 — SSAFY 교육과정에 Docker가 이미 포함되어 있음.
  - `--network=none` 으로 네트워크 차단, `--read-only` 로 파일시스템 보호, `--memory`/`--cpus` 로 리소스 한도. 한 명령줄로 다 됨.
  - 기존 판정 스크립트를 컨테이너에 얹기만 하면 되어 구현 복잡도 낮음.
- 단점
  - 컨테이너 시작 오버헤드가 1~3s. 한 판이 10s라면 25~30% overhead. 배치 채점에서는 누적이 크다.
  - Docker Desktop 라이선스 이슈: 학생 로컬이 Docker Desktop을 쓰면 상업 라이선스가 필요할 수 있음 — **SSAFY 교육기관은 면제되지만 졸업 후 재사용 시 주의**. 대안으로 Rancher Desktop, Podman Desktop 사용 가능.
  - 시뮬레이터와 학생 코드가 같은 컨테이너에 들어가면 학생 코드가 시뮬레이터 전역을 오염시킬 수 있음 — 옵션 2(RestrictedPython)와 결합하거나, 시뮬레이터를 외부에 두고 stdin/stdout 브릿지를 쓰는 구조가 더 안전.
- 판정: **제출 채점 서버의 기본 격리 계층으로 유력.** 로컬 검증은 Docker 없이 돌 수 있어야 하므로 별도 계층 필요.

### 옵션 7. gVisor / Kata Containers

**개요**: 사용자 공간 커널(gVisor) 또는 경량 VM(Kata) 로 컨테이너를 다시 감싸는 고강도 격리.

- 장점: 격리 강도 최상 — 실제 Cloud Run, Play with Docker 등이 이 계층을 씀.
- 단점
  - 설정 복잡도 폭발. 2인 팀에 부담.
  - Windows 로컬 미지원.
- 판정: **과잉.**

### 옵션 8. Pyodide (WASM 브라우저)

**개요**: CPython을 WebAssembly로 컴파일한 런타임. 브라우저 안에서 Python을 돌리고, 학생 코드를 브라우저 메모리 내에서 실행한다. 네트워크·파일시스템 접근이 기본적으로 브라우저 샌드박스에 의해 차단된다.

- 장점
  - **서버가 필요 없다.** 학생이 웹 페이지를 열고 코드 붙여넣기만 하면 그 자리에서 시뮬레이션이 돈다. 리플레이 UI(React)와 한 프론트엔드에 통합 가능.
  - 브라우저 보안 모델이 OS 격리와 비슷한 강도를 제공 — 학생 코드가 학생 PC 파일을 읽을 수 없음.
  - 결정론: Pyodide는 브라우저 JS 엔진 위에서 같은 시드로 동일 동작. FE 스토어가 이미 `시뮬레이터 + UI` 한 몸으로 구성되면 IPC 오버헤드도 없음.
  - **로컬/제출 검증이 동일 계층**. 학생 로컬에서 돌아간 결과와 서버 검증 결과가 일치.
- 단점
  - 첫 로드 시 Pyodide 런타임(~10MB gzip) 다운로드. 학생은 최초 1회 대기 후로는 빠름.
  - 학생 코드가 외부 Python 패키지를 import할 때 Pyodide 의 micropip 로 설치해야 함 — `heapq`, `collections`, `dataclasses` 등 표준 라이브러리는 그대로 사용 가능. `numpy`, `networkx` 는 Pyodide가 빌드해둔 버전을 로드할 수 있으나, 알고리즘 학습용이라면 표준 라이브러리만으로 충분하다.
  - **채점은 어떻게 하나?** → 학생이 제출하면 서버(헤드리스 Chrome 또는 Node.js + pyodide-npm)가 같은 Pyodide 런타임을 돌려 결과를 재현한다. CI에서 흔히 쓰는 패턴.
  - 시뮬레이터(Python) 를 JS/TS 로 포팅하지 않으려면 시뮬레이터 자체도 Pyodide 위에서 돌려야 함 — 즉 시뮬레이터도 Python으로 작성. 리플레이 UI는 JS, 시뮬레이터 + 학생 코드는 Pyodide, 이 사이는 `pyodide.runPython()` 으로 데이터를 주고받음.
- 판정: **강력한 후보.** 특히 "학생이 웹 페이지에서 바로 실행 → 리플레이 즉시 확인" 이라는 교육 루프가 이 프로젝트의 본질적 가치와 일치한다. Pyodide 선택 시 타당성 검토에 쓴 Java 시뮬레이터는 **검증용 참고 구현**으로만 남고, 실제 런타임은 Python으로 새로 써야 한다 — 단, 시뮬레이터는 단일 파일 수준이라 포팅 부담은 낮다 (Phase 1/Phase 2 Java 코드를 Python으로 1:1 재작성: 2~3일).

### 옵션 9. Judge0 / Codejail / E2B

**개요**: 기성 코드 실행 서비스. Judge0 는 온라인 저지 백엔드(Dockerized language runners + REST API), Codejail 은 edX 의 Python 전용 샌드박스(AppArmor + setrlimit), E2B 는 클라우드 기반 "AI 에이전트용 코드 인터프리터" 서비스.

- 장점
  - 이미 운영·디버그된 서비스를 바로 쓸 수 있음.
  - Judge0 는 온프렘 배포 가능 (Docker Compose 한 번).
- 단점
  - **Judge0** 는 1회 실행 모델(stdin 입력 → stdout 출력 → 종료) 이라, 매 틱 학생 함수를 호출하는 이 프로젝트 구조와 맞지 않음. 우회하려면 학생 코드에 자체 while 루프를 넣어 시뮬레이션을 흉내내야 하는데 그러면 학생이 본 스펙(`decide(state)` 호출형)과 달라짐.
  - **Codejail** 은 edX 전용으로 설치·설정이 Ubuntu AppArmor에 강하게 묶여 있음. Windows 로컬 ✗.
  - **E2B** 는 SaaS — 학생 코드를 외부 클라우드로 보내는 구조. SSAFY 교육 환경에서 학생 코드·데이터 외부 전송은 정책적으로 걸릴 가능성이 있고, 비용도 발생.
- 판정: **구조 불일치 또는 정책 리스크.** 기성 서비스 중 이 프로젝트에 정확히 맞는 것은 없음.

## 4. 의사결정 프레임

두 개의 관점이 있다.

### 관점 A. "FE 중심 — 웹 페이지에서 다 끝낸다"
- Pyodide + React + 단일 HTML 배포
- 시뮬레이터를 Python으로 (재)작성, 브라우저에서 실행
- 제출 채점은 headless Chrome/Node Pyodide 로 재현
- 장점: 로컬·서버 동일, 설치 0, 데모 쉬움
- 단점: 시뮬레이터 Python 재작성 필요 (Java → Python), 런타임 로드 지연 한 번

### 관점 B. "시뮬레이터는 Java, 학생 코드만 Python"
- 현재 Java 시뮬레이터(`CookSsafyFeasibility*.java`) 유지
- 학생 Python 코드를 **서버에서 Docker 격리** + **학생 로컬에서 RestrictedPython 격리** 의 이중 구성
- Java 시뮬레이터 ↔ Python 학생 코드 간 IPC (stdin/stdout JSON)
- 장점: 이미 검증된 Java 시뮬레이터 재사용
- 단점: 로컬·서버 격리 계층이 달라 "내 PC 에선 됐는데" 가 발생 가능. IPC 오버헤드. 언어 간 브릿지 유지 비용

## 5. 권장안

**관점 A — Pyodide 단일 계층**

### 근거
1. **교육 루프 품질이 압도적으로 좋다.** 학생이 `cook.py` 를 브라우저 에디터에 붙여넣고 "실행" 을 누르면 그 자리에서 리플레이가 돈다. 별도 CLI/서버 설치가 없다. SSAFY 교육생에게 "이 게임을 플레이하려면 Docker부터 깔아야 한다" 는 장벽이 사라진다.
2. **리플레이 UI와 런타임이 한 프론트엔드에 통합**된다. 현재 `08_리플레이_UI_공수추정.md` 의 FE 스택(React + Dagre + Zustand)에 Pyodide만 추가하면 됨. IPC 없음 → 레이턴시 0. 틱 로그·DAG 상태·KPI 가 Pyodide 실행 결과를 React 스토어에 직접 넣을 수 있다.
3. **격리 강도가 2인 팀 위협 모델에 충분**하다. 브라우저 샌드박스는 학생 PC 파일·네트워크 접근을 구조적으로 차단한다. `os.system` 같은 호출은 Pyodide 에 애초에 없다 (브라우저 WASM 런타임이라 OS syscall이 없음). 악의 없는 학습자 + 의도적 장난꾸러기 수준은 전부 커버된다.
4. **로컬·서버 동일 계층**. 제출 검증은 Node.js + `pyodide` npm 패키지 또는 headless Chrome 로 재현 — 학생 로컬과 동일 런타임이라 재현성 논쟁이 없다.
5. **구현 비용이 작다.** Pyodide는 README 5줄 수준 (`loadPyodide()` → `pyodide.runPython(studentCode)` → `pyodide.globals.get("decide")(state)` ). 시뮬레이터 Python 포팅이 들어가지만 Java 시뮬레이터가 단일 파일 ~500줄 수준이라 2~3일이면 끝난다.

### 반대 근거 — 관점 B가 나은 경우
- **이미 작성한 Java 시뮬레이터를 폐기하기 싫다**면 관점 B. 단, Java 시뮬레이터는 "타당성 검증" 을 위한 1회용 아티팩트로 설계한 점을 고려하면 지금 폐기해도 손실은 작다. Phase 1/2 실험 결과(정책 간 strict ordering)만 유지되면 된다.
- **다중 워커(Ch6~7) 에서 실제 OS 스레드/프로세스 병렬이 필요**하면 Pyodide의 단일 스레드 모델이 병목이 될 수 있다. 그러나 이 프로젝트는 **시뮬레이션이 틱 기반 결정론**이므로 실제 OS 병렬이 아니라 논리적 병렬(여러 직원이 같은 틱에 다른 노드를 시작) 로 표현된다 — 한 스레드 안에서 구현 가능. 따라서 이 단점은 실재하지 않는다.

### 결정
- **1차 선택: Pyodide (관점 A)**
- **보험: RestrictedPython** — Pyodide 도입 중 예상치 못한 문제가 나오면 "학생 코드만 RestrictedPython, 시뮬레이터는 호스트 Python" 으로 후퇴 가능. 두 옵션 모두 **Windows 에서 돌고**, **학생이 설치할 것이 없거나 pip 한 줄**이라는 공통점이 있어 후퇴 경로가 짧다.
- **Docker 옵션은 "제출 채점 서버의 2차 격리"** 로만 고려 — 1차 격리(Pyodide/RestrictedPython) 가 먼저 다 걸러낸 뒤에 서버가 재현 검증할 때 Docker를 덧씌우는 depth-in-defense.

### 채점 서버 구성 (관점 A 채택 시)
```
학생 제출 (cook.py)
        ↓
[제출 서버]
  - Node.js + pyodide npm
  - 시뮬레이터 Python 코드(내장) 로드
  - 학생 cook.py 를 pyodide.runPython() 으로 실행
  - 시드별 N회 실행 → 결과 집계
        ↓
[결과 DB]
  - 주문 성공률, 평균 완료시간, on-time 수, 로그
        ↓
[리더보드 / 리플레이 공유 URL]
```

- 제출 서버 1대로 동시 50건 × 10s 이하 처리. 큐잉은 간단한 in-memory 큐면 충분.

## 7. Residual Risks

1. **Pyodide 런타임 크기**: 초기 로드 ~10MB gzip. 반(班) 단위에서 동시 접속 시 네트워크 부하. 완화: CDN 캐싱 (`cdn.jsdelivr.net/pyodide/`) + SSAFY 내부 정적 서버에 미러링.
2. **표준 라이브러리 일부 미지원**: Pyodide 는 `threading`, `multiprocessing`, `subprocess` 가 의미 없음 (싱글 스레드 WASM). 이 프로젝트는 틱 기반 결정론이라 이 제약이 오히려 좋은 가드레일이지만, 학생이 실수로 `threading.Thread` 를 쓰려고 하면 에러 메시지가 명확해야 함 — FAQ·가이드 문서 필요.
3. **POC 실패 시 후퇴**: Pyodide 통합 POC(1일차) 에서 예상 문제가 발견되면 즉시 관점 B(RestrictedPython + Java 시뮬레이터 유지)로 전환. 이 후퇴는 결과물 손실 없이 가능 — 시뮬레이터 Python 포팅만 보류.
4. **브라우저 호환성**: Pyodide 는 최신 Chrome/Edge/Firefox 지원. SSAFY 교육생 PC 브라우저가 오래된 경우 대응 필요 — 그러나 SSAFY 환경은 최신 Chrome 기본이므로 현실적 리스크 낮음.
5. **제출 검증 성능**: Node + Pyodide 의 런타임 초기화 비용이 한 판당 200~500ms 추가. 50건 순차 처리 시 실벽시계 ~5분. 실시간 응답이 필요하면 pyodide 런타임 1회 로드 후 학생 코드만 교체하는 pool 전략으로 해결 가능.
