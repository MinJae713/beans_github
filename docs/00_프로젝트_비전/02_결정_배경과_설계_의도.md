# 결정 배경과 설계 의도

> 상태: accepted_candidate. 이 문서는 Nidhogg식 전선 돌파, ROUNDS식 패자 반격, 승리감 분리의 판단 맥락에 한해 임시 구현 기준으로 사용한다. 문서 상태와 binding 범위는 `05_문서관리_규칙/08_문서_상태_인덱스.md`를 우선한다.

이 문서는 Colosseum의 주요 결정을 왜 그렇게 했는지 설명한다.

다른 문서가 “무엇을 만들 것인가”를 다룬다면, 이 문서는 “왜 그렇게 만들기로 했는가”를 다룬다. 팀원이 중간에 합류하거나 AI 도구가 세션을 새로 시작했을 때, 단순 규칙뿐 아니라 판단 맥락까지 복구하는 것이 목적이다.

## 핵심 사고방식

| 원칙 | 의미 |
|---|---|
| 구간 돌파가 중심이다 | 단순 킬 수보다 전장을 밀고 당기는 흐름이 중요하다 |
| 패배자는 반격 수단을 얻는다 | 하지만 일부러 죽어서 성장하는 구조는 막는다 |
| 카드는 총알을 바꾼다 | MVP에서는 이동 능력 성장보다 전투 양상 변화에 집중한다 |
| 승리감은 시스템과 연출이 함께 만든다 | 최종 승리뿐 아니라 압박, 놀림, 반격, 돌파가 감정을 만든다 |
| 수치는 바뀔 수 있다 | 기준문서는 원칙을 잠그고, 수치는 프리셋에서 조정한다 |

## Nidhogg와 ROUNDS를 참고하되 그대로 복제하지 않는 이유

| 항목 | 결정 |
|---|---|
| 가져온 것 | Nidhogg의 전장 전진/후퇴 구조, ROUNDS의 패배자 반격 선택 구조 |
| 바꾼 것 | 카드 선택 자체보다 “전장 주도권을 잃은 쪽이 반격 수단을 얻는다”는 구조를 강조 |
| 포기한 안 | 단순 아레나 슈터, 순수 Nidhogg식 근접 결투, ROUNDS식 카드 선택 UI 중심 게임 |
| 설계 의도 | 한 번의 킬보다 “밀고 들어가고, 밀리고, 다시 반격하는 흐름”을 핵심 재미로 삼기 위함 |

ROUNDS처럼 죽을 때마다 강해지는 느낌은 참고하지만, 모든 사망에 보상을 주지는 않는다. Colosseum에서는 “전장을 빼앗긴 패배”가 더 큰 사건이고, 그 사건에 반격 수단을 연결한다.

## 5구간 전장 구조를 선택한 이유

| 항목 | 결정 |
|---|---|
| 전체 구조 | 총 5구간 |
| 전투 구간 | 가운데 3구간 |
| 최종 구간 | 양쪽 끝 1구간씩, 승리 예정 캐릭터만 달려가는 구간 |
| 포기한 안 | 모든 구간을 전투 구간으로 만드는 안, 최종 구간 진입 즉시 승리 처리하는 안 |
| 설계 의도 | 전투의 밀고 당김과 최종 승리 연출을 분리하기 위함 |

전투 구간에서는 플레이어 두 명이 모두 등장하고, 사망, 돌파, 리스폰, 카드 선택이 반복된다. 최종 구간에 진입하면 상대는 리스폰되지 않고, 승리 예정 캐릭터만 등장한다. 이 캐릭터가 최종 지점에 도달하면 조작 불가능한 연출이 시작되고 매치 최종 승리가 확정된다.

최종 구간은 단순한 이동 구간이 아니라 승리를 체감하는 구간이다. 달려가는 동안 이미 이긴 느낌을 주되, 최종 연출이 시작되기 전까지는 승리 확정 시점을 명확히 분리한다.

## 이동 주도권과 GO UI를 둔 이유

| 항목 | 결정 |
|---|---|
| 이동 주도권 | 직전에 상대를 사망시키거나 구간을 돌파한 플레이어가 가진다 |
| 주도권 보유자 | 공격 방향으로만 진행 가능하며 뒤로 물러날 수 없다 |
| 비주도권자 | 뒤로 물러날 수 있으나 경계 이탈 또는 낙사 위험을 감수한다 |
| UI | 화면 상단에 `=> GO` 또는 `GO <=` 형태로 진행 방향을 표시한다 |
| 설계 의도 | 전투 후 “어느 쪽으로 밀어야 하는지”를 명확히 보여주고, 전장 압박을 지속시키기 위함 |

자유롭게 양방향 이동을 허용하면 사망 이후의 전장 흐름이 흐려진다. 이동 주도권은 플레이어에게 현재 게임의 방향성을 직접 알려주는 장치다.

## 모든 사망에 카드를 주지 않는 이유

| 항목 | 결정 |
|---|---|
| 모든 사망 카드 지급 | MVP 기준 반대 |
| 기본 카드 지급 트리거 | 구간 돌파 패배 |
| 일반 전투 사망 | 이동 주도권 전환은 일어나지만 즉시 카드 지급은 하지 않음 |
| 보류 항목 | 상대가 만든 일반 사망에도 제한적으로 카드를 줄지 여부 |
| 설계 의도 | 일부러 죽어서 성장하는 전략과 과도한 카드 인플레이션을 막기 위함 |

카드는 반격 수단이다. 하지만 모든 죽음에 카드를 주면 전투보다 카드 선택이 게임의 중심이 되고, 플레이어가 일부러 죽는 전략도 가능해진다. 그래서 MVP에서는 “구간을 빼앗긴 패배”에만 카드 보상을 연결한다.

## 카드를 총알 중심으로 제한한 이유

| 항목 | 결정 |
|---|---|
| MVP 카드 방향 | 총알, 발사 리듬, 투사체 성질을 바꾸는 카드 |
| 제외 | 이동 속도 증가, 점프 강화, 대시 강화, 2단 점프 같은 지속 이동 성장 |
| 포기한 안 | 총 종류를 통째로 교체하는 무기 슬롯 교체 구조 |
| 설계 의도 | 전투 양상은 바꾸되, 캐릭터 조작 밸런스를 과도하게 흔들지 않기 위함 |

이 게임의 MVP 전제는 “총알을 컨트롤한다”이다. 카드는 단순 피해량 증가가 아니라 탄환의 성질, 압박 방식, 공간 장악 방식을 바꾸는 방향으로 설계한다.

이동기 카드는 액션성을 높일 수 있지만, 점프와 대시가 지속적으로 강화되면 맵 구조, 카메라, 리스폰, TTK가 한꺼번에 흔들린다. 그래서 MVP에서는 확장 후보로만 둔다.

## 카드 티어 제한을 둔 이유

| 항목 | 결정 |
|---|---|
| 티어 개방 | 모든 티어는 처음부터 등장 가능 |
| Common | 낮은 하드캡을 두지 않음 |
| Rare | 프리셋에서 제한값 관리 |
| Epic | 최대 2장 |
| Legendary | 최대 1장 |
| 설계 의도 | 강한 카드를 일찍 보는 재미는 살리되, 게임 시스템이 통제 불가능해지는 것을 막기 위함 |

티어를 후반에만 열면 초반 전투가 밋밋해질 수 있다. 반대로 강한 카드가 무제한 중첩되면 한쪽이 통제 불가능하게 강해진다. 그래서 모든 티어를 처음부터 열어두되, Epic과 Legendary는 보유 수 제한으로 통제한다.

## MVP 무기 후보를 제한한 이유

| 항목 | 결정 |
|---|---|
| 우선 검증 | 기본탄, 넉백/충격탄, 반사탄, 곡사탄 |
| 이후 후보 | 저격탄 |
| MVP 제외 | 레이저, 즉발 광선, 복잡한 상태이상 탄 |
| 설계 의도 | 구현 난도와 전투 가독성을 동시에 관리하기 위함 |

넉백, 반사, 곡사는 전투 양상을 명확히 바꾼다. 반면 레이저나 즉발 광선은 투사체 전제를 깨고, 상태이상 탄은 카드 조합과 UI 설명 비용이 커진다. MVP에서는 전투 양상 변화가 분명하면서도 구현과 검증이 가능한 후보부터 다룬다.

## TTK를 너무 짧게 잡지 않는 이유

| 항목 | 결정 |
|---|---|
| 방향 | 순간 삭제보다 읽고 대응할 수 있는 전투 |
| 이유 | TTK가 너무 짧으면 플레이타임 대부분이 카드 선택으로 흐른다 |
| 포기한 안 | 기본 한 방 킬, 초반 저격 원샷 중심 전투 |
| 설계 의도 | 카드 선택보다 실제 교전이 게임의 중심이 되게 하기 위함 |

카드 선택 시간이 짧지 않다면, 전투 시간이 너무 짧아서는 안 된다. 플레이어가 위치, 점프, 엄폐, 구조물, 탄환 특성을 읽고 대응할 시간이 있어야 한다.

## 딱밤과 승리감 연출을 카드 효과로 넣지 않는 이유

| 항목 | 결정 |
|---|---|
| MVP 특수 기믹 | 딱밤 |
| 확장 후보 | 슬라이딩 태클, 이모트, 혹 연출 강화 |
| 카드 효과 제외 | 승리감 연출, 딱밤, 혹 상태는 카드 효과로 넣지 않음 |
| 설계 의도 | 심리적 재미와 전투 밸런스 시스템을 분리하기 위함 |

딱밤과 혹은 “상대를 이겼다”는 감정을 강화하는 장치다. 이를 카드 효과로 넣으면 카드 밸런스와 승리감 연출이 섞인다. MVP에서는 딱밤을 단순 기믹 또는 presentation 중심 기능으로 두고, 카드 시스템은 전투 양상 변화에 집중한다.

## Unity 2D/Fusion 구조를 기준으로 삼은 이유

| 항목 | 결정 |
|---|---|
| 기준 엔진 | Unity |
| 물리 기준 | Rigidbody2D, Collider2D, NetworkRigidbody2D |
| 네트워크 기준 | Photon Fusion 2 |
| 금지 방향 | 신규 3D Rigidbody, ConfigurableJoint, 액티브 래그돌 전제 |
| 설계 의도 | 팀원이 작성한 프로토타입과 기술스택 결정을 기준으로 구현 리스크를 줄이기 위함 |

초기에는 2.5D와 3D 물리 기반 액티브 래그돌도 검토했지만, 현재 팀의 확정 기술스택과 프로토타입은 2D 물리와 Fusion을 기준으로 한다. 따라서 팀 공유 기준문서에서는 3D 물리 확장을 허용하지 않는다.

## AI 협업 운영 원칙을 문서화한 이유

| 항목 | 결정 |
|---|---|
| 방향 | 특정 AI 도구를 강제하지 않고, 작업 방식과 검증 기준을 표준화 |
| 이유 | 팀원들이 모두 AI를 적극 활용하므로 세션 리셋과 담당자 간 해석 차이를 줄여야 함 |
| 포기한 안 | 각자 AI에게 자유롭게 지시하고 결과만 합치는 방식 |
| 설계 의도 | 게임개발의 의존성 폭증을 막고, 같은 기준으로 작업을 시작하고 멈추게 하기 위함 |

AI 협업 문서는 AI를 통제하기 위한 문서가 아니라, 사람이 AI에게 일을 맡길 때 필요한 공통 언어다. 작업 브리핑, 수정 가능 파일, 금지 파일, 검증 방식, 중단 조건이 있어야 여러 AI가 동시에 작업해도 결과물이 충돌하지 않는다.

## 팀원이 가장 먼저 복구해야 하는 결론

| 질문 | 답 |
|---|---|
| 이 게임의 핵심은 무엇인가 | 죽을수록 무작정 강해지는 게임이 아니라, 전장을 빼앗긴 쪽이 반격 수단을 얻는 게임 |
| 카드는 무엇을 바꾸는가 | 총알과 발사 양상을 바꾼다 |
| 전투의 목표는 무엇인가 | 상대를 죽이는 것만이 아니라 구간을 밀고 최종 구간까지 돌파하는 것 |
| MVP에서 조심할 것은 무엇인가 | 모든 사망 보상, 이동 성장 카드, 3D 물리 확장, 수치 하드코딩 |
| 협업에서 가장 위험한 것은 무엇인가 | 씬/프리팹/네트워크 설정/게임 규칙을 각자 다르게 고치는 것 |
