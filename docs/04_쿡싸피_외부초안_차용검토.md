# 쿡싸피 외부 초안 차용 검토

## 검토 대상
- 사용자 제공 `쿡싸피 v0.1` 초안
- 현재 로컬 문서 세트
  - `00_기획브리프_초안.md`
  - `01_문제정의_핵심컨셉.md`
  - `02_핵심시스템_초안.md`
  - `03_챕터구조_초안.md`

## 총평
- 이전 검토 시점에는 외부 초안이 현재 방향보다 `스케줄링` 쪽으로 너무 기울어져 있다고 봤다.
- 하지만 현재 방향이 `수동 턴제 퍼즐`이 아니라 `코드 작성형 시뮬레이션`으로 확정되면서, 외부 초안은 오히려 매우 강한 레퍼런스가 되었다.
- 특히 `decide(state)` API, 영업 시간 고정, 결정론 시드, 리더보드 구조, 시각 연출 포지셔닝은 그대로 참고할 가치가 높다.
- 다만 현재 프로젝트는 여전히 `위상정렬을 기반 개념으로 앞세운다`는 점에서 외부 초안을 약간 조정해 받아오는 편이 맞다.

## 현재 기준 최종 결론
- `운영 구조는 적극 차용`
- `학습 포지셔닝은 보정해서 차용`
- 추천 방향:
  - 외부 초안의 `코드 기반 주방 시뮬레이터` 구조를 메인 프레임으로 수용
  - 초반 챕터와 문서 표현은 `위상정렬 기반`을 더 앞에 세운다
  - 복수 직원과 assignment 심화는 단계적 확장으로 둔다

## 그대로 차용해도 좋은 것

### 1. `decide(state)` 단일 함수 구조
- 현재 방향과 가장 잘 맞는다.
- 학생이 만지는 핵심 인터페이스가 한 곳에 모여 설명력이 좋다.
- 배틀싸피류 감성과도 잘 맞는다.

### 2. 틱 기반 영업 시간 구조
- 주문 도착, 작업 완료, 새 작업 시작을 일관되게 시뮬레이션하기 좋다.
- 재현성과 디버깅 가능성도 높다.

### 3. 결정론 설계
- 같은 코드와 같은 시드에서 결과가 같아야 한다는 원칙은 그대로 유지해야 한다.
- 리더보드, 테스트, 데모, 회고 모두에서 중요하다.

### 4. 종료 후 평가형 채점
- 영업 시간을 끝까지 돌리고 성공률과 지연 시간을 평가하는 구조는 적합하다.
- 학생은 중도 실패보다 `왜 이 정책이 무너졌는지`를 끝까지 볼 수 있어야 한다.

### 5. 외부 게임 차용 프레임
- `[G] 로직`, `[V] 시각`, `[X] 거부` 구분은 계속 유지할 가치가 있다.
- 특히 Overcooked와 Diner Dash에서 무엇을 시각만 빌리고 무엇을 버릴지 명확히 적을 수 있다.

### 6. 시각 연출 방향
- 상단 주문 티켓
- 마감 타이머 또는 인내심 하트
- 작업 진행 게이지
- 완료 시 피드백 효과
- 실패 시 시각적 원인 표시는 현재 프로젝트에도 잘 맞는다.

## 수정해서 차용할 것

### 1. 한 줄 요약
- 외부 초안은 `Job-Shop 스케줄링 알고리즘 챌린지`라고 표현한다.
- 지금 방향에서는 이 문장이 너무 스케줄링 중심이다.
- 현재 버전은 아래처럼 보정하는 편이 맞다.
  - `레시피 DAG와 주문 타임라인을 바탕으로 학생 코드가 주방을 운영하는 위상정렬 기반 시뮬레이션 게임`

### 2. 학습 목표의 순서
- 외부 초안은 FIFO, SJF, `EDF (Earliest Deadline First)`, matching이 빠르게 전면에 나온다.
- 현재 프로젝트는 초반에 `가능한 작업 판별`과 `선행조건 이해`를 먼저 강조해야 한다.
- 즉 학습 목표의 순서는 아래가 적합하다.
  - 위상정렬
  - 시간 제약 하 우선순위
  - 공유 작업
  - 복수 직원 assignment

### 3. 상태 모델 표현 방식
- 외부 초안의 `remaining_ops` 중심 표현은 구현에는 편할 수 있다.
- 하지만 현재 문서와 발표에서는 `nodes / edges / available_node_ids`처럼 DAG가 직접 드러나는 표현이 더 적합하다.

### 4. 챕터 도입 순서
- 외부 초안은 단일 공정 주문으로 시작해서 Ch4에서 다단계로 간다.
- 현재 프로젝트는 Ch1부터 DAG가 보여야 한다.
- 그래서 현재 문서에서는 초반 챕터를 더 위상정렬 친화적으로 재배치했다.

## 보류 또는 후반으로 미룰 것

### 1. 복수 직원 기본 전제
- 좋은 확장 축이지만 MVP 기본값으로 두기엔 무겁다.
- 현재는 Ch7 이후 확장으로 두는 편이 맞다.

### 2. Routing / Dispatching 분리 서술
- 후반 고급 모드에서는 유용하다.
- 하지만 초반 문서에서 너무 강조하면 프로젝트 정체성이 `assignment 문제`로 읽힐 수 있다.

### 3. SJF / EDF를 전면에 세운 브랜딩
- 이 개념들은 후반 설명에 좋다.
- 다만 메인 브리프의 첫 문장부터 나오면 `위상정렬 기반` 설명이 약해진다.

## 현재 프로젝트에 실제로 반영한 차용 포인트
- `decide(state)` 중심 학생 API
- 틱 기반 시뮬레이션
- 영업 시간 고정
- 결정론 시드
- 종료 후 평가
- 주문 티켓과 인내심 기반 리플레이 UI
- 단계적 챕터 누적 구조

## 최종 판단
- 현재 기준에서 외부 초안은 `부분 차용`이 아니라 `핵심 뼈대 차용`에 가깝다.
- 다만 문서 언어와 챕터 순서를 조정해 `위상정렬 기반` 정체성을 더 선명하게 만드는 것이 필요하다.
