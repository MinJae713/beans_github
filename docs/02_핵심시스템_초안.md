# 핵심 시스템 초안

## 1. 기본 구조
- 학생은 `cook.py` 같은 단일 파일에서 `decide(state)`를 구현한다.
- 시뮬레이터는 영업 시간 동안 매 틱 현재 상태를 학생 코드에 전달한다.
- 학생 코드는 idle 상태인 직원에게 다음 작업을 할당하거나, 아무 것도 하지 않도록 결정한다.
- 실행 결과는 점수, 로그, 리플레이 형태로 제공된다.

## 2. 시간 모델
- 시간은 `틱 기반`으로 진행한다.
- 한 판의 영업 시간은 고정 길이를 가진다.
  - 예: 200틱
- 같은 코드와 같은 시드에서는 주문 도착과 메뉴 분포가 항상 동일해야 한다.
- 즉, 결정론 시뮬레이션이 기본 원칙이다.

## 3. 학생 API

### MVP 방향
```python
def decide(state: KitchenState) -> Assignment | None:
    ...
```

### 확장 방향
```python
def decide(state: KitchenState) -> list[Assignment]:
    ...
```

### 설계 원칙
- MVP는 직원 1명 기준이므로 단일 Assignment 또는 None으로도 충분하다.
- 다만 장기적으로 복수 직원을 고려하면 `list[Assignment]` 구조로 확장 가능해야 한다.
- 선점은 허용하지 않는다.
  - 이미 작업 중인 직원에게 새 지시를 내려도 무시된다.

## 5. 레시피 DAG 시스템

### 표현 원칙
- 각 메뉴는 `노드 + 간선`으로 표현한다.
- 노드는 작업 단위를 의미한다.
  - 예: 손질, 끓이기, 굽기, 조합, 플레이팅
- 간선은 선행조건을 의미한다.
  - A -> B 는 A 완료 후 B 가능

### 노드 상태
- 잠김
- 가능
- 진행 중
- 완료

### 후반 확장
- 동일한 준비 노드를 여러 주문이 참조할 수 있다.
- 예:
  - `육수 준비` 완료 시 우동과 라면의 후속 조리 작업이 가능 상태가 되어, 이후 스케줄링 후보가 동시에 늘어남

## 6. 작업 시간 시스템

### 원칙
- 작업 시간은 모두 같지 않다.
- 하지만 `작업 타입별 고정 시간`으로 단순화한다.

### 예시 시간표
- 손질: 1틱
- 섞기: 1틱
- 플레이팅: 1틱
- 조리: 2틱
- 끓이기: 2틱
- 굽기/튀기기: 3틱

### 의미
- 학생 코드는 어떤 작업이 빨리 끝나고 어떤 작업이 오래 걸리는지 고려해야 한다.
- 결과적으로 `가능한 작업 판별`과 `우선순위 선택`이 동시에 발생한다.

## 7. 시뮬레이션 루프

### 한 틱의 흐름
1. 현재 틱 갱신
2. 새 주문 도착 처리
3. 작업 완료 처리
4. 완료 결과를 반영해 새 가능 노드 계산
5. `state` 생성
6. 학생 코드 `decide(state)` 호출
7. 반환된 Assignment 유효성 검증
8. 유효한 작업만 시작
9. 로그 기록

### 검증 규칙 초안
- 존재하지 않는 직원 지정 시 무시
- idle이 아닌 직원 지정 시 무시
- 존재하지 않는 주문 또는 노드 지정 시 무시
- 현재 가능한 노드가 아닌 작업 지정 시 무시
- 무시된 지시는 로그에 남겨 디버깅 가능하게 한다

## 8. 평가 시스템

### 기본 방향
- 즉시 실패보다 `최종 평가형`이 적합하다.
- 영업 시간은 끝까지 진행한다.

### 핵심 지표
- 주문 성공률
- 평균 주문 완료 시간
- 평균 지연 시간
- 미완료 주문 수
- 잘못된 Assignment 횟수

### 챕터 통과 예시
- 주문 성공률이 챕터별 임계값 이상이면 통과
- 동점 비교는 평균 완료 시간 또는 평균 지연 시간으로 처리

## 9. 리플레이 및 디버깅 UI

### 목적
- 학생이 코드를 고칠 이유를 명확히 보여준다.

### 필요한 화면 요소
- 상단 주문 티켓
- 각 주문의 남은 인내심/마감 표시
- 현재 진행 중 작업과 남은 시간
- 레시피 DAG 상태 표시
- 틱 로그
- 실패 주문의 원인 태그
  - 늦은 공유 준비작업
  - 긴 작업 타이밍 오류
  - 잘못된 Assignment

## 10. 현재 시스템 결론
- MVP 핵심은 `decide(state)` 기반 틱 시뮬레이션이다.
- 학생은 직접 플레이하지 않고 정책 코드를 작성한다.
- 게임의 재미는 조작감이 아니라 `내 로직이 주방 전체 흐름을 어떻게 만들었는가`를 보는 데서 나온다.
